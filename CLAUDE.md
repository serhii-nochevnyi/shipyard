# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo ships **the shipyard delivery conveyor** plus the environment it runs in. It contains no application code — it is infrastructure. Two deliverables, and they are frequently confused:

1. **The conveyor** (`plugins/delivery-pipeline/` + `capabilities/delivery-pipeline/`) — investigate → decompose → deliver, with its deterministic git/`gh`/graph layer and blocking GSD gates. It targets **two runtimes**: Claude Code (canonical) and the OpenAI Codex CLI (generated from the same commands by `scripts/gen-codex-shipyard.cjs`, installed host-side by `make install-shipyard-codex`). It also installs into host Claude Code (`make install-shipyard-claude-hook`, `make install-shipyard-capability`).
2. **The container** (`Dockerfile.base` + `Dockerfile`) — a remote **Claude Code** dev environment, runnable via Compose or deployable to Kubernetes, baking a pinned toolchain, the Claude Code CLI, Claude Code plugins (gsd-core, andrej-karpathy-skills, the in-repo `shipyard` conveyor, four official plugins) and default MCP server configs. The image is Claude-Code-only by design; Codex is never installed into it.

**Consequence for edits:** a behavior change to a command doc or a script belongs to the conveyor and therefore reaches BOTH runtimes — so it must not assume Claude-only capabilities (the Workflow tool is the standing example: absent on Codex, hence the Agent fallback). Codex artifacts are generated, never hand-edited; edit the Claude command and re-run the installer.

The `workspace/` directory is the mount point users do their actual work in at runtime; it is intentionally empty in the repo.

## Build & run

All workflows go through the `Makefile`. The image is built in two stages — base then overlay — and you almost always need both before running:

```bash
make build-base        # Dockerfile.base: OS, Node, Go, kubectl, helm, Claude Code CLI, context7-mcp, typescript-language-server
make build-dev-image   # Dockerfile: overlay that installs gsd-core + registers karpathy/shipyard + official plugins + the auto-route hook
make run-docker        # docker compose run --rm dev  (drops you into /workspace)
make deploy-k8s        # kubectl apply of k8s/{configmap,pvc,service,statefulset}.yaml
```

`make build-base` runs `sync-ssh-config` first (stages only `config`, `known_hosts`, `known_hosts2` from `~/.ssh` — never private keys; a host with no `~/.ssh` is fine and produces an empty staging dir). `make build-dev-image` runs `sync-karpathy-skills` first to stage the andrej-karpathy-skills plugin source into `.build/`. `make up` / `make run-docker` depend on `ensure-image` (builds when the overlay tag is missing) and `runtime-dirs` (creates every host path the compose mounts need, and migrates the legacy credentials file).

Before first run, copy `.env.example` to `.env`. Key vars: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token` on the host), `CLAUDE_STATE_DIR` (default `./.claude-state`, the persisted remote-MCP OAuth state), `SSH_AUTH_SOCK_HOST`, `SSH_DIR` (opt-in: expose real `~/.ssh` including private keys — leave unset to use agent forwarding), `GITHUB_TOKEN`/`GH_TOKEN`, `GSD_CORE_VERSION` (optional pin override).

## Tests

```bash
make test-fast          # unit + graph + worktree + docs + ssh-sync — no Docker, no network
make test-unit          # frontmatter parser, model policy, ticket↔PR matching
make test-graph         # Gate 2 contract + plan:post gate applicability, on fixture projects
make test-worktree      # epic-branch.sh + ticket-worktree.sh against real local git repos
make test-sentinel      # state-sync → gate/merge_scope → sentinel duty, against a stubbed gh
make test-docs          # README + .env.example invariants
make test-ssh-sync      # sync-local-ssh-config.sh behavior
make test-k8s           # kubectl dry-run over k8s/
make test-base          # base image contents
make test-overlay       # overlay image / plugin install
make test-runtime       # full compose runtime (mounts, credential round-trip, hook)
make test-mcp-runtime   # MCP server config at runtime
make test-codex-shipyard# Codex generator + installer (needs network)
make test               # everything, in order
```

**Run `make test-fast` on every edit** — it is seconds, needs nothing installed, and covers the deterministic layer where the sharp bugs live.

`tests/smoke/docs-smoke.sh` is a contract on `README.md`, `.env.example`, `docker-compose.yml`, `Makefile` and `k8s/`: it greps for required phrases, checks the documented command surface against `plugin.json`, verifies every `make <target>` the README names exists, and asserts the mount invariants (no `${PWD}` mount, no single-file credentials mount, no mount over `/home/dev/.ssh`). **If you change documented behavior, update the README to match or `make test-docs` will fail.**

## Architecture

**Two-layer image, separated by change frequency.** `Dockerfile.base` (`claude-shipyard-base:test`) installs the slow-moving, pinned toolchain — versions are `ARG`s at the top (Node, Go, kubectl, helm, Claude Code CLI via npm `@anthropic-ai/claude-code`, context7-mcp binary, typescript-language-server). Every downloaded binary is checksum-verified. `Dockerfile` (`claude-shipyard:test`) is a thin overlay over the base that installs gsd-core and registers the remaining plugins; iterate here when changing plugins, not the base.

**Base image installs Claude Code via npm.** The base image runs `npm install -g @anthropic-ai/claude-code@<version>` with a pinned version controlled by the `CLAUDE_CODE_VERSION` build arg.

**Overlay image installs gsd-core and registers plugins.** The overlay runs `npx --yes @opengsd/gsd-core@<version> --claude --global --profile=full` during build, which writes Claude Code plugin configuration under `~/.claude`. The andrej-karpathy-skills plugin is staged via `scripts/sync-karpathy-skills.sh` (clones at a pinned commit `KARPATHY_SKILLS_REF`) into `.build/karpathy-skills/` and registered with `claude plugin`. The in-repo `shipyard` plugin (`plugins/delivery-pipeline/`) is copied to `/opt/delivery-pipeline` and registered the same way; it implements the delivery conveyor from `docs/gsd_multilevel_delivery_pipeline.md` (`/shipyard:route`, `/shipyard:investigate`, `/shipyard:decompose`, `/shipyard:deliver`, `/shipyard:bench`, plus deterministic scripts under `plugins/delivery-pipeline/scripts/`). Four additional plugins come from the official `claude-plugins-official` marketplace (`anthropics/claude-plugins-official`): `skill-creator`, `code-simplifier`, `github` (GitHub MCP server), and `typescript-lsp`. Their versions are pinned by the marketplace's GitHub ref at clone time. The overlay also installs the **shipyard auto-route `UserPromptSubmit` hook** into the image's own `~/.claude/settings.json`, so the container needs no manual setup for the router to surface. The host `~/.config/gh` directory is mounted read-only at `/home/dev/.config/gh` so `gh` can use host authentication.

**The GSD capability's plan:post gate is applicability-scoped.** The companion capability (`capabilities/delivery-pipeline/`) is installed at **global** scope, so its blocking `plan:post` gate runs in every GSD project on the machine. Gate 2's contract (a `delivery:` block, non-empty `files_modified`/`requirements`, no file overlap) belongs to the conveyor alone, so `checks/graph-gate.cjs` decides applicability **before** strictness: it passes when there are no plans, when no plan carries a `delivery:` block, or when `pipeline.graph_gate` is `false` — and fails closed for real conveyor projects. Adding a gate here without an applicability check breaks planning for every unrelated project in the container.

**The deterministic layer is shared and tested.** `plugins/delivery-pipeline/scripts/` holds the code the skills call instead of improvising git/gh:
- `frontmatter.cjs` — the YAML-subset parser for plan frontmatter. It either represents a construct or reports a structured error; it never half-parses. A trailing `# comment` used to be folded into the last `files_modified` entry, which silently voided Gate 2's file-overlap guarantee.
- `pipeline-config.cjs` — the single config reader plus the role × risk × attempt model policy and its matching reasoning effort (`model <role> [--json] [flags]`). **It only ever emits the tier aliases `opus`/`sonnet`/`haiku`/`fable`, because the Agent tool validates `model` against exactly that set** — a full model ID or a suffixed alias like `opus[1m]` is rejected on input. `fable` (Claude Fable 5, Opus-tier + 1M context) is the alias that expresses what `opus[1m]` was reaching for; it is paid, so it is opt-in only. Effort mirrors GSD's light/standard/heavy defaults and follows the resolved tier. Unknown config keys and non-alias values produce warnings rather than silent no-ops.

  **shipyard is a superstructure over GSD, so the installers now install GSD.** `ensure-gsd-core.sh <claude|codex> [version]` runs from both host installers and defaults to `latest`. That default is deliberate and is the opposite of the image rule: a superstructure that pins its base rots against it, and the evidence was a real split on this machine: the plugin at 1.10.0, both npm globals at 1.9.1 — including `~/.codex/gsd-core`, which is where `gen-codex-shipyard.cjs` reads its converter AND its model catalog from. **Read `$CORE/VERSION` to answer "what is installed"**; an earlier pass diffed the npm package tree against the installed tree and concluded the Codex side was older than 1.8.0, which was simply false — the two layouts are different artifacts, so a file-count diff between them measures nothing. On Claude there are TWO installs and updating one does not move the other — the npm global (what `gsd-tools` resolves and our scripts read) and the PLUGIN `gsd-core@gsd-core` from marketplace `open-gsd/gsd-core` (what supplies the `/gsd-*` slash commands); the script refreshes both, adding the marketplace and installing the plugin when absent, and skips the plugin half entirely when the `claude` CLI is not on PATH. Codex has no plugin concept. `GSD_CORE_VERSION` pins; `SHIPYARD_GSD_AUTO_INSTALL=0` opts out entirely, and **two callers must use it**: the Dockerfile (it installs a pinned gsd-core a few lines earlier, and a reproducible image must not have `latest` pulled in behind it) and `codex-shipyard-smoke.sh` (it pins a version on purpose and asserts against THAT converter). For Codex the install is not a convenience — the generator cannot convert a command without gsd-core — so a failed install there is fatal rather than a warning, but only when nothing is already installed.

  **Models are TWO layers, and we own only the first.** `pipeline-config.cjs` decides the TIER (`opus`/`sonnet`/`haiku`/`fable`) plus a universal effort — that is shipyard policy, and it is the single source. GSD owns the second layer: `runtimeTierDefaults.<runtime>` in its model catalog maps a tier to a concrete model (`opus` → `claude-opus-4-8` on claude, `gpt-5.6-sol` + `xhigh` on codex), overridable by the user through `model_profile_overrides.<runtime>.<tier>` and `model_policy.runtime_tiers.<runtime>.<tier>`. **On Claude the ladder reaches agents at CALL time** (Workflow passes `model`/`effort` into every `agent()`); **on Codex an agent is a static `.toml`, so the tier must be baked in at generation time** — `gen-codex-shipyard.cjs` resolves it through GSD's own catalog rather than hardcoding, so a user remap takes effect. Without that, all seven Codex agents ran at the CLI default and arch-review was the same model as drift-check. The Codex values are necessarily the ladder's BASELINE: risk is per-ticket and attempts are per-run, neither of which exists when a static file is written.

  **`fable` is Claude-only, and an UNSET runtime must not assume it.** It is the top tier for exactly two roles — `arch-review` and `integrator` — because the 1M window is what actually distinguishes them (both read the whole diff against every ADR at once); anywhere else it is only a costlier `opus`. GSD's tier vocabulary is `opus|sonnet|haiku`, so `fable` is invalid in `models.*` and in the Codex `.toml`. The unset-runtime default is `opus`, deliberately asymmetric: `opus` on Claude costs a smaller window on work that usually fits, while `fable` on Codex is a model id nothing resolves.

  **GSD settings are read, warned about — and now fixable in one act.** `gsd-tune.cjs` is the button the warnings never had: it reports (default, exit 1 on drift) or `--apply`s the settings a conveyor project needs on its runtime, splitting them into REQUIRED (`runtime`, `git.branching_strategy: none` — the conveyor is incorrect without them) and tuning (models, effort, `workflow.use_worktrees`, `model_profile` mirroring `pipeline.model_policy`). It never writes without `--apply`, preserves every other key, and refuses an unparseable config. It runs in TWO places, because the settings live in two. **Step 0 of deliver** handles the project (`.planning/config.json`). **The installers** handle `--global` (`~/.gsd/defaults.json`) — the file a directory with NO `.planning/` inherits, which is a new project before anyone configures it; the moment a project has its own config.json, even an empty one, the global file stops contributing. The global set is deliberately MODEL-SHAPED ONLY: it is inherited by GSD projects that never asked for shipyard, and an ordinary one legitimately wants phase branches, so `git.branching_strategy`, `workflow.*` and `agent_skills` stay per-project. That file also holds ONE `runtime` shared by both installs, so whichever installer ran last wins — which is how it came to say `codex` on a Claude machine, where every unconfigured directory then resolved `gpt-5.6-sol`. `--global` announces such a handover instead of performing it silently. **On Claude it also sets `model_overrides.gsd-planner` and `model_overrides.gsd-code-reviewer` to `fable`** — the two GSD agents whose work is genuinely context-bound. Note WHICH key: `model_profile_overrides.claude.*` and `model_policy.runtime_tiers.claude.*` look like the lever and are INERT, because the resolver's runtime-tier step is guarded by `configRuntime !== 'claude'` and Claude returns the bare tier ALIAS for its Agent tool to resolve. `model_overrides.<agent-id>` is step 1, ahead of all tier logic, and accepts a bare alias (`CLAUDE_AGENT_ALIASES` includes `fable`). Verified against GSD's own resolver: planner goes `opus` → `fable`, code-reviewer `sonnet` → `fable`. Equally, `model_profile` takes `quality|balanced|budget|adaptive|inherit` (`VALID_PROFILES`) — `golden` is ONLY the raw field name inside model-catalog.json, which `MODEL_PROFILES` rebuilds as `quality: meta.golden` at load. Reading the JSON and concluding the vocabulary is `golden` is a trap this repo fell into once, and an expensive one: the resolver does `agentModels[profile] || agentModels['balanced']`, so a name outside the vocabulary does not fail — it silently becomes `balanced`. Check `VALID_PROFILES`, never the catalog's field names. Note `adaptive` exists and is what GSD now recommends: role-based, `adaptiveTierMap[routingTier]` — the same philosophy as our own ladder. The runtime decides the `agent_skills` FORM: `global:shipyard:delivery-rules` on claude (plugin-namespaced) versus `global:shipyard-delivery-rules` on codex (flat, generator-prefixed) — a mix of the two resolves nowhere and is silently skipped, which is how the first draft of this script nearly rewrote a correct config into a broken one.

  **Config namespaces:** `delivery_pipeline.*` is the capability's own declared config — GSD-native, readable by the gate's `when:` clauses, settable through GSD's tooling — and it WINS over `pipeline.*`, which is shipyard's own namespace (`pipeline` is not a valid GSD config key, so `/gsd-config --set pipeline.x` is rejected). Prefer declaring new knobs in `capability.json` so they become GSD-settable.

  **GSD settings the conveyor obeys** (read, never written): `git.base_branch` outranks the repo default for epic cut/target — a project integrating into `develop` must not get epics off `main`; `git.branching_strategy` must be `none` or GSD creates its own branches while the conveyor owns branching (warned); `workflow.use_worktrees` is READ and no longer warned about at any value — this repo asserted it must be `false` because `/gsd-code-review --fix`, which the conveyor calls from inside a ticket worktree, would fork a nested one. Checked against GSD 1.9.1's source, that is false: `code-review.md` does not mention worktrees at all, and `git worktree add` appears only in `execute-phase`, `new-workspace` and `worktree-safety.cjs` — none of which the conveyor invokes. `true` is also GSD's own default, so the warning fired for most projects and taught the user to ignore warnings. The boundary that DOES hold is the one below (never call `execute-phase`), and it is about wave parallelism, not this flag; `runtime` decides effort clamping AND whether a plugin-namespaced `agent_skills` entry resolves at all — `global:<plugin>:<skill>` works only on `claude` and is silently skipped elsewhere, so Codex needs the bare `global:shipyard-delivery-rules`; `response_language` governs how agents talk to the user, while shipped artifacts stay English.

  **Executor isolation is the conveyor's, not GSD's.** GSD 1.9.1 added `dispatch.isolation` — a HOST descriptor (`harness-worktree` on claude/cursor, `orchestrator-worktree` on codex, `none` elsewhere) that decides how `/gsd:execute-phase` isolates concurrent same-wave executors. The conveyor never calls `execute-phase` or `autonomous`: it fans out its own executors, one per ticket, each in a worktree `ticket-worktree.sh` created and the main loop verifies. So there is nothing for us to declare — `dispatch.isolation` is not a capability field and shipyard does not set it — but the boundary has to hold in one direction: no shipyard path may reach for GSD's wave parallelism, because two orchestrators creating worktrees for the same plans is the collision this boundary exists to prevent. The Codex value being `orchestrator-worktree` is what makes this concrete rather than theoretical: there, GSD itself runs `git worktree`.

  **A cross-repo checkout must live OUTSIDE the project.** Since 1.9.1 (#2843) GSD's `findProjectRoot` refuses to cross a git-repo boundary, so a `pipeline.repos` checkout nested inside the project no longer resolves to this project's `.planning/` — GSD tooling run there silently binds to the nested repo instead. Keep such checkouts outside, or declare the top segment in GSD's `sub_repos`, which is honored before the boundary guard (warned). The conveyor's own config reader is unaffected: it reads `<cwd>/.planning/config.json` exactly and never walks up.
- `validate-graph.cjs` — Gate 2. Collects every error before exiting; ancestor closures are computed over the topological order (a shared-visited recursion once cached truncated closures and rejected valid diamond graphs). It also owns the **repo boundary**: `delivery.repo` (a ticket in a sibling repository) makes identical paths in two repos not an overlap, keeps a cross-repo parent out of the cascade (`pr_base` must never name a branch from another repo), and flags `files_modified` entries that escape the repo root as `unreachable_paths` — a warning plus a flag rather than a gate failure, because one unreachable ticket must not stop delivery for the valid rest.
- `state-sync.cjs` — rebuilds delivery state from live GitHub. Note `gh pr checks` reports CI state through its **exit code** (8 = pending, 1 = failing/no checks) while still printing JSON, so a non-zero exit there is data, not an error. It also computes `reapable` — the reaper force-deletes branches, so that decision must be mechanical, not inferred. Every query is scoped to the ticket's **own repo** (`--repo`, `repos/<owner>/<name>/…`): watching the wrong repository made a ticket whose PR was merged next door read as `pending` forever, which blocked every dependent behind work that was already done. An unreachable foreign repo is a parked ticket, never an aborted sync. **Never add `reviewDecision` back to the bulk `gh pr list` window** — it is the one field that dominates the call (the same 1000 rows cost 41s with it and 7s without on a monorepo) and it is only read for OPEN PRs, so it comes from a separate open-only pass. state-sync runs on every babysit round, so its wall time is the conveyor's tick rate; `SHIPYARD_TIME=1` prints per-`gh`-call timings when it regresses.
- `front.cjs` — the **stop condition as code**. `computeFront(tickets, state, {parked, autoMerge})` sorts everything into actionable (execute/publish/fix/finalize/merge), waiting (ci/merge_human/checkpoint) and parked, and prints `fixpoint: YES|NO`; it also names the OWNER of each bucket (`sentinel.duty` = fix/finalize/merge — the guard's; execute/publish — the main loop's), which is the split that lets the two run at once. `merge` only becomes actionable with `autoMerge` AND a conform gate AND `merge_scope: 'stacked'`; state-sync ends every board with it and writes `.planning/graph/delivery-front.json`. This exists because prose could not hold the rule: runs serialized on `gh pr checks --watch` and read a `human_checkpoint` as "do nothing", then reported a fixpoint with a dozen tickets executable. Waiting on CI is deliberately "not a fixpoint, and not a reason to block". Session-only facts (an `escalate`, attempts > max) are invisible to GitHub, so they come in via `--parked` — without that the babysit loop re-offers an escalated PR forever.
- `sentinel.cjs` — the **PR sentinel's** core: `duty` (one action per open PR, plus the guard's own `clear` verdict), `merge` (the guarded ticket-PR → stack merge), `report`. The guard is what lets delivery cascade onward while open PRs are still being driven to green; before it, the run either serialized on CI or declared a fixpoint over a pile of unmerged green PRs. **`merge` re-verifies everything against LIVE GitHub** (open, undrafted, checks green, unresolved threads 0, a `gate_status: arch-review=conform` trailer in the body, not CHANGES_REQUESTED, not `human_checkpoint`) and refuses outside the stack — the base must be the phase epic or a parent ticket branch in the same repo. **The epic → integration-branch PR is never auto-merged**, whatever the config says: that boundary is what makes the epic a quarantine. Gated by `pipeline.auto_merge` (`epic` default | `off`) and `pipeline.sentinel` (`auto` | `off`), which the config reader keeps consistent with each other.
- **A child never lands into an OPEN `human_checkpoint` parent.** The base can be inside the stack and still be a branch nobody may squash into yet: line 393 of `sentinel.cjs` refuses a checkpoint ticket's OWN merge and said nothing about merging INTO one. Two things break if it happens — the squash rewrites the diff a person is actively reading, and the post-merge retarget sends that child's children to the EPIC, incoherent with content sitting in a checkpoint branch. Field-found: three of five escalations in one proving-ground phase were manual holds on exactly this, each citing the check by line number. `sentinel.cjs` (gate + duty) and `front.cjs` now share the same `checkpointParent` test, because the front must never offer what the guard refuses. The child routes to `waiting.human`, NOT `parked` — nobody owes work, a person holds the key. **`parentIsMoving` is deliberately untouched**: its checkpoint exception is correct for driving a child to GREEN and wrong only for merging it, and removing it would freeze a whole subtree behind a human.
- `graph-dir.cjs` — **"which ticket graph does this invocation belong to", for the gates handed a `--worktree`.** The recurring defect in this repo is a script that resolves `.planning/graph` from `process.cwd()` while its documented caller is an agent standing in a ticket worktree — which has no `.planning/` at all when the project keeps it untracked (the proving ground does). `base-merge.cjs` and `scope-gate.cjs` both had it, and base-merge is the one that mattered: `ci-fix.md`/`review-fix.md` name it as THE remedy for a moved base, and both tell the agent to `cd` into the worktree first. Resolution order is flag/env → cwd → **the worktree's own repository** (`git rev-parse --path-format=absolute --git-common-dir` reports the main repo's `.git` even from a linked worktree), which rescues the agent without changing any prompt contract. `--graph` remains the only thing that works **cross-repo**, where the worktree lives in a sibling repository and the graph does not. When nothing resolves, say so honestly: the old message was `run validate-graph first`, which named neither the cause nor a command that could help. `state-sync.cjs`/`sentinel.cjs` keep the cwd rule (they are the project's, not a worktree's) and fail loudly, so `pr-sentinel.md` states the working directory instead. The same file owns `resolveBaseRef`: both gates measure **`origin/<base>` when it exists** — the PR's base lives on origin, and after the sentinel squash-merges a parent via the API the local epic does not move, so the bare name made base-merge report `already up to date` while origin was ahead (silent false success; the worktree never received the parent's work) and made scope-gate flag the parent's files right after a correct merge (the false positive that gets a gate switched off). base-merge resolves AFTER its fetch; scope-gate resolves without fetching — a blocking pre-publish gate must not grow a network dependency. Both print the ref they measured: a silently substituted base would be a new invisible behaviour. When converting the repro to a test, assert CONTENT, not the message — `merged cleanly` lies against a stale ref exactly as well as `already up to date`.
- `drift-record.cjs` / `escalation-record.cjs` — **the two durable stores, and both are written from cwds that are not the project.** `drift-gate.mjs` dispatches its judges in PARALLEL from ticket worktrees and tells each to record its own verdict, which broke both halves: drift-record had no `--graph` flag while the prompt passed one (verdict written into the worktree where state-sync never reads it, flag text swallowed into the reason, exit 0), and an unlocked `load→save` lost updates — six concurrent marks reliably produced five records. Both now take `--graph <project>/.planning/graph` in ANY position (one spelling, shared with `log-event.cjs`), refuse when the resolved graph dir has no `tickets.json`, and do the whole read-modify-write under `withLock` + `writeAtomic` with the lock **beside the store** (a lock taken at a worktree cwd serializes nothing). The flag fixes the instruction; the refusal fixes the class, because the next prompt that forgets it must fail loudly rather than write into the void. Watch the `-1` case when stripping a flag by index: `i !== flagAt + 1` with no flag present reads as `i !== 0` and eats the subcommand.
- `escalation-record.cjs` — the durable park, and the sole writer of the journal's `escalation` event. An escalation reached the front through ONE channel — a `--parked` flag the caller re-passed on every sync — so it died with the session: the next run re-dispatched review-fix and arch-review at a PR a human had already been asked to resolve, with the reason gone. Not a deadlock (the stop hook lets a second stop through), but paid-for work re-deciding something already decided. **Parking and journalling are ONE act** here, because they were two and only one ever got done: the proving ground held six journalled escalations with no park and a seventh parked with no journal entry. Expiry follows drift-record's rule over a different subject — the verdict is bound to a fingerprint of the delivery-state facts a human would move (status, draft, review_decision, check tallies), so answering the review lifts the park by itself; a ticket with no PR simply stays until `clear`, which is the honest outcome rather than a special case. The fingerprint is built from fields state ALREADY carries — adding one to state-sync's bulk `gh pr list` window is what cost 41s vs 7s. **Whatever the front parks, `sentinel.cjs` must park too**: the guard runs concurrently off the same state, so a narrower parked set there means it keeps dispatching at exactly the PRs the front set aside.
- `stop-gate.cjs` — the front's stop condition **as a hook**. `front.cjs` computes whether stopping is legitimate; nothing consumed that answer at the moment it mattered, because ending a turn is not a step, so no script runs there. deliver.md stated the loop-back as mandatory prose and runs ended early against it anyway — always while composing a summary, which reads like completion. This is the same lesson as the merge rule and the drift verdict: **prose rules get skipped, mechanical gates hold.** It reads only `.planning/graph/delivery-front.json`, so the installer COPIES it to `~/.claude/hooks/` rather than pointing at the plugin's versioned cache path — re-run `make install-shipyard-claude-hook` after an upgrade. It is installed globally, so its five escape hatches are load-bearing: no front, a stale front (`SHIPYARD_STOP_GATE_FRESH_MS`), nothing actionable (waiting on CI is explicitly allowed), all-left-behind, and `stop_hook_active`. A stop gate that traps a session gets uninstalled, after which it enforces nothing — so it always exits 0 and stays silent on anything it cannot read.
- `lock.cjs` — cross-process locking (`withLock`) and atomic replacement (`writeAtomic`). The sentinel runs CONCURRENTLY with the main loop, so `state-sync` writes state/yaml/front in one locked section, and `ticket-worktree.sh`/`epic-branch.sh` serialize anything that writes the shared `.git` (index.lock). A lock directory with no `owner.json`, or one older than the TTL, is taken over — a killed session must not wedge the next run.
- `ticket-worktree.sh` / `epic-branch.sh` — idempotent worktree and epic lifecycle. Both resolve refs that exist only as `origin/<name>`; a bare remote-only branch name does not resolve through `git rev-parse`, which used to break every resumed run.

Anything the skills are told to "decide" that can be computed belongs here instead. When adding to it, add a case to `tests/unit/` or the matching fixture smoke test in the same change.

**The Codex generator rewrites the word "Claude" in prose.** `convertClaudeCommandToCodexSkill` (gsd-core, first-party — not ours) substitutes it, so `…only mean anything on the Claude runtime` shipped to Codex as `…on the the agent runtime`: the sentence that existed to say "not here" now reads as "here". Any claim whose meaning depends on naming Claude as a runtime distinct from the reader's inverts on the far side. Name the MECHANISM instead (`the Agent tool`, `the Workflow tool`) — those survive the pass — and re-read the generated `~/.agents/skills/shipyard-*/SKILL.md` after editing a paragraph that contrasts the two runtimes, because the generator is silent about what it changed.

**The Workflow path bypasses the skills' prose.** `workflows/*.mjs` build agent prompts deterministically, so anything the skill states in Markdown — the anti-injection framing, the artifact language — does NOT reach those agents unless the script says it too. That is the whole point of the path (no context leakage), and also its trap: a rule that lives only in a command doc is not in force there.

**A rule for a dispatched agent belongs in the `references/` file that agent reads, not in `deliver.md`.** The Workflow prompts hand fixers the paths to `ci-fix.md` and `review-fix.md`; that IS the delivery channel, and it is the only one. "A moved base is merged in, never rebased onto" lived in `deliver.md` and `pr-sentinel.md` alone, so every fixer the Workflow path dispatched was free to rebase a pushed branch — one force-push per parent in a cascade, each dismissing an approval and re-anchoring the threads just resolved. One rule, one home: put it where the agent reads, and do not duplicate it into the workflow prompt.

**Runtime config is merged non-destructively by the entrypoint.** `scripts/entrypoint.sh` is the container ENTRYPOINT. On every start it `jq`-merges baked MCP defaults into `~/.claude.json` using `(.existing // default)` semantics — adding `atlassian-rovo` (HTTP) and `context7` (stdio, baked binary) only if absent — pre-seeds bypass-permissions acceptance and per-directory trust for `/workspace` and each project inside it (`shipyard-trust <dir>` covers repos cloned later), copies SSH client files in from the read-only mount, and restores/mirrors the MCP credentials.

**Auth via CLAUDE_CODE_OAUTH_TOKEN.** The `CLAUDE_CODE_OAUTH_TOKEN` environment variable is the Claude Code subscription OAuth token, generated on the host via `claude setup-token` and passed into the container via `.env`. No host `~/.claude` directory is mounted.

**Persistence via a state DIRECTORY, not a file.** `CLAUDE_STATE_DIR` (default `./.claude-state`) is mounted at `/home/dev/.claude-state`; the entrypoint restores `credentials.json` from it into `~/.claude/.credentials.json` at start and mirrors the live file back whenever it changes. It must stay a directory: a bind-mounted *file* cannot be replaced by `rename(2)`, so any writer that saves atomically would fail on it. Everything else under `~/.claude` is baked into the image or generated at startup and is ephemeral.

**Mounts are deliberately narrow.** The repo checkout is **not** mounted (it holds `.env` with the OAuth token, and sessions run with `bypassPermissions`). SSH client files arrive read-only at `/home/dev/.ssh-host` — never over `/home/dev/.ssh`, which must stay writable so `ssh` can record host keys, and whose baked defaults must not be shadowed. The default `.ssh-host` source is the build-staged safe subset, so private keys are not in the container unless `SSH_DIR` opts in.

**Atlassian OAuth is bootstrapped in-container.** Because macOS stores OAuth tokens in the system Keychain (not a portable file), the browser-based Atlassian Rovo login must run inside the container via `make bootstrap-atlassian-oauth`. The host's full `~/.claude` is never mounted; the result is mirrored into `CLAUDE_STATE_DIR`.

**Runtime user is `dev` (uid 1000), home `/home/dev`, workdir `/workspace`.** Git identity and defaults are baked into `/home/dev/.gitconfig` at base-build time via `ARG`s.

## Conventions

- All shell scripts use `set -euo pipefail` and validate inputs/preconditions early with explicit error messages — match this when adding scripts.
- Tool versions are pinned as Dockerfile `ARG`s and surfaced as overridable Makefile variables; never hardcode an unpinned `latest`.
- The plugin (`plugins/delivery-pipeline/.claude-plugin/plugin.json`) and its capability (`capabilities/delivery-pipeline/capability.json`) ship as one product: bump both versions together, or `make test-overlay` fails on the drift check.
- **Cutting a release is five steps, and the last one has no other feedback.** Bump both versions → `make test-fast` (plus `test-codex-shipyard` when the conveyor changed) → merge to `main` → signed annotated tag `vX.Y.Z` → push branch AND tag → **`gh release create`**. Tagging, pushing and installing all announce themselves; a missing release announces itself to nobody, which is how twelve consecutive tags shipped bare while the repo had kept notes since v0.4.0. `make test-releases` is the check that now says so. Assemble the notes from `git log --no-merges --reverse --format='## %s%n%n%b%n' <prev-tag>..<tag>` — a release spanning several commits is otherwise described by whichever one happened to land last.
- In a `cmd | grep -q` assertion, remember `set -o pipefail` reports `cmd`'s exit status — capture the output first when the command is expected to fail.
