# Shipyard 1.0.0-rc.5.18

Patch prerelease based on `v1.0.0-rc.5.17`.

## Fixed

- **A Codex review fix no longer blocks the next fix after its own push moved a review thread.** Before a new review-fix launch, the Codex delivery host re-checks every thread an earlier fix resolved. It compares the thread as it was recorded when the resolution was confirmed with the original thread plus `resolved: true`.
  - The recorded thread already carried the line number GitHub reported after the earlier fix's own signed push. The comparison treated that mutable line number as part of the thread's identity.
  - In a native Codex delivery, a review thread was anchored to line 944. The first fix added code above it, and GitHub moved the same thread to line 952. Shipyard resolved the thread and recorded the confirmation.
  - The next review-fix was then refused with `REPAIR_PREDECESSOR_INVALID: host resolution changed its original external thread`, although the thread ID, file and original anchor were unchanged.
- **The confirmed push may move only the line.** A different line number is now accepted only when all of these hold:
  - the earlier fix's signed publication is authenticated as confirmed;
  - its changed files include the thread's file;
  - the new line is null or a positive integer.
  - Thread ID, file, original line, author, comment text and the reply checks are compared exactly as before.
  - A move in a file the push did not change, or any change to the original line, is still refused. That refusal comes when the earlier fix rechecks its own publication, before any reply or resolution.

## Validation

A Codex review-fix case runs the full cycle from the report: fix → signed push (GitHub moves the thread from line 944 to 952) → reply and resolve → the next fix. The next fix now launches as the repeat rung. On the rc.5.17 host the same case fails with `REPAIR_PREDECESSOR_INVALID`.

Two further cases move the line during the first fix's push in a way the push does not explain: in a file the push did not change, and together with the original line. Each is refused with `REPAIR_SUBJECT_CHANGED` and names the changed fields. The first fix pushes once and posts no reply, and no thread is resolved.

Release verification results are recorded in the published prerelease.
