# Shipyard 1.0.0-rc.5.15

Patch prerelease based on `v1.0.0-rc.5.14`.

## Fixed

- **Review parts and the final agree on what `complete` means.** The host counts a review part as reviewed only when its `review_completeness` is `complete` and both `limitations` and `unresolved_sources` are empty. The prompts never said what `limitations` is for.
  - In a native Codex integrator run, every part reported its static review as `complete`. Each also wrote in `limitations` that it reviewed statically, that tests were not run, that native/Redis/PDF acceptance was separate, and that other parts held other paths.
  - The host marked all three parts as not reviewed, and refused the final `passed` with `complete code review has unreviewed parts`.
- **One shared definition of `limitations`.**
  - `limitations` lists only obstacles that kept the reviewer from verifying its assigned scope, such as an unread path, diff slice or source.
  - Boundaries of the read-only role are not limitations and belong in `summary`: a static review, tests or CI not run, runtime, deployed or separate acceptance not checked, and paths outside the assigned scope.
  - `complete` requires both lists empty; otherwise the reviewer returns `incomplete`.
  - The definition is one constant. These prompts carry it: the part prompt, the code-review final prompt, the single-session code-review prompt and the arch-review prompt, on both runtimes. The integrator final prompt says a part counts as reviewed only when it is complete with both lists empty.
  - The integrator, code-review and arch-review references document it.
- **A contradictory part answer is refused at the part, with one relaunch.** A part answer that says `complete` but has a non-empty `limitations` or `unresolved_sources` is now a part-format refusal. Before, the part was accepted and only the final failed. The refusal reads `part review_completeness is complete but limitations has 1 entries and unresolved_sources has 0; complete requires both lists empty`.
  - It uses the rc.5.14 retry: the part is relaunched once, with the same authenticated packet and the refusal stated.
  - The refusal carries only counts, never the model's own text. Nothing is removed from an answer.
  - A part that still contradicts itself after the retry ends the run before the final.
- **The refusal names each part that is not reviewed.** A complete verdict or a `passed` integration over unreviewed parts is still refused. The refusal now names each such part and why, for example `complete review has unreviewed parts: part-2 (incomplete, limitations 1); part-3 (incomplete, unresolved_sources 1)`.
- **Arch-review states the size of the contradiction.** A `complete` arch-review with limitations is refused as before. The refusal now reports how many `limitations` and `unresolved_sources` entries it has.
- **What is unchanged.** A real gap — an unread path, an unresolved source or an incomplete part — still blocks a complete verdict and a `passed` integration. The host still derives coverage from the parts, and does not strip or reinterpret any limitation.

## Validation

Core cases cover the definition:
- a complete part that states its role boundaries in `summary` is accepted;
- a complete part with any `limitations` or `unresolved_sources` entry is a counted part-format refusal that does not echo the model text;
- an incomplete part with a real gap is accepted as incomplete;
- the per-part refusal of a complete verdict lists each part and its reasons;
- the shared rule appears in the part, final and retry prompts and equals the arch-review copy.

Native Codex integrator cases with several parts reproduce the reported run. Every part first files a role boundary as a limitation, is relaunched once with the counted refusal, and moves the note to `summary`. The final then seals `passed` with a synopsis that keeps runtime acceptance unverified. Further Codex cases cover:
- a part that keeps the limitation after its retry is refused before the final;
- an incomplete part with a limitation, or with an unresolved source, still blocks `passed`, and is named by part.

A Claude integrator case covers the same relaunch and sealed final. Codex code-review cases check the rule in the part and final prompts and the counted part refusal. Arch-review prompt cases on both runtimes check the rule.

On the rc.5.14 sources the reported scenario fails with `complete code review has unreviewed parts`. Release verification results are recorded in the published prerelease.
