## Goal

Three places describe the fields of each finding in a role judgment result:

- the integrator reference (`integrator.md`);
- the launched output schema (`claude-role-host.cjs roleOutputSchema`);
- the one findings validator (`role-artifact.cjs completeFinding`, shared by the integrator and arch-review seal paths).

After this plan, all three agree on the type of every field:

- `finding.ticket` is either a compact ticket id string (the ticket the finding is about) or `null` for a phase-level finding;
- a proposed fix ticket goes in its own `finding.fix_ticket` object `{title, scope, files, depends_on}`.

A well-formed result is sealed on the first try. A malformed result is refused with `INVALID_RESULT` or `INCOMPLETE_FINDING`, and a remedy that names the field. The generic `must be a non-empty text value` message is no longer used for this case.

This extends REQ-135 / T-39-14 (a role worker receives its bound at launch and is refused deterministically, with a named remedy) from the result identity to the findings. It closes the refusal of the second phase-39 integrator dispatch. That result was refused before it could be sealed. `INTEGRATION.md` F1 was delivered by hand-copy.

## Defect (verified before planning)

  - the fix finding (F1) carried `"ticket": {"title": …, "files": […], "scope": …, "depends_on": []}`, which is the proposed ticket as an object;
  - the informational findings (F2 through F6) carried `"ticket": null`.
- `role-artifact.cjs:1256-1266`: for an integrator `fix-ticket` / `fix` finding, `completeFinding` calls `findingText(finding, ['ticket'], …)`. That goes through `roleText` (`:848-853`), which fails with `INVALID_RESULT` and `integrator finding 0.ticket (ticket) must be a non-empty text value`. The message has no remedy and gives no hint that the proposed ticket belongs anywhere else. The same branch requires `scope` and a non-empty `files` at the top level of the finding.
- For the informational findings, `ticket: null` is never read (`:1270-1273`), so their contract is undefined rather than stated.
- `integrator.md:89-94` says "A `fix-ticket` also carries its ticket, scope, and non-empty file list", and `:42-44` says "attach a concrete fix-ticket list (title, scope, files, depends_on)". Both readings fit that text: `ticket` as an id, or `ticket` as the proposed ticket object. The worker chose the object.
- `claude-role-host.cjs:685-713` `roleOutputSchema` declares `findings: { type: 'array' }` with no `items` for both integrator and arch-review. The CLI therefore cannot bound the finding fields at launch.
- Arch-review shares `completeFinding` (`role-artifact.cjs:1235-1255`, reached through `completeFindingIndex` at `:1557`). Its reference example (`arch-review.md:88-101`) has no `ticket` field.
- The sentinel has no findings array. Its `performed` / `refused` entries already carry `ticket` as an id string (`claude-role-host.cjs:170-171`, `pr-sentinel.md:318-319`). So the shared rule covers integrator and arch-review findings, and the sentinel needs no change.

## Scope

- **Contract (one statement, used verbatim in the reference).** Every finding may carry `ticket`. When it is present, it is a compact ticket id string (for example `"T-39-09"`) or `null` for a phase-level finding. A `fix-ticket` finding carries the proposed ticket in `fix_ticket`: `{ "title": text, "scope": text, "files": [non-empty text, …] (at least one), "depends_on": [ticket id, …] }`. `depends_on` is optional and defaults to absent.
- **Validator (`role-artifact.cjs`).** In `completeFinding`, for every role that reaches it (integrator and arch-review), before the per-type branches:
  - **The `ticket` field.** When `finding.ticket` is not `undefined` and not `null`, it must pass `compactIdentity`. Otherwise call `fail('INVALID_RESULT', …)` with the message `<role> finding <index>.ticket is <an object|an array|a number|a boolean|an empty or multi-word string>; remedy: set ticket to the affected ticket id string, or null for a phase-level finding, and put a proposed fix ticket in fix_ticket {title, scope, files, depends_on}`.
  - **`fix_ticket` on the wrong type.** When `finding.fix_ticket` is present on a type other than `fix-ticket` / `fix`, call `fail('INVALID_RESULT', '<role> finding <index>.fix_ticket is only valid on a fix-ticket finding; remedy: set type to fix-ticket or drop fix_ticket')`.
  - **The integrator `fix-ticket` / `fix` branch.** Replace the current top-level `ticket` / `scope` / `files` requirements:
    - `finding.fix_ticket` must be a plain object. Otherwise use `INCOMPLETE_FINDING` with `integrator finding <index>.fix_ticket is required; remedy: put the proposed ticket {title, scope, files, depends_on} in fix_ticket`.
    - `fix_ticket.title` and `fix_ticket.scope` go through `roleText`, labelled `integrator finding <index>.fix_ticket.title` / `.scope`.
    - `fix_ticket.files` is a non-empty array of `roleText` values. Otherwise use `INCOMPLETE_FINDING` with `integrator finding <index>.fix_ticket.files must be a non-empty array`.
    - `fix_ticket.depends_on`, when present, is an array of `compactIdentity` values.
    - `summary` / `reason` stays required.
  - A top-level `scope` or `files` on a finding is no longer read.
  - The other type branches and the returned `{ ...finding, id, type, blocking }` are unchanged.
- **Schema (`claude-role-host.cjs`).** Add:
  - frozen `FINDING_TICKET_SCHEMA = { type: ['string', 'null'] }`;
  - frozen `FIX_TICKET_SCHEMA`: `{ type: 'object', additionalProperties: false, required: ['title','scope','files'], properties: { title: string, scope: string, files: { type: 'array', minItems: 1, items: string }, depends_on: { type: 'array', items: string } } }`.
  - **integrator** `findings`: `{ type: 'array', items: { type: 'object', required: ['id','type','blocking','summary'], properties: { id: string, type: { enum: ['fix-ticket','human-question','violation','adr-outdated','note','informational'] }, blocking: boolean, summary: string, ticket: FINDING_TICKET_SCHEMA, fix_ticket: FIX_TICKET_SCHEMA, question: string, evidence: string } } }`. Finding items get no `additionalProperties: false`, because the validator accepts documented aliases such as `reason`.
  - **arch-review** `findings`: `{ type: 'array', items: { type: 'object', properties: { ticket: FINDING_TICKET_SCHEMA } } }`. Its other properties stay unchanged.
  - The pr-sentinel schema is unchanged.
  - The role host adds no findings check of its own. The `role-artifact.cjs` refusal reaches the `run()` caller with its code and message unchanged. Assert this; do not assume it.
- **Reference (`integrator.md`).**
  - In `## Verdict`, change the `needs-fix` bullet to: attach each fix ticket as a `fix-ticket` finding whose `fix_ticket` carries `title`, `scope`, `files`, `depends_on`, ready for validate-graph.
  - Replace the finding paragraph's sentence "A `fix-ticket` also carries its ticket, scope, and non-empty file list." with the Contract statement above.
  - After the result example, add a second fenced JSON example of a `needs-fix` `findings` array. It has one `fix-ticket` finding with `"ticket": null` and a `fix_ticket` object, and one `informational` finding with `"ticket": "T-33-02"` and `evidence`.
  - Keep the `ticket_set` sentence, the digest sentence and the `## Verification contract` section.
- **Comment policy:** add no explanatory, historical or ticket comments on added code lines. At most one single-line `@contract:` marker of 120 characters or less is allowed.

## Acceptance criteria

1. **Captured shape, refused.** The claude-role-host integrator fake gets a result mutated to `outcome: 'needs-fix'` and `blocking_count: 1`, with these findings:
   - `{id:'F1', type:'fix-ticket', blocking:true, summary, ticket:{title, files:[…], scope, depends_on:[]}}`;
   - `{id:'F2', type:'informational', blocking:false, summary, evidence, ticket:null}`.

   It is refused, and:
   - `error.code === 'INVALID_RESULT'`;
   - the message contains `finding 0.ticket is an object` and `remedy:` and `fix_ticket`;
   - the message does not contain `non-empty text value`;
   - no artifact is returned.
2. **Well-formed shape, sealed.** The same result, with F1 as `ticket: null` and `fix_ticket: {title, scope, files:['a.cjs'], depends_on:[]}`, is sealed and returns an artifact. F2 with `ticket: null` is accepted. An informational finding with `ticket: 'T-01-01'` is accepted.
3. **Validator unit (`judgment-artifacts.test.cjs`).** A `roleArtifact.seal` integrator input is refused with a message naming the field:
   - with `fix_ticket` missing: `INCOMPLETE_FINDING`, `fix_ticket is required`;
   - with `fix_ticket.files: []`: `INCOMPLETE_FINDING`, `fix_ticket.files`;
   - with `ticket: 42` on an informational finding: `INVALID_RESULT`, `.ticket is a number` and `remedy:`;
   - with `fix_ticket` on an informational finding: `INVALID_RESULT`, `only valid on a fix-ticket finding`.

   The well-formed `needs-fix` input seals. The existing human-question test passes unchanged.
4. **Launch schemas.**
   - The integrator launch `selection.schema.properties.findings.items` has `properties.ticket.type` deep-equal to `['string','null']`, `properties.fix_ticket.required` deep-equal to `['title','scope','files']` and `properties.fix_ticket.properties.files.minItems === 1`.
   - The arch-review launch schema's `findings.items.properties.ticket.type` deep-equals `['string','null']`.
   - The pr-sentinel schema deep-equals the value it had before this change.
5. **Reference.** `integrator.md` contains `"fix_ticket": {` and `or null for a phase-level finding`, and no longer contains `also carries its ticket, scope`. `node tests/unit/source-contract.test.cjs` passes.
6. **Existing tests.** The existing `claude-role-host`, `judgment-artifacts` and `role-artifact` tests pass unchanged.
