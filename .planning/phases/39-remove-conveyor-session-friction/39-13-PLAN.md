## Goal

The deterministic Jira export plan once again implements ADR-004 D8 (integrator
finding F1): "the old label is searched as a fallback and migrated with a note",
and an issue that belongs to another repository is never updated. Each epic and
issue step carries an ordered lookup. A legacy match is claimed only when its
`Source of truth` line names this repository or has no repository prefix. On a
claimed match the step migrates the issue: it adds the namespaced label, rewrites
the pointer line and comments `label migrated`. A hit whose pointer names another
repository is refused, and the lookup falls through to create. `decompose.md`
Step 5 documents the plan fields that the agent executes. The script keeps
REQ-130's properties: byte-deterministic output, no network code, no credential.

  (uppercase `T`, `ADR-004-positive-evidence-before-a-mutation.md:99-101`) is not
  a lookup candidate at all.
- `jira-export.cjs:155-163` epic steps: the description has no `Source of truth`
  line, so a legacy epic cannot be checked or migrated.
- `plugins/delivery-pipeline/commands/decompose.md:580-601` (Step 5 procedure)
  says only "Execute each step of that plan verbatim". The pre-phase lookup
  order and the "never update an issue whose source-of-truth line names another
  repository" rule were removed by T-39-10 (INTEGRATION.md F1).

## Scope (per REQ-130 and ADR-004 D8)

- **Ordered lookup.** In `jira-export.cjs`, replace `lookupOf` with a builder that returns an array `lookup` on every step. Entries appear in this fixed order, and each entry has `order`, `kind`, `label`, `jql` (`project = KEY AND labels = "<label>"`) and `on_match`.
  - Issue steps:
    1. `kind: "primary"`, the lowercase namespaced label, `on_match: { action: "update" }`.
    2. `kind: "adr-004"`, `shipyard-<owner>-<repo>-<ticketId>` with the ticket id as written (uppercase `T`).
    3. `kind: "legacy"`, `shipyard-<ticketId>`.
  - Epic steps:
    1. `kind: "primary"`, `shipyard-epic-<owner>-<repo>-<phase>`, `on_match: { action: "update" }`.
    2. `kind: "legacy"`, `shipyard-epic-<phase>`.
  - The epic ADR-004 spelling equals the primary label, so epics get no separate `adr-004` entry.
  - Every non-primary entry carries:
    - `requires_source_of_truth: "<owner>/<repo>:<path>"`;
    - `accepts_unprefixed: "<path>"`;
    - `on_match: { action: "migrate", add_label: <primary label>, pointer: <step pointer line>, comment: "label migrated" }`;
    - `on_foreign: "skip"`.
  - Each step also carries `on_no_match: "create"`.
- **Epic pointer.** Epic descriptions gain a final single line `Source of truth: <owner>/<repo>:.planning/phases/<phaseDir> (this issue is a generated projection)`. `<path>` for epics is `.planning/phases/<phaseDir>`, and for issues it is `t.plan`.
- **Pure decision helper (exported).**
  - `classifySourceOfTruth(description, repo, planPath)` finds the first line that starts with `Source of truth:` and returns one of:
    - `"this-repo"`: the value starts with `<repo>:`;
    - `"unprefixed"`: the value starts with `planPath`, with no `<x>/<y>:` prefix;
    - `"foreign"`: any other `<x>/<y>:` prefix, or another path;
    - `"absent"`: no such line.
  - `resolveLookup(step, hits)` takes `hits`, keyed by entry `order` to an array of `{ key, description }`. It walks `step.lookup` in order and returns the first decision:
    - More than one hit on one entry → `{ action: "ambiguous", order, keys }` (fail closed; the agent reports it and does not write).
    - A primary hit → `{ action: "update", key }`.
    - A non-primary hit classified `this-repo` or `unprefixed` → `{ action: "migrate", key, add_label, pointer, comment: "label migrated" }`.
    - A hit classified `foreign` or `absent` → never claimed; the walk continues.
    - Nothing claimed → `{ action: "create" }`.
  - Neither function does I/O.
- **Determinism.** Entries are emitted in literal order with fixed key order, so `plan --json` stays byte-identical across runs. The CLI's text summary line is unchanged.
- **decompose.md Step 5.** Under procedure item 2, add prose stating that for each epic or issue step the agent:
  - runs each `lookup` entry's `jql` in `order`;
  - applies the entry's `on_match` only when the hit's `Source of truth` line names this repository (`requires_source_of_truth`) or carries no prefix (`accepts_unprefixed`);
  - on `migrate`, adds `add_label`, replaces the pointer line with `pointer`, and posts the comment `label migrated`;
  - never updates an issue whose source-of-truth line names another repository, or has none, and moves to the next entry;
  - creates the issue when no entry claims a hit;
  - stops and reports when one entry returns more than one issue.
  The existing "verbatim / do not reinterpret" sentence stays.
- Comment policy: add no explanatory, historical or ticket comments on added code lines. At most one single-line `@contract:` marker of 120 characters or less is allowed.

- For repo `acme/demo`, project `MYD` and ticket `T-01-01`, the issue step's `lookup` is exactly three entries with labels `shipyard-acme-demo-t-01-01`, `shipyard-acme-demo-T-01-01` and `shipyard-T-01-01`, in that order. Entries 2 and 3 carry `requires_source_of_truth: "acme/demo:<plan>"`, `accepts_unprefixed: "<plan>"`, `on_foreign: "skip"` and `on_match.action === "migrate"` with `comment === "label migrated"` and `add_label === "shipyard-acme-demo-t-01-01"`. The step has `on_no_match === "create"`.
- The epic step's `lookup` has exactly two entries: primary and `shipyard-epic-01`. Its description ends with one `Source of truth: acme/demo:.planning/phases/<dir> (this issue is a generated projection)` line.
- `resolveLookup` behaves as follows:
  - Foreign-repo legacy: only a legacy hit whose pointer reads `Source of truth: other/repo:<plan> …` returns `{ action: "create" }`. The foreign key does not appear in the decision.
  - Unprefixed legacy: a legacy hit whose pointer reads `Source of truth: <plan> …` returns `migrate` with that key, the primary `add_label`, the step's pointer and `label migrated`.
  - Namespaced hit: a primary hit returns `{ action: "update", key }`, even when a legacy hit also exists.
  - An `adr-004` hit naming `acme/demo` returns `migrate`.
  - Two hits on one entry return `ambiguous`.
  - A legacy hit with no pointer line is not claimed.
- `plan --json` stays byte-identical across two runs, and the network-token sweep test passes unchanged.
- `decompose.md` Step 5 contains `lookup`, `in order`, `requires_source_of_truth`, `label migrated`, `names another repository` and `never update`.
