## Goal

Every `dispatch` event in the journal names what the resolver DECIDED, what the
spawn could actually APPLY, and why — with anything unapplied recorded as
unknown rather than as fact. A later question about the ladder is then answered
by reading the journal instead of by argument, and the reading is not itself a
guess.

## Context (Reads)

- **The measurement that makes this ticket exist.** On 2026-09-08 the operator
  asked whether `xhigh` is too much effort for the executor. The answer had to
  be given from judgement about the ROLE, because the conveyor cannot answer it
  from its own records: `dispatch` events carry `ts, event, ticket, role, pr,
  by` and record neither the model nor the effort — **196 events, none of
  them.** Every ladder row in T-25-04 is therefore adopted on reasoning, and no
  revision of it can be better until this lands. That is the whole value here;
  it changes no behaviour.
- `dispatch-record.cjs` is the sole writer of the `dispatch` event. It already
  validates the role against `ROLES` and refuses an unknown one by name — the
  same shape of validation this ticket needs for the two new fields.
- `pipeline-config.cjs model <role> --json` already emits exactly
  `{model, effort}` (plus `strategy` when a signature state was passed), so the
  caller HAS both values in hand at the moment it marks the dispatch. Nothing
  needs to be re-derived, and nothing may be: a value the recorder computes for
  itself would record the ladder's opinion rather than what was dispatched.
- **A resolved effort is not an applied effort, and recording it as one would
  poison the very evidence this ticket exists to collect.** External audit,
  2026-09-08, and it is right: **the Agent tool has no `effort` parameter** —
  only Workflow's `agent()` carries it. So a `dispatch` event that records
  `effort: xhigh` for `arch-review`, `pr-sentinel`, `research` or the
  integrator would be recording an intention that the spawn silently dropped;
  those roles run at the SESSION's own effort. Measured this session: the Agent
  path is **46.9%** of subagent tokens. A ladder review reading such a journal
  would compare rows that were never in force against rows that were, and
  conclude something false about both.
  This is ADR-004's own principle turned on the record: **positive evidence
  before a mutation, and the mutation here is writing a fact.** The same
  discipline the conveyor applies to `landed`, to `checks` and to `unresolved`
  applies to its own audit trail.
- **On Codex the analogue is which FILE was invoked.** An agent there is a
  static `.toml`, so the dispatch's real decision is the model baked into it
  and whether the ordinary or the `-deep` variant was chosen (T-25-02's
  `DEEP_SUFFIX`, written only when it would differ from its twin). Recording the
  role alone loses exactly the distinction the palette exists to express.
- **`log-event.cjs` must not grow this.** It is a dumb append-only writer that
  several roles call from ticket worktrees, and `dispatch` is not in its
  vocabulary by design (it refuses the events other scripts own). The recorder
  owns the event; the recorder records the fields.
- The dispatch overlay is the other half of `dispatch-record.cjs`: `mark`/`clear`
  call `refreshFront`, which rewrites `delivery-front.json` from a FIXED key
  list. Two consequences to respect: a new field must not be smuggled into the
  overlay expecting it to survive (T-26-05 hit exactly this and used a sidecar),
  and nothing about the front's shape may change — the stop gate reads it.
- `.planning/backlog/a-missing-signal-resolves-to-the-dearer-tier.md` records
  the class this ticket makes visible: a signal the dispatch never passes.
  Recording the resolved pair is what turns that from an audit finding into a
  query.

## Scope

- **`dispatch-record.cjs mark <ticket> <role>`** gains, all optional:

  | flag | meaning | when it is written |
  |---|---|---|
  | `--model <alias>` | the tier the spawn was given | both paths — `Agent` and `agent()` both take `model` |
  | `--effort <level>` | what the RESOLVER decided | whenever the caller resolved one |
  | `--effort-applied <level>` | what the SPAWN could carry | **Workflow path only** |
  | `--reason <text>` | which branch of the ladder fired | whenever the caller has it |
  | `--agent-file <name>` | the Codex `.toml` actually invoked, ordinary or `-deep` | Codex runtime only |

  Validation mirrors the role check that already exists: a value outside `TIERS`
  / `EFFORTS` is refused by name with the accepted set printed, because a
  mis-spelled alias recorded silently is worse than no field — it would be
  counted later as fact.

- **`--effort` and `--effort-applied` are two different claims and must never
  be collapsed.** The first says what the policy chose; the second says what
  reached the model. On the Workflow path they are equal and both are written.
  On the Agent path `--effort-applied` is **omitted**, and its absence means
  *unknown*, not *the same*, not *the session's value* — the recorder must not
  helpfully fill in `effortLevel` from settings, because a session setting is
  not a per-dispatch observation. A reader that wants to know what the Agent
  path ran at must go and look; the journal's job is to say honestly that it
  does not know.
- **`--reason` is the field that makes a later review cheap** rather than
  another archaeology exercise: the branch that fired (`risk: high`,
  `signature repeat`, `R1 window 312k > 250k`, `role baseline`). One short
  string, written by the caller that already knows it; the recorder never
  invents it.
- **Absent stays absent.** No default, no inference, no "probably opus": a
  dispatch marked without a flag records no such key at all — assert ABSENCE,
  not `null`, because a null reads as a measured unknown and this is an
  unmeasured one. Same rule T-25-04 states for the resolver, applied to the
  recorder.
- **`deliver.md`** passes both on every `mark` it documents — the executor, the
  drift judges, the fix rounds, the guard, arch-review, the integrator — taking
  them from the `pipeline-config.cjs model … --json` call the step already
  makes. The line that describes `mark` gains one sentence saying why: so the
  ladder can be revised on evidence.
- **`references/pr-sentinel.md`** does the same for the guard's own `mark`,
  since that dispatch is made from inside the guard and not by the main loop.
- Out of the box this must be queryable in one line, so state the query in
  `deliver.md` beside the new flags — the tokens are not in this journal, but
  the pairing is, and joined against the role counts it is what a ladder review
  needs:

      node -e 'const fs=require("fs");
        const d=fs.readFileSync(".planning/graph/delivery-log.jsonl","utf8")
          .trim().split("\n").map(JSON.parse).filter(e=>e.event==="dispatch");
        const k={}; for (const e of d) {
          const applied = "effort_applied" in e ? e.effort_applied : "UNCONFIRMED";
          const s=`${e.role} ${e.model||"?"} resolved:${e.effort||"?"} applied:${applied}`;
          k[s]=(k[s]||0)+1; } console.log(k);'

  The `UNCONFIRMED` bucket is not a defect in the data — it is the Agent path
  telling the truth about itself, and its SIZE is the number that says how much
  of the ladder is currently unverifiable. If it ever reads zero for
  `arch-review` or `pr-sentinel`, somebody has started filling the field in.

## Out of scope

`log-event.cjs` (see Context). The front's shape and `refreshFront`'s key list.
Any change to what the ladder RESOLVES — that is T-25-04, this ticket's parent.
Joining the journal against token spend: the per-agent token counts live in the
harness's task notifications, not in this journal, and inventing a field for
them here would record a number nobody measured.

## Acceptance criteria

- `dispatch-record.cjs mark T-01-01 executor --model opus --effort high
  --effort-applied high --reason "role baseline"` writes a `dispatch` event
  carrying all four, and the dispatch record carries them too.
- **The Agent-path case, which is the point of the ticket:**
  `mark T-01-01 arch-review --model opus --effort xhigh` (no
  `--effort-applied`) writes `effort: "xhigh"` and **no `effort_applied` key at
  all** — assert its ABSENCE. A test that accepts `null` here would let a later
  convenience default through, which is the whole failure mode.
- The same call with `--model gpt-5.6-sol` (not a tier alias) and with
  `--effort ultra` (not in `EFFORTS`) each exit non-zero naming the rejected
  value and printing the accepted set — mirroring the existing unknown-role
  refusal, whose message this must not diverge from in shape. `--effort-applied`
  is validated identically.
- `mark T-01-01 executor` with no flags at all succeeds and writes none of the
  five keys (assert absence, not `null`).
- `--agent-file shipyard-arch-review-deep` is recorded verbatim, and a
  `--agent-file` naming a file the generator does not produce is refused — the
  point is to record which file RAN, so an unverifiable name is worse than none.
- `clear` is unchanged, and the front written by a following `refreshFront` is
  byte-identical to the front written before this change for the same input —
  the overlay must not gain a field.
- `grep -c -- "--model" plugins/delivery-pipeline/commands/deliver.md` matches
  every `dispatch-record.cjs mark` line in the file, and the same for
  `references/pr-sentinel.md`. Assert the COUNT against the number of `mark`
  lines so a later added dispatch cannot forget it.
- The query in Scope, run against a journal with two dispatches at different
  pairs, prints both keys with count 1.

## Test strategy

TDD, in `tests/unit/dispatch-record.test.cjs`, which already holds the
concurrency and refusal cases — extend it rather than adding a file. The
absence assertion is the one worth writing first: it is the case a later
convenience default would break, and the test is what stops that. Then the two
refusals, then the round trip. No new fixture project is needed; the existing
harness writes a graph dir and reads the journal back.
