## Goal

A ticket handed to an agent stops being offered as work. The front reports it as
waiting, the stop gate therefore stops blocking on it, and the record expires by
itself so a killed run cannot hide work from the next one.

## Context (Reads)

- `.planning/backlog/front-has-no-in-flight-state.md` — the whole case, written
  from five occurrences in one session. Read it; it already contains the shape
  of the fix and, more importantly, the trap: **a dispatch record that never
  expires trades a spurious block for a silent stall, which is the worse of the
  two.**
- Measured, not suspected. The stop gate fired on fully dispatched fronts five
  times — on 3, 5, 6, 4 and 5 items — across BOTH owners. Every one was verified
  in flight before being reported.
- **It is wrong by construction, not by accident.** `deliver.md` tells the
  operator to post the guard and NOT wait for it, so `fix`/`finalize`/`merge`
  are dispatched by design. The front therefore mis-reports the guard's bucket
  on every healthy run that follows the documented protocol.
- `front.cjs` already names the OWNER of each bucket (`sentinel.duty` = fix /
  finalize / merge; execute / publish = the main loop). That split is the
  natural key for whose dispatch a record belongs to.
- `escalation-record.cjs` and `drift-record.cjs` are the two existing durable
  stores and the pattern to follow: `withLock` + `writeAtomic` from `lock.cjs`,
  the lock **beside the store**, a `--graph <dir>` flag accepted in any position,
  and a refusal when the resolved graph dir has no `tickets.json`. Follow their
  parsing exactly — three scripts gained a `--graph` flag-as-value guard
  independently because the same bug was found in each.
- **The stop gate needs no change.** It reads only `delivery-front.json` and
  already allows "nothing actionable". Once the front reports a dispatched
  ticket as waiting, the gate's existing hatch covers it. Do not touch
  `stop-gate.cjs`; verifying that it now stays silent is part of the acceptance.

## Scope

- `dispatch-record.cjs` — `mark <ticket> <role> [--graph <dir>]`, `clear <ticket>`,
  `list [--json]`, and an `activeDispatches(cwd, state)` reader for `front.cjs`.
- **Expiry is the load-bearing property**, and it has two independent triggers,
  because either alone leaves a hole:
  - the ticket's delivery state MOVED since the dispatch (a branch appeared, a
    PR opened, checks changed) — the dispatch did its job;
  - a TTL, so a killed session cannot park a ticket forever. Pick it from the
    observed shape of real work rather than a round number, and say why in a
    comment.
- `front.cjs` reports a live dispatch as `waiting.dispatched`, never as
  `parked` — nobody has given up, an agent is working — and never as actionable.
- `deliver.md` and `pr-sentinel.md` record the dispatch at the moment they hand
  work over, and clear it when the work returns.
- Both manifests bump together.

## Out of scope

`stop-gate.cjs`, `sentinel.cjs` (it reads the front, it does not compute it),
and the two other structural backlog items — the diamond base and the phase
ordering are separate defects with separate fixes.

## Acceptance criteria

- A ticket with a live dispatch appears under `waiting`, and `fixpoint` is
  computed without it in the actionable set.
- The same ticket, once its delivery state has moved, is actionable again with
  no `clear` call — proven by changing the state, not by calling `clear`.
- A dispatch older than the TTL is ignored, and the ticket is offered again.
- `clear` removes it immediately.
- A dispatch for a ticket that is already `merged` never suppresses anything.
- **The stop gate stays silent on a fully dispatched front** — drive
  `stop-gate.cjs` with the front this change produces and assert exit 0 with no
  block message. That is the whole point of the ticket and it must be measured
  end to end, not inferred from the bucket name.

## Test strategy

The expiry tests are the ones that matter: assert that a moved state lifts the
record WITHOUT a clear call, and that a TTL-expired record does not hide work.
A test that only proves suppression would pass on an implementation that hides
tickets forever — the exact failure the backlog note warns is worse than the bug.
