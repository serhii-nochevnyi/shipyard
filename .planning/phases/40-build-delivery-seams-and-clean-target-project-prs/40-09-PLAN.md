## Goal

REQ-148 part C5 (D-13). A Codex parent can no longer relay a shortened or rewritten task to its child without the host noticing:

- The host writes the full task to a host-owned file outside the model-writable tree.
- The parent receives only the path and the sha256.
- After the run, the host verifies from the child's native session evidence that the child read exactly that path and saw that digest, and that the file is unchanged.
- Unverifiable evidence is a refusal (RISKS R12).

The Codex boundary fixtures are re-captured from the real CLI with the new launch shape (D-02), and every Codex consumer test replays them, so the three Codex host consumer tests leave the registry's `migrating` list from T-40-07 (REQ-137). `migrating` keeps only the two usage tests described below.

## Scope

- `codex-runtime-host.cjs`:
  - Before launch, write the full task to `<run store>/tasks/<dispatch or run id>.md` with mode 0600 under the existing host state root (never inside the worktree), and compute sha256 with `node:crypto`. Refuse `INVALID_STATE_DIR` if the path resolves inside the worktree.
  - The parent prompt names only `TASK_FILE=<abs path>` and `TASK_SHA256=<hex>`, plus the existing spawn instructions: the child must read that file and follow it exactly.
  - After the run, verify the relay from the child's native session evidence and refuse `TASK_RELAY_UNVERIFIED`, naming every missing item, unless all of the following hold:
    - (a) the child session's `session_meta` names the parent session as its parent;
    - (b) before the child's first tool call there is an `agent_message` authored by `/root` to `/root/<task_name>`, where `task_name` is the name from the spawn evidence;
    - (c) the child's first command-execution tool call reads the exact `TASK_FILE` path, and its recorded output contains the exact `TASK_SHA256` value;
    - (d) the file's sha256 is still unchanged after the run.
  - A plaintext first user/developer message carrying both `TASK_FILE=` and `TASK_SHA256=` values (older CLIs) satisfies (b) and (c) as well.
  - Remove the file after verification.
  - Keep the existing spawn-evidence checks.
  - The decompose and delivery hosts keep passing with the task-file launch; if one of them needs a host change, stop and report it as a new ticket with the failing replay as evidence.
