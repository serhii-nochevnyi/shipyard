## Goal

The conveyor dispatches a diamond child only into a tree that contains all of its parents (D-42, REQ-138 dispatch from the graph, REQ-136 seams before point fixes). A diamond child is a ticket with two or more same-phase, same-repo parents.

- **Readiness (`state-sync.cjs`).** The primary parent keeps the current rule: at `branched` it is enough, because the worktree is cut from its branch. Every other same-phase, same-repo parent must have **landed in the phase epic**. Until then the ticket is blocked, and the board line says which parent it is waiting for and why.
- **Worktree (`ticket-worktree.sh create`).** When it cuts a fresh branch for a diamond child, it merges `origin/<epic>` into the new branch before printing the path. The tree then holds the primary chain and every landed non-primary parent. If that merge conflicts, `create` fails and leaves nothing behind.
- **Scope (`scope-gate.cjs`, `delivery-commit-finalizer.cjs`).** A diamond child's own work is measured against the merge of its base and the epic, not against the base alone. The epic content the child merged in is not reported as out of scope, and any path the child itself changes still is.
- **Backlog.** This closes `.planning/backlog/diamond-child-base-is-materially-incomplete.md`.

Operational order for this phase: diamond children of phase 40 (T-40-09, 11, 15, 22, 23, 24, 25, 26) are dispatched only once this ticket is merged into the epic and the conveyor that delivers them runs a build containing it: the dogfood install root from T-40-21, or a release. Before that, use the manual workaround described in the backlog entry. This is an operating precondition, not a `depends_on`: none of those tickets imports, edits or verifies against this ticket's files (see 40-PLAN-CHECK "Amendment after user review").

## Scope

1. NEW `plugins/delivery-pipeline/scripts/diamond-parents.cjs`: the only module that answers the diamond questions.
   - `nonPrimaryParents(id, tickets)` returns the row's `depends_on` entries that are in the same phase and repo and are not `primary_parent`, in declaration order.
   - `landedInEpic(id, tickets, state, epic)` returns `{landed: true}` or `{landed: false, reason}`.
     - A parent has landed when its state entry is `merged` and `merged_into === epic`.
     - It has also landed when `merged_into` is the `branch` of another same-phase, same-repo ticket that has itself landed. Follow that chain recursively with a visited set. This covers a stacked parent squashed into its own parent's branch before that branch landed.
     - A missing state entry, a missing `merged_into`, or a chain that ends on an unlanded branch is `landed: false`. Each case has its own reason sentence.
   - `scopeBase({root, base, row, tickets, env})` returns `{kind: 'ref', ref: base}` unless all of these hold:
     - the row has non-primary parents;
     - `origin/<row.epic>` resolves;
     - that ref is an ancestor of HEAD;
     - it is not an ancestor of `base`.

     When they all hold, it returns `{kind: 'tree', tree, epic}`, where `tree` comes from `git merge-tree --write-tree <base> <epic sha>`. When `merge-tree` fails or reports a conflict, it throws an error naming the epic and the base. That fails closed: the caller must refuse, not fall back to a narrower measurement.
   - CLI: `diamond-parents.cjs non-primary <ticket> [--graph <dir>] --json` prints `{ticket, primary_parent, epic, non_primary: [...]}`. It locates the graph through `graph-dir.cjs`. An unknown ticket exits 2.
2. `state-sync.cjs`, epic-stacked mode only:
   - When a PR's `state` is `MERGED`, record `entry.merged_into = pr.baseRefName` so the file stays deterministic (T-40-02).
   - In the readiness loop, for each non-primary parent that `landedInEpic` reports not landed, `addBlocker(d, reason)`. Each reason names the parent, its status, the primary parent the worktree is cut from, and the epic. Example: `non-primary parent T-x is branched — T-y's worktree is cut from T-z and receives T-x only through <epic>; T-x must merge into <epic> first`.
   - The primary parent's rule is unchanged: `pending` blocks and `branched` is enough. Cross-repo, cross-phase and direct-to-main rules are unchanged.
   - When a diamond child is ready, set `s.base_merge = t.epic`, and append to `s.base_reason` that `ticket-worktree.sh create` merges `<epic>` in for the named non-primary parents.
   - The existing `← awaiting` board line prints the new reasons. Add no new board section.
3. `ticket-worktree.sh create`, fresh-branch path only:
   - After `worktree add -b`, when the graph lookup finds the ticket, call `diamond-parents.cjs non-primary`. When `non_primary` is not empty:
     - Resolve `origin/<epic>`. If it is absent, remove the new worktree and branch and exit 13, naming the epic and the parents.
     - Otherwise run `git -C "$wt_dir" merge --no-ff --no-edit -m "Merge <epic> into <branch>"`. The subject carries no ticket id, because it is neutral for target projects (D-19).
     - On conflict, run `git merge --abort`, `git worktree remove --force` and `git branch -D`, then exit 13 naming the conflicting paths and the parents.
     - On success, assert that `origin/<epic>` is an ancestor of HEAD, and print `base-merged <epic> (<sha7>) — non-primary parents <list> are in this tree` on stderr.
   - In both reuse paths, never merge. When `non_primary` is not empty and `origin/<epic>` is not an ancestor of the reused branch, print a stderr warning naming `base-merge.cjs <T> --worktree <path> --base <epic>`.
   - Before writing this step, read the dispatch preflight in `claude-delivery-host.cjs` (around `:490-510`) and `codex-delivery-host.cjs` (around `:200-220`). If either requires HEAD or the commits between base and HEAD to be signed, sign the merge (`-S`) whenever `user.signingkey` is configured, and add a test for it. If it requires something this script cannot provide, stop and escalate (deviation Rule 4). Do not edit the hosts.
   - Keep `set -euo pipefail`, bash 3.2 compatibility and the git lock that is already held.
4. `scope-gate.cjs` and `delivery-commit-finalizer.cjs`: measure through `scopeBase`.
   - The scope gate diffs `<tree> HEAD` when the result kind is `tree`, and `<base>...HEAD` otherwise.
   - The finalizer finds its row through `resolveGraphDir([], root)` plus `loadTickets`, by `branch === expectedBranch`. For kind `tree` it computes `committed` from `git diff --name-only -z --no-renames <tree> <head>`. The ancestry check on `expectedBase` stays as it is.
   - If the graph cannot be resolved, or no row matches, behaviour is unchanged. That is the strict direction.
   - If `scopeBase` throws, both scripts refuse with its message.

## Acceptance criteria

- A two-parent diamond is not ready while its non-primary parent is only `branched`, and the board line names that parent, the primary parent and the epic.
- After the non-primary parent has merged into the epic, directly or through a stacked branch that landed, the child is ready. Its base is still the primary parent's branch, and `base_merge` names the epic.
- A primary parent at `branched` is still enough. Cross-repo, cross-phase and direct-to-main results do not change for any existing fixture.
- `ticket-worktree.sh create` for a diamond child yields a tree that contains every parent, prints only the path on stdout, and leaves nothing behind on a conflict or a missing epic (exit 13).
- `scope-gate.cjs` and the finalizer do not report the merged epic content, still report every undeclared path the child changes, and refuse when the diamond scope base cannot be computed.
- The backlog entry is marked resolved.
