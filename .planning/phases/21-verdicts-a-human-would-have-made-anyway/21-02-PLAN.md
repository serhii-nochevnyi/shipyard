## Goal

A pre-authorized checkpoint ticket merges unattended; an un-authorized one still
waits for a person, and still does not block the cascade. The guard and the
board must reach that answer through the SAME code.

## Context (Reads)

- `sentinel.cjs:428` — `if (t.human_checkpoint) return block('human_checkpoint ticket — the merge is the human\'s by contract')`.
  This becomes: refuse if checkpoint AND NOT pre-authorized.
- `sentinel.cjs:233` `checkpointParentOf(id)` and `front.cjs:95` `checkpointParent(id)`
  — **two copies of the same rule.** Measured, not assumed: they are separate
  functions in separate files, used at `sentinel.cjs:331/337` and
  `front.cjs:162/175`. CLAUDE.md's standing rule is that the front must never
  offer what the guard refuses, and this phase's own predecessor showed how
  duplication ends: T-22-01 shipped because two renderers hardcoded a lifting
  rule the store contradicted. Adding a second condition to two copies is the
  same mistake with a longer fuse. Reduce to one shared predicate as part of
  this change — that is the point of the ticket, not a side quest.
- `tickets.json.preauthorized` — written by T-21-01, read here for the first time.
- **The epic → integration-branch PR is never auto-merged, whatever the config
  says** (CLAUDE.md; `sentinel.cjs` refuses it today). Pre-authorization must not
  reach it. This is the single most dangerous way this ticket could go wrong, so
  it gets an explicit test rather than a comment.
- The child rule: a child never lands into an OPEN `human_checkpoint` parent,
  because squashing rewrites the diff a person is reading. If the parent is
  PRE-AUTHORIZED, that reasoning does not apply — nobody is reading it — but the
  parent must still land first. Decide this deliberately and state the choice in
  the code: the safe reading is that the child waits for the parent to MERGE (as
  any stacked child does), not for a person.
- Journalling: a pre-authorized merge must record `preauthorized=true` on its
  `merge` event. Design-time authorization is only defensible if it is auditable
  afterwards — otherwise the board cannot distinguish "a human approved this in
  advance" from "the guard merged a checkpoint it should have refused".

## Scope

- One predicate — "does this ticket still need a person?" — exported from one
  home and used by both `sentinel.cjs` and `front.cjs`. Both call sites for the
  parent rule use it too.
- `sentinel.cjs merge` refuses a checkpoint ticket only when it is not
  pre-authorized; the refusal text keeps naming the contract.
- `front.cjs` routes an un-authorized checkpoint to `waiting.merge_human` exactly
  as today, and a pre-authorized one into the actionable `merge` bucket.
- The `merge` journal event carries `preauthorized=true` when that is why it was
  allowed.
- The epic → integration PR remains refused unconditionally.

## Out of scope

The frontmatter field (T-21-01), `decompose.md` (T-21-03), and any change to
what `human_checkpoint` MEANS — it still marks a ticket as needing human
judgment.

## Acceptance criteria

- Checkpoint + `preauthorized: true` + green + conform + threads 0 → `merge`
  proceeds, and the journal line carries `preauthorized=true`.
- Checkpoint + not pre-authorized → refused with today's message, and the front
  shows it under `waiting`, never `parked`.
- A pre-authorized checkpoint ticket's CHILD is not offered for merge until the
  parent has actually merged.
- The epic → integration PR is refused even when every ticket in the phase is
  pre-authorized.
- `front.cjs` and `sentinel.cjs` agree on every combination — asserted by a test
  that drives both from the same state, not by two parallel tests.

## Test strategy

The agreement test is the one that matters: build the state once, assert the
board's bucket and the guard's verdict are consistent for authorized,
un-authorized, and child-of-authorized. Pin the epic refusal separately.
