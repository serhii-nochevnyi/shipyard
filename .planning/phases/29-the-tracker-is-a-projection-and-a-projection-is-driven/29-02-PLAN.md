## Goal

`delivery_pipeline.jira_transitions` — a map from OUR status to the tracker's
TARGET STATUS NAME, declared where GSD can set it, defaulting to empty, which
means the projection is off.

## Context (Reads)

- ADR-008 D2, including why the knob is TOP-LEVEL and not a member of
  `cfg.jira`.
- `pipeline-config.cjs:505-537` — `merged = {...raw.pipeline, ...raw.delivery_pipeline}`
  is a SHALLOW merge, so an object-valued `jira` in one namespace replaces the
  other's wholesale. That is the whole argument for a flat key: a nested one
  would vanish the moment a user set a single key in the other namespace.
- `pipeline-config.cjs:153-215` — `codex_models`, the precedent to copy: a
  structure declared in `capability.json` as a comma-separated STRING because
  GSD's capability config vocabulary is `boolean|string|number|enum`, parsed
  here into an object, with a warning per malformed entry rather than a throw.
- `pipeline-config.cjs:345` — `KNOWN_KEYS = new Set(Object.keys(DEFAULTS))`, so
  the key is known by virtue of appearing in `DEFAULTS`.

## Scope

- `DEFAULTS.jira_transitions = {}` — empty, which is OFF. Same posture as
  `pipeline.fable: off`: silence is not consent to write into someone's tracker.
- Parse `"pr-open:In Progress, merged:Done"` (and an object, like
  `codex_models` accepts both) into `{ 'pr-open': 'In Progress', merged: 'Done' }`.
- Warn and SKIP, never throw:
  - a left-hand side that is not one of the four statuses `state-sync` actually
    writes — `pending`, `branched`, `pr-open`, `merged`. The warning must NAME
    those four, because the tempting wrong values are the front's BUCKET names
    (`fix`, `finalize`, `merge`, `ci`), which are computed by `front.cjs` and
    never appear in the `status_change` stream this map is consumed against.
  - an empty right-hand side.
- Declare `delivery_pipeline.jira_transitions` in `capability.json` as a
  `string` with default `""`, beside `codex_models`.
- Copy every container value rather than sharing it with `DEFAULTS` (the comment
  at `pipeline-config.cjs:516` says why: a caller that mutates the returned map
  in place would change what the next `loadConfig()` in the same process
  returns).

## Acceptance criteria

- Default config yields `jira_transitions: {}` and NO warning.
- `"pr-open:In Progress, merged:Done"` parses to two entries.
- `"fix:In Progress"` yields exactly one warning naming the four real statuses
  and produces no entry.
- **Witnessed mutation**: delete the left-hand-side validation, show the test
  goes red, restore it. Paste both outputs.
- **Witnessed shared-container mutation**: prove the returned map is a copy —
  mutate it and show a second `loadConfig()` is unaffected. Copy this case from
  the `codex_models` one if it exists; if it does NOT exist, say so in the PR
  rather than implying it did.
