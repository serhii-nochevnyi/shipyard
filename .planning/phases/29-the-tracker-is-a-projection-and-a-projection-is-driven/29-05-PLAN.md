## Goal

The watermark advances on EVIDENCE and on nothing else. An agent that says it
transitioned an issue and cannot name the transition id it used has not produced
evidence, and ADR-004's rule — positive evidence before a mutation — governs the
conveyor's own records exactly as it governs code.

## Context (Reads)

- ADR-008 D5; ADR-004 for the principle; ADR-006 D5 for the precedent
  (`--agent-file` cross-checked against the role, so a journal line cannot be
  written about a dispatch that did not happen).
- `plugins/delivery-pipeline/scripts/log-event.cjs:142-175` — `OWNED_BY_SCRIPTS`
  holds eight events in three kinds: `duplicate` (merge, status_change),
  `halfAct` (escalation, plan_defect, dispatch) and `forgedState` (flake,
  flake_rerun, flake_lift). Read the `dispatch` entry's comment in full — it is
  this repository's own account of what a hand-written journal line costs, and
  it exists because a plan asserted `log-event.cjs` already refused `dispatch`
  when it did not.
- `plugins/delivery-pipeline/scripts/dispatch-record.cjs` — the shape of a
  record verb that validates its arguments before writing.

## Scope

- `jira-project.cjs record <ticket> <key> --transition-id <id> --status <name> [--graph <dir>]`:
  - REFUSE, non-zero, naming what is missing, when `--transition-id` is absent
    or empty. That is the whole point of the ticket.
  - REFUSE when the ticket has no pending item in `plan`'s output — recording a
    projection nobody asked for is the same forged state the `flake` entries
    guard against.
  - On success: advance the watermark (T-29-03's store) AND append a
    `jira_transition` journal event. Both, under one lock — parking and
    journalling are ONE act here for the same reason they are in
    `escalation-record.cjs`, which shipped six journalled escalations with no
    park and a seventh parked with no journal entry.
  - A second verb `record --unreachable <ticket> <key> --offered "<names>"`
    records that the workflow does not permit the target from the current
    status. It advances NOTHING — it is a report, so the next round tries again
    once the issue moves.
- `log-event.cjs`: add `jira_transition` to `OWNED_BY_SCRIPTS` with `why:
  halfAct`, `by: 'jira-project.cjs record'`, `otherHalf: 'ADVANCING the
  watermark'`, `lost: 'record'`, and a `fix:` line spelling the real command.
  It is that kind precisely: a hand-written line leaves the watermark unmoved,
  so the next round re-projects the same ticket and transitions the issue twice.

## Out of scope

- Calling the tracker — T-29-06.
- Any retry, backoff or queue. An unreachable target is a report, not a job.

## Acceptance criteria

- `record` with no `--transition-id` exits non-zero and names the flag; the
  store and the journal are BOTH unchanged (assert both, not one).
- `record` for a ticket with no pending item is refused.
- A successful `record` advances the watermark and appends exactly one
  `jira_transition`; a second identical `record` is then refused as not-pending.
- `log-event.cjs jira_transition …` by hand is refused and prints the `fix:`
  line.
- **Witnessed mutation, both halves**: (a) delete the `--transition-id`
  requirement, show a bare record succeeds, restore it; (b) remove
  `jira_transition` from `OWNED_BY_SCRIPTS`, show a hand-written line lands,
  restore it. Paste all four outputs.
- **Witnessed atomicity mutation**: make the journal append fail after the
  watermark write and show the pair does not half-commit.
