## Goal

`jira-project.cjs plan [--json]` — a pure function of the journal, `tickets.json`
and the config, emitting what should be transitioned and nothing else. It is the
half that can be proved mechanically, so it is made as large as the design
allows.

## Context (Reads)

- ADR-008 D3, and D1 for why the journal rather than live state.
- `plugins/delivery-pipeline/scripts/state-sync.cjs:787` — the record being
  consumed: `{ts, event: 'status_change', ticket, from, to, pr}`.
- `plugins/delivery-pipeline/scripts/log-event.cjs:144` — `status_change` is in
  `OWNED_BY_SCRIPTS` with `state-sync.cjs` as its SOLE writer. That ownership is
  what makes the stream trustworthy enough to drive an external mutation from.
- `plugins/delivery-pipeline/scripts/stop-gate.cjs:292-303` — take ONE lesson
  from it and reject the other. **Take**: the first line is dropped only when
  the read actually SEEKED; dropping it unconditionally ate the only event in a
  short journal, which is every project not running for weeks, and the test
  caught it. **Reject**: `JOURNAL_TAIL_BYTES = 64 * 1024`. That bound exists for
  a HOOK's ~75ms budget, and this journal is ALREADY 139 KB / 806 events — more
  than double it. A bounded read here would silently drop transitions older than
  the window, which would quietly falsify ADR-008 D6's whole justification
  ("catch-up is free, a skipped round lags one round and the next closes it").
  The planner runs once per round, not on a hook budget.
- `.planning/graph/delivery-log.jsonl` in this repo — 205 real `status_change`
  records to build a fixture from.

## Scope

- `plan` reads: the journal **from the OLDEST per-ticket watermark forward** —
  never a fixed-size tail — plus `tickets.json` for `jira` keys and
  `jira_transitions` from the config. With no watermarks at all, read the whole
  file; it is one sequential read per round.
- `pipeline.jira.enabled: false` → empty list, exit 0, no warning. State it as a
  rule rather than relying on the accident that no ticket currently carries a
  key.
- Emits, per pending item: `{ticket, key, from, to, target_status}`.
- A ticket with no `delivery.jira` key is NOT a subject and not a warning.
- A `to` with no entry in the map is skipped silently — an operator who mapped
  only `merged` asked for only `merged`.
- **An item recorded `unreachable` at some `to` is SUPPRESSED until a newer
  `status_change` for that ticket exists.** Without this the pair is a retry
  loop wearing a report's hat: the item is re-emitted every round, the agent
  asks the tracker for transitions again, records unreachable again, forever —
  one tracker call per stuck ticket per round, which is exactly the "never retry
  hard" that ADR-008 D4 forbids. This is `escalation-record.cjs`'s
  fingerprint-expiry shape over a different subject: the block lifts by itself
  when the world moves.
- Collapse: several `status_change`s for one ticket since the watermark produce
  ONE item, at the LATEST status. A board that moved `pending`→`branched`→
  `pr-open` between two runs must not walk the issue through three transitions.
- Exit 0 with an empty list when there is nothing to do. This runs every round;
  the common case is zero work and it must be silent and cheap.

## Out of scope

- Performing anything. No `getTransitionsForJiraIssue`, no MCP, no network — the
  negative pin from T-29-01 is already watching this file.
- Advancing the watermark — T-29-05 owns that, because advancing it is the act
  that requires evidence.

## Acceptance criteria

- Over a fixture journal: the collapse case yields ONE item at the latest
  status; a ticket already at its watermark yields none; a ticket with no `jira`
  key yields none; an unmapped `to` yields none; `jira.enabled: false` yields
  none.
- **Witnessed window mutation, the one that matters**: build a fixture whose
  journal exceeds 64 KB with the pending `status_change` OLDER than the last
  64 KB, and show the item is still emitted. Then impose a 64 KB tail and show
  the item VANISHES — silently, exit 0, empty list. Paste both. A projection
  that loses transitions without saying so is worse than one that never ran.
- **Witnessed unreachable-suppression mutation**: record an item unreachable,
  re-run `plan`, show it is NOT re-emitted; append a newer `status_change` for
  that ticket and show it comes back.
- Empty map (the default) → empty list, exit 0, no warning.
- **Witnessed collapse mutation**: remove the collapse and show the fixture
  produces three items where one is correct; paste both outputs.
- **Witnessed tail mutation**: reproduce the short-journal case — drop the first
  line unconditionally and show the single-event fixture yields nothing.
- `plan` makes ZERO network calls: assert it by running with no network
  reachable, or by asserting the source contains no `http`/`fetch`/`gh `/`mcp`
  token. State which of the two you did.

## Test strategy

records in `.planning/graph/delivery-log.jsonl`, not hand-invented shapes.
