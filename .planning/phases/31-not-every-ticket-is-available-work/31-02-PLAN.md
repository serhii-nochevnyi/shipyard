## Goal

Give projects an explicit, opt-in vocabulary for the tracker statuses that may
enter the delivery conveyor.

## Context (Reads)

- `.planning/architecture/ADR-009-not-every-ticket-is-available-work.md` — D3,
  especially the empty-default and status-name decisions.
- `plugins/delivery-pipeline/scripts/pipeline-config.cjs:384-453` — the existing
  flat string-map parser for `jira_transitions`, its namespace precedence, and
  warning conventions.
- `plugins/delivery-pipeline/scripts/pipeline-config.cjs:665-820` — config
  loading, `KNOWN_KEYS`, and the preferred `delivery_pipeline.*` namespace.
- `capabilities/delivery-pipeline/capability.json` — the declared string
  settings that GSD can validate and set.
- `tests/unit/pipeline-config.test.cjs` — config fixtures covering defaults,
  namespace precedence, malformed values, and capability declarations.

## Scope

- Add `jira_todo_statuses` to the shared config reader and capability manifest as
  a comma-separated string, with an empty default meaning the eligibility gate
  is off.
- Normalize trimmed, non-empty status names while preserving their tracker
  spelling; reject non-string or unusable values with a warning and leave the
  gate disabled.
- Keep `delivery_pipeline.jira_todo_statuses` preferred over the legacy
  `pipeline.jira_todo_statuses`, matching the existing shallow namespace merge.
- Document the key and its opt-in semantics in the delivery command and public
  README, including that matching uses the tracker status NAME.
- Test the empty default, parsing, malformed input, namespace precedence, and
  capability declaration.

## Out of scope

Fetching Jira, matching `statusCategory`, assignee logic, changelog/worklog
inspection, parking, direct overrides, or any front/state-sync behavior.

## Acceptance criteria

- A project with no `jira_todo_statuses` behaves exactly as before and makes no
  eligibility decision.
- A value such as `To Do, Backlog, Selected for Development` becomes a stable
  ordered set of status names with blanks removed.
- A malformed value cannot turn the gate on silently and produces the same
  warning-oriented config behavior as other delivery knobs.
- The capability manifest declares the same string key and empty default the
  reader implements.
- Documentation names status NAME as the matching field and does not imply a
  `statusCategory` fallback.

## Test strategy

Use isolated config fixtures and the existing capability parity assertions. No
network or tracker credentials are needed.

node --test tests/unit/pipeline-config.test.cjs

## Artifacts this phase produces

## Dependencies and risks

The predicate and park records must not invent their own status vocabulary, so
they consume this normalized config after the external-import hole is closed.
