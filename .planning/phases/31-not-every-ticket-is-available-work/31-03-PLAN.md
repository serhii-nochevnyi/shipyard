## Goal

Create one pure predicate that answers whether a tracker observation authorizes
a ticket to start, using only the status NAME and assignee fields already in the
default issue response.

## Context (Reads)

- `.planning/architecture/ADR-009-not-every-ticket-is-available-work.md` — D4
  and the evidence excluding changelog and worklogs.
- `plugins/delivery-pipeline/scripts/pipeline-config.cjs` — the normalized
  `jira_todo_statuses` value from T31-02.
- `plugins/delivery-pipeline/scripts/check-state.cjs` and
  `plugins/delivery-pipeline/scripts/front.cjs` — shared pure-predicate style
  and the requirement that readers consume one owner rather than duplicate
  rules.
- The connected Jira tool contract recorded in ADR-009 — default fields include
  `status` and `assignee`; changelog pagination is not a complete history.

## Scope

- Add a side-effect-free evaluator that accepts a tracker status NAME, an
  assignee observation, and the configured status set, and returns a structured
  eligible/ineligible verdict with a human-readable reason.
- Treat eligibility as status-name membership AND unassigned; distinguish an
  assigned ticket from an unknown observation.
- Normalize the documented status/assignee shapes needed by the caller without
  depending on the MCP variant's optional `fields` versus `view` argument.
- Keep status matching exact after trimming and do not inspect or accept
  changelog, worklog, `statusCategory`, priority, labels, or sprint data.
- Cover assigned, unassigned, status mismatch, empty policy, malformed or
  missing observations, and the honest re-eligibility case after an assignee is
  cleared.

## Out of scope

Tracker I/O, cache persistence, generation/expiry, front buckets, direct
overrides, or changes to the delivery command.

## Acceptance criteria

- The same input always returns the same verdict and performs no filesystem or
  network access.
- A configured status with no assignee is eligible; every other complete pair is
  ineligible with a reason naming the observed status or assignee.
- Missing status or assignee is represented as unknown rather than eligible.
- The evaluator does not read a changelog or infer prior work from any history
  field.
- A status returned to a configured name with the assignee cleared evaluates as
  eligible, matching ADR-009's stated consequence.

## Test strategy

Unit-test the pure evaluator with table-driven positive and negative fixtures,
including extra history fields that must be ignored. Keep tracker access out of
the suite.

~~~

- Focused unit coverage for the status-plus-assignee rule.
