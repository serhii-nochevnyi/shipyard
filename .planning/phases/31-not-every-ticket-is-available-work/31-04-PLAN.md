## Goal

Add the durable read-cache and its sole writer so an unreadable tracker answer
parks only the affected ticket and never authorizes a new dispatch.

## Context (Reads)

- `.planning/architecture/ADR-009-not-every-ticket-is-available-work.md` — D5
  and D7's separation from the Jira projection watermark.
- `plugins/delivery-pipeline/scripts/drift-record.cjs` and
  `plugins/delivery-pipeline/scripts/escalation-record.cjs` — the established
  four-store discipline: project graph resolution, a lock beside the store,
  atomic writes, active-record expiry, and structured reasons.
- `plugins/delivery-pipeline/scripts/jira-project.cjs` — the existing
  `jira-projection.json` write watermark that must remain a different store with
  different expiry semantics.
- `plugins/delivery-pipeline/scripts/lock.cjs` and
  `plugins/delivery-pipeline/scripts/graph-dir.cjs` — the canonical lock and
  `--graph` handling, including refusal to write beside a missing ticket graph.
- `tests/unit/record-stores.test.cjs` — concurrency, graph selection, and atomic
  store expectations.

## Scope

- Create `tracker-record.cjs` with a project graph `tracker.json` store and
  `tracker-record` lock, keeping the store separate from
  `jira-projection.json`.
- Implement the library reader for active records and the validated write
  primitives needed by later tickets. Bind each observation to the current
  delivery-state generation (and retain the tracker observation timestamp) so a
  later cold start does not reuse an old answer without a new read.
- Persist structured records containing the ticket, Jira key, observed status
  and assignee when available, verdict, reason, observation time, and the
  delivery generation. Preserve `unknown` as a first-class verdict with the
  tracker error words; never coerce it to an empty status or to eligible.
- Refuse a write without a ticket graph, ticket id/key, status for the normal
  observation path, or an explicit assignee value (`none` is valid). Keep all
  read-modify-write operations under the lock and use atomic replacement.
- Expose the active map in the shape the front can consume, with records from a
  previous delivery generation omitted. Add concurrent mark fixtures and prove
  that the existing Jira projection store is untouched.

## Out of scope

The front's bucket transition, MCP calls, direct override journalling, external
ticket routing, and changes to state-sync or dispatch-record call sites.

## Acceptance criteria

- A complete eligible or ineligible observation survives a process restart and
  is readable from the project graph regardless of the caller's cwd.
- An unknown observation is durable, names the tracker error, and is returned as
  unknown so a consumer can park the ticket.
- A record from an older delivery generation is not active on the next cold
  start; a newly recorded observation can become active for the current one.
- Missing status, missing explicit assignee, malformed graph selection, and
  concurrent writes fail safely without losing another ticket's record.
- No write changes `jira-projection.json`, the delivery journal, or foreign
  config/state files in this ticket.

## Test strategy

Use temporary project graphs and child processes for atomic/concurrent writes.
Assert exact JSON fields and negative writes; do not contact Jira or GitHub.
