## Goal

Make the actionable front withhold only the moment a new ticket would enter
`execute`, while allowing the conveyor to continue its own branched and PR work.

## Context (Reads)

- `.planning/architecture/ADR-009-not-every-ticket-is-available-work.md` — D1
  and D5, including the definition of outside work and the fail-closed result.
- `plugins/delivery-pipeline/scripts/front.cjs:311-769` — the pure front
  classifier and the narrow `pending + ready → execute` branch.
- `plugins/delivery-pipeline/scripts/front.cjs:1360-1490` — board rendering and
  fixpoint behavior; tracker parks must remain visible as blockers and must not
  create a false completed fixpoint.
- `plugins/delivery-pipeline/scripts/tracker-eligibility.cjs` and
  `tracker-record.cjs` from T31-03/T31-04 — consume their verdicts instead of
  duplicating status or cache rules.
- `tests/unit/front.test.cjs` — pure front fixtures for pending, branched,
  parked, and fixpoint cases.

## Scope

- Add a tracker-verdict input to `computeFront` and gate only a pending ticket
  that is otherwise ready for `execute` when the policy is enabled.
- Allow a current-generation eligible record to enter `execute`; route
  ineligible, unknown, missing, and no-key records to a durable-style blocked
  explanation that names the tracker fact and the direct-ticket remedy.
- Leave `branched`, `pr-open`, `merged`, and dependency-blocked tickets on their
  existing paths, so a resumed conveyor can finish work it already owns.
- Preserve the disabled-policy behavior exactly: an empty
  `jira_todo_statuses` value does not require or inspect tracker records.
- Test the transition boundary, all tracker verdicts, missing observations,
  policy-off behavior, and the fact that an in-flight/PR ticket is not gated.

## Out of scope

Tracker I/O, cache writes, direct override recording, state-sync wiring, and
changes to the stop-gate or sentinel ownership model.

## Acceptance criteria

- A ready pending ticket with an eligible current record appears only in
  `actionable.execute`.
- The same ticket with an ineligible or unknown record is in a blocked bucket
  with a reason that preserves the tracker observation and does not appear in
  any actionable bucket.
- A missing current record fails closed when the policy is enabled.
- A policy-off front produces the pre-Phase-31 result even if tracker data is
  present or malformed.
- A branched or PR-open ticket remains deliverable/guardable regardless of the
  tracker gate.

## Test strategy

Exercise `computeFront` directly with explicit tracker maps and isolated config
options. No MCP, GitHub, or filesystem store is needed for the classifier proof.

## Verification commands

~~~bash
node --test tests/unit/front.test.cjs
~~~

## Artifacts this phase produces

- A pure front transition guard for new execution.
- Unit evidence that resumed conveyor work is never deadlocked by tracker state.

## Dependencies and risks

The front consumes the D5 store contract but does not write it. Keeping the
transition boundary here prevents a missing tracker answer from changing the
sentinel's handling of work already on a branch or PR.
