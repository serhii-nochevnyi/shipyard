## Goal

D6 shipped a guard whose whole purpose is that the next phase not ship an inert
mechanism — and it cannot fail for four of its six rows. And the one repair path
that CAN measure its own depth records it where nothing reads it. Both halves,
in one ticket, because the second satisfies two of the first's new homes.

## Scope

- **Every `WIRED` row must fail when its caller is deleted.** Re-anchor the four
  that survive so each matches a CALLER-ONLY shape, the way
  `entry\.behind_by\s*=` already does: either a section-bounded slice (the
  `SUBJECTS` machinery already has one) or a pattern that cannot match the
  event's own schema documentation.
- **`references/pr-sentinel.md` becomes a second `home`** for `effort_applied`
  and the `base_merge` event, so the pin asks about BOTH entry points.
- **The guard's attempt row carries the depth.** Add
  `effort_applied=<level|unknown>` to the "After EVERY push" `log-event.cjs
  attempt` line, with one sentence distinguishing the two stores: the level goes
  on the **attempt** row because that is what `failure-signature.cjs` reads;
  `dispatch-record.cjs --effort-applied` records the same fact about the
  **dispatch** and is not a substitute.
- **The guard's `base-merge` duty journals**, matching `deliver.md` step d.

## Out of scope

The three paths where NO depth exists to record — the guard fixing in-process,
the Agent fallback, and all of Codex. No edit produces that evidence; the remedy
reverses ADR-007 D2's own "`unknown` is not evidence" sentence, or makes the
rule runtime-aware, and either is a decision about when the conveyor stops
repairing on its own. That earns an ADR and a checkpointed ticket, and the
integrator's W1 says so. Also out: `missing_paths` as a `decided` row (E4),
`CLAUDE.md` and `drift-needed.cjs`'s header (M3/M4, post-merge by construction).

## Acceptance criteria

- **Each of the six rows fails when its caller is deleted, demonstrated per
  row.** Not one criterion covering the table: six runs, six recorded. The four
  currently-passing rows fail on base for the wrong reason today — they pass —
  so the demonstration IS the RED-on-base evidence.
- Deleting only the SCHEMA documentation of an event, leaving its caller, does
  NOT fail the pin. Assert it: that is the boundary the re-anchoring must not
  cross, or the pin starts failing on documentation edits and gets loosened
  again.
- `references/pr-sentinel.md` names `effort_applied` on its attempt line and
  calls `log-event.cjs base_merge` in its `base-merge` duty; the pin has both as
  a second home and goes red if either is removed.
- The sentence distinguishing the `attempt` store from the `dispatch` store is
  present in the guard's file — a reader who has `--effort-applied` must not
  conclude the attempt row is covered.
- **Mutation check (ADR-006 Consequences).** Six caller-deletions and one
  schema-only deletion, each applied, the named test watched, reverted, and both
  runs recorded in the PR body.

## Test strategy

The demonstration is the deliverable here, so run it the way the integrator did:
against an extracted tree, deleting a caller and nothing else. A pin re-anchored
without that per-row evidence would be the same defect one turn later — this
ticket exists because a table was believed on the strength of one row's
criterion.
