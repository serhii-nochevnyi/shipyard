## Goal

`pipeline.max_concurrent_agents` counts AGENTS. A guard holding four open PRs is
one agent, not four, so the ordinary mid-phase board stops reporting a full
capacity with nothing dispatched. And on a board that IS full, the three
mechanisms that read capacity say one thing instead of three.

## Context (Reads)

- ADR-006 D1, and the measurement behind it: `.planning/backlog/phase-26-followups.md`
  §"Three more, from arch-review on PR #61", item 1. `deliver.md:1129` marks a
  `pr-sentinel` record for EVERY guarded ticket while Step 4 spawns ONE agent;
  `front.cjs:742` counts `Object.keys(dispatched)` over a role-blind
  `activeDispatches`. Four guarded PRs → `in_flight: 4` → `free: 0` under the
  default of 4, and no executor launches until a PR merges.
- The same note, item 2: `stop-gate.cjs` does not read `capacity` at all, and its
  with-an-agent hatch sits behind `count <= 0`.
- `ci-wait.cjs`'s own header: it REFUSES whenever anything is actionable, because
  "that wake-up is free and sooner". On a capacity-full board that wake-up is not
  free — the work cannot be taken.
- `dispatch-record.cjs`'s role table (`fields`/`lifts` per role) — read only. It
  is the list of roles this ticket assigns a cardinality to; T-27-05 owns edits
  to that file.
- `plugins/delivery-pipeline/workflows/{executors,fix-round,drift-gate}.mjs` — the
  `effort` each passes into `agent()`.

## Scope

- **The counting unit becomes the agent.** `computeFront`'s `in_flight` collapses
  live dispatch records by role cardinality: a role that runs as ONE agent per
  round regardless of how many tickets it holds (`pr-sentinel`) contributes 1;
  every per-ticket role (executor, the fixers, a drift judge, arch-review)
  contributes one per record, because `drift-gate.mjs` really does dispatch one
  judge per ticket in parallel. The cardinality table lives beside the counter in
  `front.cjs` and names `dispatch-record.cjs`'s role list as its source.
- `capacity` gains the collapsed count and keeps `max`/`free`. The actionable
  ORDER is still never reordered and never filtered — the cap remains a
  TRUNCATION, as T-26-12 shipped it.
- **The three readers agree on a full board.** `front.cjs` already says "do not
  dispatch" (`free: 0`, `fixpoint: NO`, reason names capacity). `ci-wait.cjs`
  stops naming capped-out items as work to take first: when everything actionable
  is beyond `free`, there is no free wake-up, so waiting is correct and the
  refusal (exit 3) must not fire on that ground alone. `stop-gate.cjs` reads
  `capacity` from the front it already loads and treats a full board as
  "an agent is out" — which it is — instead of falling through the
  `count <= 0` arithmetic.
- **A `max` of 0 is not a reason to trap a session.** `stop-gate.cjs` gains the
  hatch phase-26-followups item 2 names: a board that correctly cannot dispatch
  anything is not a defect to block on.
- **The effort assertion.** `tests/unit/workflows-args.test.cjs` asserts that every
  `workflows/*.mjs` `effort` default equals `pipeline-config.cjs`'s answer for
  that role, resolved in a config-free temp cwd so the check documents shipped
  policy rather than this checkout's tuning. `executors.mjs` and `fix-round.mjs`
  agree today by luck; `drift-gate.mjs` does not agree at all and is corrected
  here.

## Out of scope

Per-role or per-model WEIGHTING of the cap (T-26-12 put it out of scope for the
same reason: it needs a cost model the conveyor does not have). Raising the
default. `dispatch-record.cjs` itself — T-27-05 owns it. `drift-gate.mjs`'s
per-ticket `baseRef`, which is T-27-06.

## Acceptance criteria

- A board with one `pr-sentinel` record covering four guarded tickets reports
  `in_flight: 1`, `free: 3`. On current code it reports `in_flight: 4, free: 0`,
  so the test fails on base.
- A board with four executor records still reports `in_flight: 4, free: 0` — the
  collapse is per role, not a blanket one.
- On a full board: the front says `fixpoint: NO` with a capacity reason,
  `ci-wait.cjs --json` does NOT refuse with exit 3 naming the capped items, and
  `stop-gate.cjs` does not block. Today the second and third disagree with the
  first; assert all three in one fixture.
- `capacity.max === 0`: `stop-gate.cjs` exits 0 and stays silent.
- `workflows-args.test.cjs` fails on base because `drift-gate.mjs`'s effort
  default does not equal the resolver's answer for `drift-check`.
- **Mutation check (ADR-006 Consequences).** Restoring `pr-sentinel` to
  one-record-per-ticket fails `front.test.cjs`; changing any single
  `workflows/*.mjs` effort default fails `workflows-args.test.cjs`. Record both
  runs in the PR body.

## Test strategy

TDD in `front.test.cjs` first — the cardinality arithmetic, then the guard-holds-
four fixture, which is the whole ticket. Then one shared fixture asserted by all
three readers in their own suites: the point of the ticket is that they agree, so
three suites reading three hand-built boards would not prove it. `capability.json`'s
description of the knob changes from records to agents; `make test-graph` covers
its shape.
