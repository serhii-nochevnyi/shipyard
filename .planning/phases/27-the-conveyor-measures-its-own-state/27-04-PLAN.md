## Goal

An epic whose base has moved learns what landed under it, on purpose and with a
verb of its own. And a worktree is cut from the ref the board named, not from
whatever a stale local branch happens to point at.

## Context (Reads)

- ADR-006 D4, and the measurement: `epic/25` and `epic/26` each 27 then 31 commits
  behind `main`, containing zero occurrences of the predicates their next tickets
  were written against. Four separate times in one session, each time with
  `ticket-worktree.sh create` reporting success.
- `epic-branch.sh` — its existing `ahead_by`, and the rule that both scripts
  resolve refs that exist only as `origin/<name>`.
- `graph-dir.cjs`'s `resolveBaseRef`: both gates measure `origin/<base>` when it
  exists, because after an API squash-merge the LOCAL epic does not move. The same
  fact is what makes a bare `epic/…` dangerous here.
- `lock.cjs` — anything writing the shared `.git` serializes; `epic-branch.sh` and
  `ticket-worktree.sh` already take that lock.
- T-27-03: the base a child is published against. This ticket is the other half —
  the base being CORRECT is worth nothing if the epic never received the parent.

## Scope

- **`epic-branch.sh refresh <epic>`**: fetch, merge `origin/<base>` into the epic,
  push. It never resolves a conflict — it refuses, printing the conflicting paths,
  because a conflict here is a decision about someone's work and this script has
  no standing to make it.
- **Whatever refreshes also fast-forwards the local refs.** A refresh performed
  from a detached worktree leaves the local base and epic behind, and that is
  exactly the state measured four times: the next `create` then cuts from the old
  tip while reporting success. `git update-ref` on both, and say which refs moved.
- `deliver.md` Step 0 calls `refresh` for every epic whose base has moved, and only
  those — a refresh of an epic already up to date must be a no-op, not a push.
- **`ticket-worktree.sh create` measures `origin/<base>`**: it reports the distance
  of any branch it REUSES rather than reusing it silently, and a bare `epic/…`
  never resolves to a local ref when `origin/epic/…` exists and is ahead.

## Out of scope

Deciding a conflict, in any direction. Reaping branches. The epic → integration
PR, which is never auto-merged whatever this ticket does. `state-sync.cjs`, whose
`base`/`pr_base` resolution is T-27-03's.

## Acceptance criteria

- An epic behind its base: `refresh` merges, pushes, and afterwards BOTH the local
  base and the local epic point at the pushed tips. Assert the local refs, not just
  the remote — the local half is the part that was broken four times.
- An epic already current: `refresh` exits 0, pushes nothing, and says so.
- A conflicting refresh: non-zero, the conflicting paths named, the epic branch
  left exactly as it was (assert the sha).
- `create` reusing an existing ticket branch prints how far it is from
  `origin/<base>`. On base it prints nothing, so the test fails on current code.
- `create` with a bare `epic/<phase>` name, a stale local ref, and `origin/epic/<phase>`
  ahead: the worktree is cut from the ORIGIN tip. This is the four-times defect and
  it is the test that must fail on base.
- **Mutation check.** Drop the `update-ref` of the local base and the reuse-distance
  case still passes while the ref assertion fails — confirm that split, because it
  is what proves the local half is really being asserted.

## Test strategy

`worktree-smoke.sh` against real local git repositories, which is what that smoke
already does. Every case here is about ref topology, so nothing about it can be
proved with a stub: build a bare "origin", clone it, move the base, and assert
shas. Write the stale-local-ref case first.
