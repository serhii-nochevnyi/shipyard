## Goal

A `base-merge` that provably changes nothing keeps the architecture verdict
instead of buying it again. The proof is two object identities — the head trees
equal and the base trees equal — and the trailer records the base it judged as a
TREE, so the proof survives the base branch being reaped.

## Scope

- **The trailer records what it judged.** `gate-trailer.cjs` writes
  `base_tree=<40-hex>` beside `head=<oid>`: the tree of the merge base the verdict
  was rendered against. `parseGate` reads it; a trailer without it parses as
  before.
- **A `carry` verb, and it is the only writer of a carried verdict.**
  `gate-trailer.cjs carry <T> --pr <n> --from <old-head> --to <new-head>` re-stamps
  the existing verdict onto the new head IF AND ONLY IF both hold: the two head
  shas resolve to the SAME tree object, and the recorded `base_tree` equals the
  tree of the new merge base. It prints both trees on refusal. Anything else —
  a missing `base_tree`, an unresolvable sha, a tree mismatch — is a refusal, and
  the verdict is simply owed again.
- **`base-merge.cjs` calls it** after a merge it completed, passing the pre-merge
  head. A merge that changed content resolves to a different tree and is refused
  by construction, so the caller needs no judgement of its own.
- **No reader changes, deliberately.** Because the carry re-binds `head=`, every
  existing reader — `gateConform` in `gate-trailer.cjs`, its wrapper at
  `front.cjs:943`, `sentinel.cjs`'s live merge gate, `state-sync.cjs`'s parse —
  keeps working untouched. That is also what keeps this ticket out of three files
  the later tickets of this phase own.
- `references/arch-review.md` tells the judge to record the base tree, because
  that is the file the judge reads.

## Out of scope

`checks=green` never carries — a green is measured by CI against a base, and this
ticket does not teach CI anything. `drift-check` and `degenerate-green` verdicts.
Any tolerance in the head comparison. Carrying across a base move that DOES
change content, however small.

## Acceptance criteria

- A `base-merge` whose result tree is byte-identical to the pre-merge tree, with
  a matching recorded `base_tree`, leaves the PR with a `gate_status:` trailer
  bound to the NEW head and `arch-review=conform`. On base the trailer still names
  the old head and `gateConform` reads `stale`, so the test fails on current code.
- The same move where the merge brought content: `carry` refuses, exit non-zero,
  the message prints the two tree shas, and the trailer is untouched.
- A trailer with no `base_tree=` NEVER carries. Absent proof is not proof —
  assert this explicitly, because it is the backwards-compatible direction and
  the one a future reader will be tempted to relax.
- `base_tree` is the full forty characters. An abbreviated value is rejected on
  write, not silently accepted.
- **Mutation check.** Replace the base-tree comparison with a diff comparison and
  the suite still passes → then the test is wrong; the fixture must include a
  case the two disagree on (a rename inside the merged range). Replace the
  head-tree equality with sha equality and `trailer.test.cjs` fails.

## Test strategy

TDD in `trailer.test.cjs` for parse/write/carry over hand-built bodies, then in
`files-contract.test.cjs` against the real `cascade()` git fixture, which is where
"the same tree, a different sha" actually exists. The refusal cases are written
first: a gate that fails OPEN is the failure this ticket could introduce, and it
would be invisible in the happy path.
