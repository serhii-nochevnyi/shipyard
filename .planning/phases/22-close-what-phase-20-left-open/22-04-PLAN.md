## Goal

Close the window in `acquire()` where a lock that has just been created, and
whose owner is still being written, is indistinguishable from one whose owner
died — so a live holder can have its lock broken out from under it.

## Context (Reads)

- `lock.cjs` `acquire()`, lines 12-14 and 27-36. The interleaving:

      P1: fs.mkdirSync(lockPath) succeeds          ← holds the lock
          (descheduled before writeFileSync)
      P2: mkdirSync → EEXIST
          readOwner() → null (owner.json not written YET)
          age = NaN;  !(NaN < ttlMs) === true      ← judged stale
          breakLock(P1's live lock); continue
          mkdirSync succeeds                        ← P2 now "holds" it
      P1: resumes, writes owner.json into P2's lock

  Both processes then believe they hold it.
- The comment at lines 28-31 states the assumption that is wrong: "No owner.json
  = a process died between mkdir and the write". It is also, and far more often,
  a process that is ABOUT to write. The negated comparison it explains
  (`NaN < ttl` is false) is correct for the death case and is precisely what
  makes the live case fail.
- CLAUDE.md: "A lock directory with no `owner.json`, or one older than the TTL,
  is taken over — a killed session must not wedge the next run." That property
  must SURVIVE this fix; a lock nobody can ever break is the worse failure.
- Why it matters now: the sentinel runs CONCURRENTLY with the main loop, and
  `drift-gate.mjs` dispatches judges in parallel that each write a record. This
  is no longer a theoretical interleaving.
- `tests/unit/record-stores.test.cjs:106-116` — the six-concurrent-writers
  tests. They pass (verified against an async-capable harness), so this window
  has not yet been observed losing a record; it is a race, not a certainty.
- Reuse check (§5): the lock directory's own `mtime` already records when
  `mkdir` happened — the missing age is available without a new file, a new
  format, or a change of primitive.

## Scope

- When `owner.json` is absent, derive the lock's age from the lock DIRECTORY's
  mtime instead of treating it as unknown.
- A lock younger than a short grace window is HELD, not stale — long enough to
  cover mkdir→write (microseconds) with orders of magnitude to spare, far
  shorter than the TTL.
- Beyond that grace, the existing takeover behaviour is unchanged: an
  owner-less lock is still broken, so a session killed between the two calls
  cannot wedge the next run.
- An unparseable `owner.json` timestamp keeps its current treatment.

## Out of scope

`withLock`, `writeAtomic`, the TTL default, and switching the primitive from a
directory to an O_EXCL file — a larger change than the window justifies.

## Acceptance criteria

- A lock directory created microseconds ago with no `owner.json` is NOT broken
  by a second acquirer; the second waits.
- A lock directory with no `owner.json` and an mtime older than the grace IS
  broken, and the second acquirer proceeds.
- A lock whose `owner.json` is older than the TTL is still broken (unchanged).
- `withLock` callers are unaffected; the six-concurrent-writers tests still pass.

## Test strategy

Construct the states directly on disk — `mkdir` with no `owner.json`, then
back-date the directory mtime — rather than trying to win a real race. A test
that depends on scheduling would be flaky, which is the one thing this repo
treats as a first-class defect.
