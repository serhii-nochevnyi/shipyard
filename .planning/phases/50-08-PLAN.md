<objective>Replace the unconditional immediate refusal for any live lock owner with a bounded wait for a fresh owner, keep a named annotated refusal for an owner record older than the lock TTL, close the races that let concurrent first admission end in an unnamed refusal (a partially written authority key, a key read that straddles the creator's removal of its temporary name, a catalogue read torn by a peer's replace), and prove each outcome by test, so concurrent Codex and Claude sessions get a deterministic result.</objective>

## Goal

ADR-030 L-8 ("a second session waits a bounded time or gets a named refusal with a remedy") and the L-11 obligation to confirm bounded behaviour under pid reuse. 50-RESEARCH Pitfall 5 and Discrepancy D-3: today a live owner is refused instantly and `lock.cjs`'s TTL takeover is never reached. REQ-201 asks for success or a named refusal under a concurrent first admission, which the lock alone does not give: `withArchiveAuthorityLock` calls `authorityState(worktree, true)` before it takes the lock (`role-artifact.cjs:4005`), and that call creates the key non-atomically.

## Scope

In `withArchiveAuthorityLock`: read the owner record as today. Decision taken here: (a) owner pid dead, or lock absent, or owner record unreadable: unchanged, go to `acquire`; (b) owner pid live and owner `at` younger than `DEFAULT_TTL_MS`: call `acquire` with a bounded wait of 5000 ms (a named constant) instead of refusing at once; on timeout refuse with `ARCHIVE_AUTHORITY_BUSY` whose message names the owner's label, pid and `at`; (c) owner pid live and `at` older than `DEFAULT_TTL_MS`: refuse at once with `ARCHIVE_AUTHORITY_BUSY` whose message says the owner record is older than the lock TTL and its pid may have been reused by an unrelated process; do not take the lock over (mutual exclusion for a slow genuine holder is preserved). Also annotate the existing "not a physical directory" and "ownership was lost" refusals with their cause. Record the pid-reuse result as a documented limitation: recovery is to end that process, which the `ARCHIVE_AUTHORITY_BUSY` remedy states.

In `authorityState`: (d) create the key atomically. When `hmac.key` is absent and the existing-protected-records check passes, write the 32 random bytes to `hmac.key.<pid>.<uuid>.tmp` in the same directory (flag `wx`, mode `0600`), fsync it, `fs.linkSync` it to `hmac.key`, treat `EEXIST` as "another session created the key first, its key wins", and always unlink the temporary. `hmac.key` is never written directly, so it exists only complete. (e) read both `hmac.key` and `catalogue.json` through one private bounded-retry helper over `authorityFile`: up to 5 attempts about 10 ms apart (a synchronous wait), retrying only when `authorityFile` fails with the transient stat-change refusals (`archive authority changed before bounded reading`, `archive authority changed while reading`); any other error, a key whose length is not 32, any HMAC mismatch and the fifth failure propagate unchanged, and the length check and the HMAC check stay after the read. The key read is retried too: the key is immutable once linked, but the creator's unlink of its temporary name changes the shared inode's ctime after `hmac.key` is visible (see Context), and a reader that straddles that moment must not be refused. The retry re-runs the whole `authorityFile` verification (lstat, `O_NOFOLLOW` open, stat comparisons) on every attempt and never uses bytes from an attempt that failed, so it adds no trust. The creator also reads its key through this helper, after its `finally` has unlinked the temporary.

## Acceptance criteria

- With a lock held by this test process (live pid, fresh `at`) and released by a timer shortly after, a second `withArchiveAuthorityLock` call in a child process waits and then runs.
- With a lock whose owner record carries a live pid and a fresh `at` that is never released, the call refuses with `ARCHIVE_AUTHORITY_BUSY` after the bounded wait and the message names label, pid and time.
- With a live pid (a spawned `sleep`-like node child that never touched the lock) written into an owner record whose `at` is older than 120 s, the call refuses immediately with the annotated message and does not take the lock.
- With a dead pid and a stale `at`, the call takes the lock over through `acquire` exactly as before (existing test `role-artifact.test.cjs:994` still passes).
- In every refusal case no catalogue byte changes and no second owner record appears.
- Atomic key: `authorityState(worktree, true)` never opens `hmac.key` itself for writing (a spy on `writeFileSync`, `openSync`, `renameSync` and `linkSync` sees only temporaries written and one link); afterwards `hmac.key` is exactly 32 bytes with no group or other permission bits and no `hmac.key.*.tmp` remains. A creator that loses the link race (a competing complete key is linked first, deterministically, by wrapping `fs.linkSync`) returns the competitor's key and leaves no temporary.
- Concurrent first admission stress: six child processes started together by a file barrier call `authorityState(worktree, true)` on the same fresh worktree, repeated for ten fresh worktrees; every call returns the same 32-byte key and none throws (this exercises the link-then-unlink window against real concurrent readers and detects a regression only probabilistically; the deterministic key-read cases above are the evidence).
- Stable catalogue read: when a peer replaces `catalogue.json` between the reader's lstat and open (simulated by wrapping `fs.openSync` to rename a byte-identical copy over the catalogue on the first open) `historicalBookkeepingPins` returns the pins without throwing after one retry; when the file is replaced on every attempt the read refuses after exactly 5 attempts with the original message; a catalogue with a bad MAC is refused on the first attempt with no retry.
- Stable key read: the key read goes through the same helper. Deterministic evidence (fails against a key read that is not retried): with a valid 32-byte `hmac.key` and `fs.openSync` wrapped so the first open of `hmac.key` first gives it a distinct mtime with `fs.utimesSync` (an mtime change is detectable at any filesystem timestamp granularity), `authorityState(worktree, false, false, false)` returns the key after one retry without throwing; when every open of `hmac.key` is preceded by a fresh distinct mtime, the read refuses after exactly 5 attempts with the original `ARCHIVE_AUTHORITY_INVALID` message; a 31-byte key is refused on the first attempt with `archive authority key is malformed` and no retry (an oversize key is refused on the first attempt by the bounded-file check, also without retry). Realistic shape, recorded as such because its ctime change can be invisible on a coarse-timestamp filesystem: `hmac.key` created by `linkSync` from a temporary that is still present, and the first open of `hmac.key` unlinks that temporary; the read returns the key without throwing.
