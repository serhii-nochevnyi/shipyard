## Goal

Give a run one durable owner that can wait, retry, wake, checkpoint, and resume
without duplicate dispatch or a human choosing between technical recovery
paths.

## Context (Reads)

- `plugins/delivery-pipeline/scripts/run-contract.cjs`
- `plugins/delivery-pipeline/scripts/session-handoff.cjs`
- `plugins/delivery-pipeline/scripts/capacity-lease.cjs`
- `plugins/delivery-pipeline/scripts/stop-gate.cjs`
- `plugins/delivery-pipeline/scripts/state-sync.cjs`
- `plugins/delivery-pipeline/scripts/lock.cjs`

## Scope

Implement an atomic run store and controller API for ownership fencing,
heartbeat/expiry, retry budgets, wake conditions, checkpoint acknowledgement,
successor preparation, and idempotency keys. Add `runtime_unavailable` with
bounded retry metadata and a capability recheck deadline. Preserve exact
ownership on crash/restart and refuse an older state revision or a second
active owner. Expose a controller status snapshot for stop and delivery callers.

## Out of scope

- Runtime-specific process launch.
- Changing GitHub/Jira state semantics.
- Treating unsupported credentials or protected merges as automatic approvals.
- Replacing the existing capacity-lease implementation.

## Acceptance criteria

- Two owners cannot hold one run scope, including after a stale owner expires.
- Replaying begin, acknowledge, wake, retry, or complete events is idempotent.
- Crash before and after checkpoint acknowledgement yields one recoverable
  state and no duplicate successor dispatch.
- Host unavailability parks the run in `runtime_unavailable` with a machine
  retry condition; it never asks to switch provider or runtime.
- A changed PR head, dirty owned worktree, or active child blocks resume with a
  scoped reason and preserves the checkpoint.

## Test strategy

Use temporary stores and a controllable clock. Exercise concurrent mutation,
stale epoch, crash points, duplicate events, retry cap, and recovery after
process restart. Do not use a live tracker.
