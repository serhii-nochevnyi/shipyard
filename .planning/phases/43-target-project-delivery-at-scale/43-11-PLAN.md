## Goal

D-06 (REQ-164). The export looks up issues by the shipyard label and creates on no match, so an epic with existing issues would get about 28 duplicates; the operator disabled Jira and moved statuses by hand. Decompose proposes the ticket-to-issue mapping, the human approves it with the ticket set at Gate 2, a recorded key is authoritative (lookup by key, never create, refuse an unknown key), and issues without the shipyard label are only transitioned and commented. Status transitions stay the phase-29 projection.

## Scope

- `jira-export.cjs` `planExport`: when a ticket row has `jira` (matching `JIRA_KEY_RE`), emit a step with `lookup: [{kind: 'key', key}]`, `on_no_match: 'refuse'`, and `labelled_only_fields: ['summary', 'description']` plus `unlabelled: 'transition-and-comment-only'`; never a create action for that ticket. Tickets without a key keep today's label lookup and create.
- `resolveLookup`: `kind: 'key'` resolves by key; a missing issue returns `{action: 'refuse', reason: 'unknown key <K>'}`; an issue without the shipyard label returns `{action: 'transition-comment'}`; with the label, today's update.

  - A step that proposes the ticket → existing-issue mapping from the investigation's Jira input (keys named in `PROBLEM.md`/intake), and records each approved key with `jira-export.cjs record` (the existing `upsertJiraKey` path).
