<objective>Fix the cause of the phase 50 `CONTEXT_OVER_BOUND` refusal for full-mode integration reviews: stop reading every source blob of both endpoint trees when no baseline is being inherited, in the builder and in its consumer-side rebuild together.</objective>

## Goal

ADR-033 R-5 (D-05): integration-review version two stays, and its impact reading becomes lazy and must not read repository-sized material to run a full-mode review. Research `system-state.md` §6.3: `buildReviewImpactPacket` reads every `.cjs|.mjs|.js|.ts|.tsx|.jsx` blob at both the baseline (or merge-base) and the head (`codex-arch-review-context.cjs:2006-2027`), 449 files and 14.8 MB at the phase 50 head against `FILE_LIMITS.material` of 16 MiB, irrespective of what changed; on Claude the selection is always full (`codex-delivery-host.cjs:807-809`), so the import graph exists only to expand the affected set that a full review embeds anyway. The same logic is duplicated for consumption in `role-artifact.cjs:2856-3000+` (`rebuildReviewImpactPacket`), and the two must agree byte for byte. This ticket carries a merge checkpoint (`human_checkpoint: merge`, which the operator may pre-authorize at Gate 2) because the builder and its trust-path rebuild change together.

## Scope

When the baseline selection mode is `full` (no baseline, so no obligation is inherited), skip the import-graph construction: do not read unchanged blobs; `affected` is the changed set; read only the blobs of changed paths (new side for present paths, old side for removed paths) under the existing per-blob and total bounds; `boundaries` is empty and the dynamic, unresolved and external-package uncertainty that only mattered for expanding inheritance is not computed from unchanged sources; the cross-language check that uses only the inventory listing, the governing-change rule, the unsupported-extension rule, the current-required-source rule, the `selection.reason` limitation and the `complete-current-packet-required` limitation are kept. Incremental mode (a baseline exists) keeps today's import-graph reading and closure unchanged. Apply the identical change to `rebuildReviewImpactPacket` so builder and rebuild produce the same canonical lineage and digest.

Mirror disposition of the v2 endpoint inventory and the impact reads (fourth round). The endpoint inventory and change list of the impact packet (`endpointInventory` and `endpointChanges` in `codex-arch-review-context.cjs`, the duplicate in `role-artifact.cjs`) and the impact reads are not review diffs, and `review-diff-scope` (T-53-01) does not scope them: after T-53-01 a version two integrator's model-visible diff excludes `plugins/shipyard/` while its endpoint inventory still lists the changed mirror paths, on purpose. The inventory is the digest-bound lineage the host's result must echo (`validateIntegrationCoverage`) and the consumer rebuilds, so dropping mirror paths from it would change the canonical lineage digest of every version two verdict sealed before the change, which the rollback rule (no sealed artifact becomes invalid) forbids, and would hide a mirror change from the inventory a result has to account for; the reviewer sees the mirror only as inventory metadata, never as diff content, and the packet's `review_scope` still lists the changed mirror paths with blob ids. In the lazy full-mode reading the changed mirror JS blobs are read like any other changed path, so the cost is bounded by the size of the change, not of the repository, which is what the phase 50 refusal needed. The hybrid contract builds no impact packet at all (a hybrid review is fresh and inherits no baseline), so for hybrid reviews the mirror disposition is `review_scope` alone.

Already sealed verdicts. The consumer does not trust the recorded lineage: `authenticateCurrentCoverage` rebuilds it from git with `rebuildReviewImpactPacket` (`role-artifact.cjs:3388-3391`) and requires the rebuilt lineage and digest to equal the declared one (`:3393-3407`). A lazy-only rebuild would therefore refuse every Codex native-input full-mode verdict sealed under the eager rule, which ADR-033's rollback forbids ("no sealed artifact becomes invalid"). So a lineage built by the lazy rule carries one added optional field `impact_reading: "lazy-v1"` (the `shipyard.review-coverage-lineage.v1` schema string stays; a lineage sealed before this change has no such field), `buildReviewImpactPacket` and `rebuildReviewImpactPacket` take an `impactReading` option (`lazy` for a new full-mode build, `eager` for today's behaviour, never lazy in incremental mode), and the call at `:3391` passes the reading named by the declared coverage being verified: `lazy` when `coverage.impact_reading === "lazy-v1"`, otherwise `eager`, which is exactly today's code path. The eager rebuild reads both endpoint trees as before; it succeeded when the verdict was sealed (same fixed commits, same bound), so it succeeds again. A marker added to an eager lineage or removed from a lazy one changes the rebuilt lineage and is refused by the existing equality check. The Claude inline integrator verdict (`authenticateInlineCoverage`, `:3456-3487`) does not rebuild the impact packet at all, compares the recorded lineage with the current endpoint inventories, and is unaffected.

Pinned producer digests. `codex-arch-review-context.cjs` and `role-artifact.cjs` are two of the eleven files `focusedProducerFiles('claude')` pins into every focused Claude architecture packet and re-hashes at consumption (`role-artifact.cjs:3268-3276`), so this ticket, like every ticket of the phase that edits a pinned file, makes a retained focused Claude architecture verdict sealed before it fail with `focused producer source changed` until it is re-reviewed; the T-53-04 procedure covers that and is run once after the epic's last producer-file merge. The integration review is not producer-pinned at consumption (the finding recorded in T-53-04: `authenticateInlineCoverage` and the native host-files branch contain no producer-source loop, and the integrator's `preflightPins` are re-hashed from the current files at each launch), so this change does not invalidate an integration verdict by digest; its only effect on integration verdicts is the lineage rebuild above. No pin list changes. Neither edited file is a pin of the Codex integration lineage (that pins the agent file, `references/integrator.md`, `claude-role-host.cjs` and `phase-integrator-preflight.cjs`), but both are copied into the generated package and the Codex bundle (`bundle_digests`, `package-build.json`). This ticket edits no pin, digest, `plugins/shipyard/**` file or `tests/unit/runtime-file-digests.json` entry; the refresh is the epic rollout recorded by T-53-04, once after T-53-31 merges, only through `make package-shipyard-codex`, `make install-shipyard-codex` and `make doctor`.

## Acceptance criteria

- In a repository whose JS and TS sources exceed 16 MiB at both endpoints (generated in the test), a full-mode impact build succeeds and its `newly_reviewed` entries contain the required references and the changed sources only; the same repository refused before the change with `CONTEXT_OVER_BOUND`.
- A spy on `git cat-file blob` shows only changed blobs read in full mode.
- The packet from `buildReviewImpactPacket` and from `rebuildReviewImpactPacket` for the same input have the same digest; an incremental-mode build is byte-identical to its pre-change output on the existing fixtures.
- A governing-file or uncertain-closure change still forces `mode: "full"` with its limitation recorded; `impact.paths` of a full-mode packet equals the changed paths.
- Mirror disposition: in a repository whose change set includes `plugins/shipyard/` JS paths, a full-mode impact build (eager and lazy) lists those paths in the endpoint inventory and change list exactly as it did before T-53-01, and the lazy build reads only their changed blobs; the other half of the disposition, that the version two integrator's diff content has no mirror path while its `review_scope` lists them, is asserted by the T-53-01 packet cases and not repeated here, and the case here names that ticket in a comment so the intended difference between the two is a test, not an accident.
- For a lazily built packet `validateIntegrationCoverage` accepts a result echoing the lazy inventory and refuses one echoing an expanded inventory.
- Sealed-verdict compatibility: a full-mode lineage built with `impactReading: "eager"` (the code path that is today's behaviour, captured as a fixture before any change) and sealed through the existing Codex native-input fixtures is still accepted by `authenticateCurrentCoverage` after the change; a lazily built and sealed one is accepted; adding `impact_reading: "lazy-v1"` to the eager lineage or removing it from the lazy one is refused with `REVIEW_COVERAGE_INVALID`; an incremental-mode lineage never carries the marker.
- Pinned digests: `focusedProducerFiles('claude')` still returns the same eleven names in the same order (a test pins the list, so no pin is added or dropped by this phase's edits), and the refusal of a retained focused architecture verdict after a one-byte change to either edited file is the T-53-04 table row for that file, which this ticket does not repeat; the integration review's lack of a consumption-time producer pin is the code finding recorded in T-53-04 and is not re-asserted by a test here.
- All existing incremental and lineage tests pass.
