## Goal

The integrator and architecture-review roles run on the Claude and Codex hosts whatever the size of the diff. A size-routed hybrid (inline, pull, partitioned) delivers the change under review; a review-specific pathspec keeps the generated mirror and planning noise out of every review diff; a hybrid review contract records the route and the coverage ledger; the host proves coverage per route; the receipt, graph-directory and stderr defects are fixed; thresholds are configurable and stay conservative until measured.

## Decisions

Locked by ADR-033; `D-nn` is the same decision as `R-n` and the plans cite both.

- **D-01 (R-1) Shape:** size-routed hybrid with three routes — inline, pull, partitioned. The host chooses the route from the measured size of the work and records it in the contract and the evidence. A route that cannot close its proof escalates to the next route and never accepts a partial review.
- **D-02 (R-2) Inline route:** small epics embed the diff with fewer than 50 surrounding lines and the review-specific pathspec of D-06; coverage is proven by construction.
- **D-03 (R-3) Pull route:** the packet carries a host-built manifest of changed paths (status, blob ids, size, per-file diff hash, recipe) bound into the context digest; the reviewer pulls each file's diff. Proof is declarative: declared coverage inventory equals the manifest and `complete` implies empty limitations. The upper threshold is configurable.
- **D-04 (R-4) Partitioned route:** disjoint, directory-cohesive units sized to a per-session token budget; each unit an ordinary receipt-verified dispatch on the inline path; an aggregator judges the phase from plans, ADRs, the complete change inventory, per-unit verdict summaries and a seam inventory. Coverage is a set-cover over git data plus a ledger authority outside the worktree; a phase verdict is `passed` only when the ledger is complete and every unit is complete and passing; very large unit counts use a tree reduction.
- **D-05 (R-5) Contract:** a new hybrid contract version records the route and the ledger digest; the two legacy contract versions keep working; unknown versions remain a hard refusal. Integration-review `shipyard.integration-review.v2` stays and its impact reading becomes lazy and never reads repository-sized material in a full-mode review.
- **D-06 (R-6) Review diff pathspec:** `plugins/shipyard/` is excluded from every review diff of both roles on both runtimes by a review-specific pathspec applied at every diff site, never by editing `development-artifacts.cjs`; arch-review diffs also exclude `.planning/` except `.planning/architecture/**` and DECISIONS files. The packet carries mirror metadata (changed mirror paths with blob ids, no content); CI keeps proving mirror parity. A test pins that no review diff contains a mirror path.
- **D-07 (R-7) Routing signal:** the `inputTokens > 250000` signal counts the size of the work (diff plus required material), not the launch prompt; the rule is a note on ADR-014 and the grid is unchanged.
- **D-08 (R-8) Defects fixed in this phase:** the `receipt` authority-key refusal (the key scan stays intact and no key is renamed to pass it); a selectable graph directory for the role host that keeps the clean-tree guard; the child's stderr surfaced bounded and sanitized.
- **D-09 (R-9) Thresholds:** route thresholds and the unit budget are configurable and default to conservative values until measured; the first delivery tickets calibrate them.
- **D-10 (R-10) Verification obligations:** the measurements listed in ADR-033 R-10 are delivery work and come before the route code.

## Design choices made at decomposition (Claude's discretion inside ADR-033)

These resolve details the ADR leaves to decomposition. Plans cite them as "phase design".

- **Review-specific scope module.** One new module, `review-diff-scope.cjs`, owns the exclusion predicate, the changed-row parser, the diff, listing and mirror-metadata builders for every diff site. `development-artifacts.cjs` is not edited. Excluded rows are never silently dropped: the packet records `review_scope` with the mirror path list (path, status, old and new blob id, capped at 1000 entries with the omitted count and a digest of the complete list) and counts plus digests for excluded planning rows.
- **Which behaviour changes where.** The pathspec change applies to every contract version whose diff a host builds. The smaller context (`review_context_lines`, default 10) and the work-size routing signal apply only to the hybrid contract. The legacy contracts keep `--unified=50` and their prompt-size signal, so selecting them restores today's routing, context lines and signal (rollback) and the existing context pins keep passing. The review pathspec applies to the legacy contracts too, so a legacy review diff after this phase is not byte-identical to one built before it (the generated mirror and planning noise are gone from it); ADR-033's rollback line is read as "routing, context and signal", and the pathspec has no switch on purpose (D-06).
- **The Codex v1 caller diff.** A Codex `shipyard.integration-review.v1` caller supplies its own diff in the request (`deliver.md` legacy full-input compatibility); no host builds it, so the host cannot scope, verify or rewrite it, and **the review pathspec is explicitly not applied by the host on that path**. That caller never reaches a new route: `requestValue` refuses `review_min_route`, `review_unit` and `review_aggregate` unless the hybrid contract string is present (53-25), and the coordinator refuses a non-hybrid request (53-29). D-06 reaches the v1 caller by instruction only: 53-31 tells callers to build the diff with `node ${CLAUDE_PLUGIN_ROOT}/scripts/review-diff-scope.cjs diff --role integrator`, the command 53-01 ships. Selecting the hybrid contract, whose diff the host builds, is the way to a host-enforced pathspec on Codex.
- **Contract names.** Hybrid contract strings are `shipyard.integration-review.v3` and `shipyard.focused-architecture-review.v3`; one number across the two review families. Hybrid reviews are always fresh complete reviews: no baseline inheritance, which stays a `shipyard.integration-review.v2` mechanism.
- **Route authority.** The host measures and chooses the route; the caller cannot choose a lower one. A request may raise the floor with `review_min_route` (a monotonic hint, used by the coordinator to escalate). A hybrid request whose work needs the partitioned route is refused by a single-dispatch host with `REVIEW_PARTITION_REQUIRED` carrying the route record, because one host instance performs one launch.
- **Conservative defaults (until measured).** `review_inline_max_tokens` 150000, `review_pull_max_tokens` 150000 (the pull band is empty until calibrated, so everything above inline goes to the partitioned route), `review_unit_budget_tokens` 100000, `review_context_lines` 10 (allowed 1…49: D-02 says fewer than 50 surrounding lines, and 50 is the legacy context the hybrid contract replaces; 53-11 normalizes 50 or more to the default), `review_reduction_fanout` 8, `review_max_units` 64. A configured value above a default (or any change of the three non-token knobs) takes effect only when the shipped measurement record unlocks the knob (every informing item measured and operator-signed, see "Measurement gate"); the defaults themselves change only by a code change backed by such a record (ticket 53-11 pins both). ADR-033's rollback note ("selecting v1 or raising a threshold restores the previous behaviour") therefore holds unconditionally for selecting a legacy contract, and for raising a threshold only once the record unlocks it; this follows from R-9 ("conservative until measured") and changes none of R-1…R-10.
- **Work estimate.** `ceil(bytes / 4)` over the review diff at the configured context plus required material (plans, ADRs, selected backlog, metadata), the same estimator as `context-packet.cjs`. Whether it under-counts escaped diff text is a measurement obligation, not an assumption.
- **Unit definition.** Segments are the per-file diff split only when one file's diff alone exceeds a unit's capacity (at hunk boundaries, falling back to line boundaries); rows are grouped by directory (first two path segments, then deeper segments for a group that exceeds capacity) and packed next-fit in path order. Capacity is `review_unit_budget_tokens` minus the per-unit overhead (instructions, plans and ADRs embedded in every unit).
- **Seam rule.** A seam is a static relative `require`/`import` edge between two changed files that sit in different units, found by the same resolver rules as the impact builder; test-to-source imports are the common case. Dynamic dependency forms are counted per unit as uncertain. The seam inventory is bounded and says when it is truncated.
- **Ledger authority.** The ledger and its immutable plan live in the archive authority directory of the worktree (`archiveAuthorityDirectory`), which both children are already denied, under one new entry named `partition-runs`; records are HMAC-protected with the ledger's own key `partition-runs/ledger.key`. The names avoid every reserved name of `role-artifact.cjs` `protectedRecordsWithoutKey` (`catalogue.json`, `architecture-sources-*`, `phase-archive-roster-*`, `planning-containment-*`, `review-*`): a `review-*` entry created before the worktree's `hmac.key` would make the next role launch refuse. A missing ledger key is refused, never re-published. A ledger record binds unit id, attempt, dispatch id, receipt digest, artifact reference and digest, outcome and completeness. Units are reviewed sequentially so the single evidence file and one-launch-per-host rules hold.
- **Git mechanism for review diffs.** `git diff` has no `--pathspec-from-file` (usage error on the installed git 2.54) and `:(exclude)` cannot re-include `.planning/architecture/**`. The review scope classifies the rows of one `git diff --raw -z` and builds every diff and listing from the included paths as `:(literal)` argv entries, chunked by size with rename pairs kept together; with nothing excluded the plain command runs, and an empty path list never reaches git (it would select the whole diff). Tests run the real git for every command shape.
- **Review-part dispatch plumbing (ticket 53-18).** The dispatch boundary refuses a review-part architecture-review ticket on every kind today (and an integrator one when the repository path has whitespace; otherwise it would record it as a plain ticket), so 53-18 adds boundary subject kind `review-part` beside the subject family, plus the scratch evidence name `.shipyard-integration-part-evidence.md`. Integrator unit and reducer launches write that scratch file, the aggregate writes `.planning/phases/<phase>/INTEGRATION.md` (the file `gsd-sync` reads) as the last launch, and role-artifact sealing accepts the part name only for a review-part subject (53-19).
- **Clean worktree between launches.** Five independent sources of dirt are closed: tracked graph files (`--graph-dir`, 53-03), the integrator evidence file (part evidence name, 53-18, 53-19, 53-22, 53-26), the sealed archive directory (every hybrid request runs `canonicalWorktree` with the aggregate flag, 53-20; the Codex collector gives review-part the phase-binding archive allowance, 53-24) a failed aggregate's leftover phase evidence file from an earlier call (named refusal with the `role-artifact.cjs prepare` remedy, never deleted by the coordinator, 53-29) and, within one call, the phase evidence file of an escalated inline or pull integrator attempt (rotated by the coordinator through `prepareRoleArtifact`, 53-29; the host-level contract is pinned in 53-20 and 53-25). The coordinator's own checks (the check before and after every launch and the eligibility test for that rotation) call `statusIgnoringScratch(worktree, { untracked: 'all', forJudge: false })`, the call every hybrid request makes through the aggregate flag; the function's default `forJudge: true` counts the sealed archive directory `.shipyard-role-artifacts/<digest>/` as dirt and no `.gitignore` entry hides it, so under the default the second launch of every run and every rotation would be refused. The accepted scratch is exactly the `SCRATCH_FILES` and untracked entries under that directory, and nothing else (a tracked graph file or a leftover phase evidence file still refuses and is named; the archive directory is never named in the error, deleted or rotated). The fake hosts of 53-29 and 53-30, and the host cases of 53-19 and 53-22, leave the directory a real seal leaves and run the real status call, so a dropped option fails a test.
- **Codex transport.** A hybrid Codex integrator packet is carried by the inline transport only. The host-file reader path runs through capacity measurement and completed-source restoration that are v2-only (`codex-runtime-host.cjs:3455`, `codex-arch-review-context.cjs:643`), so a hybrid packet over the 1 MiB inline limit is refused with `REVIEW_ROUTE_UNAVAILABLE` and blocker `transport-limit`, which `nextRoute` accepts and the coordinator escalates on. The Codex architecture review keeps its focused relay for hybrid contexts (no reader transport), which needs `codex-runtime-host.cjs:2631` to accept the hybrid string.
- **Codex request path.** Every Codex review request passes `requestValue` (`codex-delivery-host.cjs:95-129`) before `prepare` or `prepareIntegratorInput` runs, and today it refuses `context.review_contract` for every role but the integrator and for every string but the two legacy ones. So each Codex ticket that admits a new contract string or selector also extends `requestValue`, per role and in the same ticket: 53-23 admits the hybrid architecture string and `review_min_route` for `arch-review`; 53-24 adds `review_unit` and `review_aggregate` for it; 53-25 admits the hybrid integrator string and `review_min_route` for `integrator`; 53-26 adds `review_unit` and `review_aggregate` for it. A selector without the hybrid string of its own role, a hybrid string for the other role, a legacy string with a hybrid selector and an unknown string are each refused with `INVALID_INPUT`, tested through the exported `validateArgs` (which calls `requestValue`) and through the adapter requests of 53-29.
- **Sealed verdicts and the lazy impact reading.** A lazily built lineage carries `impact_reading: "lazy-v1"`; one built before has no such field. The consumer rebuilds by the reading the declared coverage names (eager when none), so no sealed verdict becomes invalid, and a forged marker fails the equality check (53-28).
- **Measurement gate (mechanical, in code and in the record).** A merge checkpoint can be pre-authorized by the operator at Gate 2 (decompose Step 4.3, recorded per ticket; plans never set `preauthorized`) and then stops waiting for a person, so no merge approval can be the gate, whether or not the operator pre-authorizes. Each record item may carry an operator `signoff` entry (`operator`, `signed_at`, `note` and `item_sha256`, the digest of the item's content when it was signed), written only by `review-measure.cjs signoff`, which executors and tests never run against the shipped record; editing a measured item after it was signed makes its entry stale. Each threshold lists the record items that inform it. The router's `thresholdsFrom` (53-11) reads the record at run time and honours a configured value above its conservative default only when every informing item is `measured` **and** carries a current operator sign-off; a configured value below the default is always honoured for the three token knobs (tightening is safe); any other deviation returns the conservative default, names the blocking items and records the source of every threshold in the route record. A missing, unreadable or invalid record locks every knob. So the thresholds stay conservative until the record carries an operator-signed entry for each informing obligation, whatever merges. CI never needs a live account or an operator action: tests build their records in memory or on scratch copies; the shipped record is checked for structure (`validate`, `validate --final`) and for the state-conditional lock, never for being signed; probes need `--live` and `SHIPYARD_REVIEW_MEASURE_LIVE=1`, which the isolated runner removes and which every probe case also keeps out by passing an explicit `env` (the guard accepts the variable because `run.sh` does not unset it); and `validate --signed` is an operator command, not a test dependency. 53-10 keeps its merge checkpoint and the Operator checkpoint runbook section as the place the operator measures and signs, but it is not the gate, pre-authorized or not. Calibration (53-11) only proposes values, per knob.
- **Risk labels (second round).** Anything that edits `role-artifact.cjs`, `dispatch-boundary.cjs`, `context-packet.cjs` or the sealing and validation path is at least `medium`; it is `high` where the ticket creates or changes code that admits or authenticates authority, or decides the proof level a review gets. A `high` ticket needs a checkpoint at Gate 2 (`review` or `merge` both satisfy it); every checkpoint of this phase is `human_checkpoint: merge`, so the operator can pre-authorize it ticket by ticket at Gate 2 exactly as phase 50 did, and the labels themselves are unchanged by that choice. `high` (16 tickets, each with a one-line reason): 53-02 (the receipt boundary of a model packet), 53-11 (the router and the threshold gate decide the proof level), 53-15 (new authority store), 53-16 (extends the ledger ceiling), 53-17 (contract allow-lists and result validators), 53-18 (dispatch boundary admission), 53-19 (sealing and validation), 53-20, 53-21 and 53-22 (Claude host admission of hybrid, pull, unit and aggregate requests and results), 53-23, 53-24, 53-25 and 53-26 (their Codex counterparts, including the `requestValue` admission), 53-27 (consumers), 53-28 (builder and consumer rebuild). `medium` (11 tickets): 53-01 and 53-05 (what the reviewer is shown), 53-03 (a host input channel, re-verified by the consumers), 53-06 (the launcher failure path), 53-07 (the record validator and the sign-off predicate the router reads), 53-09, 53-10 (probes and the human measurement gate, with a merge checkpoint), 53-13 and 53-14 (pure producers re-verified by the ledger and the consumers), 53-29 (orchestration that returns only ledger-verified results, re-derived by 53-27) and 53-31 (reference text whose digests are pinned, and `deliver.md`). `low` (4 tickets): 53-04 (a test and a document, no production edit), 53-08, 53-12 and 53-30.
- **Threat severity rule (third round).** The severity in a ticket's threat register is that ticket's own exposure: what goes wrong if this ticket's code or test is wrong. Where a producer's defect would be caught by an authenticating ticket, the authenticating ticket carries the high or critical threat and the producer cross-references it. So a threat is not rated above its ticket's risk (a ticket risk has no critical level, so `critical` is compared as `high`), with five disclosed exceptions: three medium tickets that carry a high threat, 53-03 (T-53-36, a graph directory pointing at a forged graph, re-verified by the consumers; disclosed in its text), 53-07 (T-53-89, the sign-off predicate the router reads; disclosed in its text) and 53-10 (T-53-90, the owed live measurements, with a merge checkpoint), and two low tickets that carry medium threats because their subject is a proof, not production code, 53-04 (T-53-37 and T-53-101: the protection of retained verdicts and the rollout it documents) and 53-30 (T-53-86 and T-53-96: the end-to-end proof of the phase's claims). The third round re-homed the rest: T-53-51 (53-14) is medium and points at the ledger (T-53-55, critical) and the consumers (T-53-78, critical), T-53-83 and T-53-85 (53-29) are medium and point at the hosts (T-53-69, T-53-74), the consumers and the ledger runtime binding (T-53-104, high, 53-15), and T-53-96 (53-30) is medium and points at the router's gate (T-53-98, high, 53-11). New threats of this round: T-53-104 (53-15, high), T-53-105 (53-29, medium) and T-53-106 (53-17, high).
- **Reduction.** Groups of at most `review_reduction_fanout` consecutive units become reducer nodes (ordinary dispatches over summaries); levels repeat until the aggregator input fits; depth is bounded.
- **Subject grammar.** Unit and reducer dispatches use a new `review-part` subject kind that cannot satisfy the phase integrator or architecture-review subject patterns, so a unit verdict can never be read as the PR-level verdict.
- **Coverage proof (third round).** The set-cover over git data is proven by one function, `review-partition.verifyCoverage`, whose review rows and segment reader are mandatory inputs and which has no mode that skips them (53-14). The ledger owns the production source of those inputs, `review-ledger.gitCoverageSource`, which recomputes the review rows and the segment bytes from git at the ledger identity's base and head and the plan's `context_lines`, never from the plan; `verifyLedger` and `ledgerVerdictCeiling` refuse to run without it, and the hybrid result validator accepts only the frozen verification result as its ledger input (53-15, 53-17). The production callers each build the input at their own call and each has an omitted-row case in which a plan that omits one changed row is refused: the aggregate preparation of each runtime and role (53-22 Claude, 53-24 Codex architecture review, 53-26 Codex integrator through the shared preparation), the consumers for Claude-sealed and Codex-sealed artifacts (53-27), the coordinator before any launch, on resume and at its final check (53-29), and the end-to-end acceptance (53-30).
- **Unit packet proof (fourth round).** The set-cover proves that every changed row sits in exactly one unit and that git's bytes for each segment equal the plan's; it does not by itself prove the unit's reviewer was shown those bytes. So each counted unit's packet is checked at verification time too. `review-partition.unitEmbeddedDigest` (53-14) is the one definition of the digest of the bytes a unit packet embeds (the unit's segments concatenated in plan order, no separator); the hosts build a unit packet's diff content as exactly that concatenation (53-22 Claude, 53-24 Codex architecture review, 53-26 Codex integrator through the shared preparation). `verifyLedger` (53-15) calls `rereadArtifact(record)`, which returns `{ artifact_digest, packet_digest, unit: { id, plan_digest }, embedded_sha256 }` read from the unit's sealed artifact and its authenticated original packet, never from the ledger record or the model's result, and compares it with the record, the plan's unit and `unitEmbeddedDigest` over bytes `gitCoverageSource` read from git; a difference is `unit-packet-mismatch` naming the unit and the field, a missing digest is `unit-packet-unproven`, never skipped. The callback is each runtime's `unitArtifactReader(options)` (exported by `claude-role-host.cjs`, `codex-arch-review-context.cjs` and `codex-delivery-host.cjs`), used by each aggregate preparation before launch, by the consumers for Claude-sealed and Codex-sealed artifacts (53-27) and by the coordinator's final check through `hosts.rereadArtifact` (53-29). A record that points at another unit's, or another plan's, genuine artifact therefore fails at every one of those callers. What stays outside every route's claim, as in ADR-033, is that the model read what it was shown.
- **Default contract per review step (fourth round; a Gate 2 confirm item).** `deliver-dispatch.cjs` is edited by no plan, so the architecture-review request it builds carries no `review_contract`, and the integrator call of `deliver.md` names `shipyard.integration-review.v2` itself. The plans therefore keep the legacy contract as the default of each step and make the hybrid opt-in per step, a selection of the step rather than of the builder, stated in `deliver.md` by 53-31: the integrator step keeps its v2 call (baseline inheritance, a v2-only mechanism, stays available) and the architecture-review step keeps the built request with no contract string; the step uses the hybrid contract through the coordinator when the epic input it already measures (`bytes ÷ 4`) is above `review_inline_max_tokens` (default 150000) or when the operator names it. That measure counts the legacy 50-line context and the generated mirror, so it is never smaller than the hybrid's work estimate: it can send a borderline epic to the hybrid's inline route and never the reverse. The request that reaches `runReview` is the built request plus the hybrid string (Claude: a top-level `review_contract`; Codex: `context.review_contract`, with `scope` and `graph_dir` taken from the same builder output), as 53-29 "Request shape" defines. Residual: an epic at or below the threshold by that measure is reviewed as today on the legacy contract; making the hybrid the default for every epic is a change of the step text (and, for the architecture review, optionally of the builder) that this phase does not make; the operator confirms the rule at Gate 2.
- **Mirror disposition of the v2 endpoint inventory and the impact reads (fourth round).** `review-diff-scope` scopes diffs, listings and change inventories of the review packets; it does not scope the v2 impact packet's endpoint inventory and change list (`endpointInventory`, `endpointChanges` and their duplicate in `role-artifact.cjs`) or its blob reads. After 53-01 a v2 integrator's diff excludes `plugins/shipyard/` while its endpoint inventory still lists the changed mirror paths, on purpose: the inventory is the digest-bound lineage the host's result must echo and the consumer rebuilds, so dropping the mirror from it would change the lineage digest of every v2 verdict sealed before the phase (the rollback rule forbids that) and would hide a mirror change from the inventory a result must account for. The packet's `review_scope` still lists the mirror paths with blob ids; the lazy full-mode reading of 53-28 reads the changed mirror blobs like any changed path, bounded by the change; a hybrid review builds no impact packet. 53-28 states this and asserts the inventory half in a test.

The integrator is not producer-pinned at consumption (a code finding read, not executed).
- **Joins wait for merges.** A join ticket receives its second parent's work only through the epic, so it waits for that merge (see Graph notes); with Gate 2 pre-authorization the guard does the merging, without it a person does. The join 53-20 [53-19, 53-03] waits for nothing in practice, because 53-03 merges long before 53-19.
