## Scope

- Default contract per review step (fourth round; recorded in CONTEXT as a Gate 2 confirm item). `deliver-dispatch.cjs` is not edited by this phase and appears in no plan's `files_modified`, so the request it builds for the architecture review carries no `review_contract`, and the integrator call of `deliver.md` names `shipyard.integration-review.v2` itself. The prose therefore states, for each step, which contract is used by default and how the hybrid is reached: the integrator step keeps `shipyard.integration-review.v2` through its existing library call (its text and pins unchanged, baseline inheritance kept) and the architecture-review step keeps the request `deliver-dispatch.cjs build arch-review` builds, with no contract string (the legacy path, unchanged); the hybrid contract is selected by the step, not by the builder, when the epic input the step already measures (`bytes ÷ 4`, the figure both steps record) is above `review_inline_max_tokens` (default 150000; read through `pipeline-config`) or when the operator names the hybrid contract; at or below that size the existing call stays, so a small epic never loses baseline inheritance. That measure counts the legacy 50-line context and the generated mirror, so it is never smaller than the hybrid's own work estimate: it can send a borderline epic to the hybrid's inline route, never the reverse. The request that reaches the coordinator is the built request itself plus the hybrid field (the shape T-53-29 defines under "Request shape": Claude, the built `shipyard.claude-role-request.v1` object with a top-level `review_contract` set to `shipyard.integration-review.v3` or `shipyard.focused-architecture-review.v3`; Codex, the built launch object with the same string in `context.review_contract`, `scope` and `graph_dir` taken from the same builder output), so no builder flag is needed. The prose does not promise more: an epic at or below the threshold by that measure is reviewed on the legacy contract as today, which is why the hybrid is described as the route for large epics and as the way to a host-enforced pathspec, and a deployment that wants the hybrid for every epic changes the step text, a follow-up not made here.
- `deliver.md`: in the integrator and architecture-review steps, for review on the hybrid contract show the coordinator call on both runtimes (`runReview` with `claudeHosts` or `codexHosts`, the built request with `review_contract` of the hybrid string added as above), say the host measures and records the route (inline, pull, partitioned), that the operator never selects a lower route, that the legacy contract strings remain the rollback (selecting one restores today's routing, context lines and routing signal for any epic, whatever the thresholds or the record say; the review pathspec of D-06 still applies to every contract a host builds a diff for, so a legacy review diff no longer carries the generated mirror or planning noise and is not byte-identical to one built before the phase, and the prose says so), that lowering `review_inline_max_tokens` always sends more epics to the pull or partitioned route while raising a threshold above its default takes effect only for a knob the shipped record has unlocked, that repeated role launches use `--graph-dir` (or the `graphDir` option) when the graph files are tracked, and that a failed child launch prints its terminal reason and a sanitized stderr excerpt; for the legacy full-input path (the Codex v1 caller that supplies its own `diff`) say to build the diff with `node ${CLAUDE_PLUGIN_ROOT}/scripts/review-diff-scope.cjs diff --role integrator --base <rev> --head <rev>`, that the host neither applies the review pathspec to a caller-supplied diff nor verifies it, that such a caller cannot select a route, and that the hybrid contract, whose diff the host builds, is the way to a host-enforced pathspec. Keep every sentence the existing pins require.
- `integrator.md` and `arch-review.md`: add the hybrid contract section: result fields `review_contract`, `review_route`, `route_record_digest`, `review_completeness`, `limitations`, `unresolved_sources`, `coverage_inventory` (pull), `review_unit` echo (unit), `ledger_digest` (aggregate); that a unit reviewer judges only its unit and uses the seam list for cross-unit concerns; that the aggregate judges from plans, ADRs, the change inventory, unit summaries and seams and cannot exceed the ledger ceiling; that pull coverage is declared and not proven; that the mirror is excluded and its changed paths are listed with blob ids; that a review that did not cover everything cannot pass; that an integrator unit or reducer writes its evidence to `.shipyard-integration-part-evidence.md` while the aggregate writes `.planning/phases/<phase>/INTEGRATION.md`.

Operator facts to state in `deliver.md` and the pipeline document, each only as far as the scripts implement it: a Codex hybrid packet that does not fit the 1 MiB inline transport is refused with `REVIEW_ROUTE_UNAVAILABLE` and `transport-limit` and the coordinator escalates (a unit that hits it needs a lower `review_unit_budget_tokens`); a failed aggregate that leaves `.planning/phases/<phase>/INTEGRATION.md` in an earlier call must have it rotated with `node ${CLAUDE_PLUGIN_ROOT}/scripts/role-artifact.cjs prepare --worktree <worktree> --role integrator --phase <phase>` before the rerun, which resumes from the ledger, while within one call the coordinator rotates that file itself between an incomplete inline or pull integrator attempt and its escalation; a ledger run belongs to one runtime and one role and is never opened by the other runtime; a partitioned review exists for a phase subject only, so a ticket-level architecture review whose work needs it is refused with `REVIEW_PARTITION_UNSUPPORTED` and is reviewed on the legacy focused contract or split; the R-10 measurements that need live accounts are owed until the operator runs them and signs each item (`review-measure.cjs show --gate` shows which knobs are unlocked, `signoff --item` signs an item, `validate --signed` checks that every item carries a current entry), and a configured threshold above its default takes effect only for a knob whose informing items are all measured and signed, so the thresholds stay at their conservative defaults until then whatever merges and whether or not a live account is ever used; the in-flight pull request procedure (`docs/audits/phase53/in-flight-pr-procedure.md`) and the pin and digest rollout it records (`make package-shipyard-codex`, `make install-shipyard-codex`, `make doctor`; no pin, mirror or digest edited by hand) are run once after the epic's last pinned-content merge, which is this ticket.
