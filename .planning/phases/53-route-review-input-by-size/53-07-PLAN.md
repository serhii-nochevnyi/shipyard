## Goal

ADR-033 R-9 and R-10 (D-09, D-10): measurements come before the route code, thresholds stay conservative until measured, and "the first delivery tickets calibrate them". Live measurements need accounts and tools a hermetic worktree does not have, so the deliverable is a record where every obligation is either evidence with its command, an owed live run with its exact command and owner, or a stated limitation. A merge checkpoint can be pre-authorized by the operator at Gate 2 (decompose Step 4.3, never by a plan), after which no person sees that merge, so the gate that keeps thresholds conservative cannot be a merge approval whether or not the operator pre-authorizes: it is a signed entry in the record that the code reads. This ticket depends on T-53-04 because it runs the T-53-04 test to fill `producer-pin-invalidation` and names the T-53-04 procedure document in `in-flight-procedure`, which must exist. The phase 50 precedent is `docs/audits/phase50/launch-upgrade-verification.md` with a test that each L-11 item has evidence or a recorded limitation.

## Scope

New `review-measure.cjs` with a CLI: `validate [--record <path>] [--final] [--signed]` (exit 0 or 1, lists problems; `--signed` implies `--final`), `show`, and `signoff --operator <name> --item <id,id,...|all> [--note <text>] [--record <path>]`; and library exports `validateRecord(record, { runtime })`, `CONSERVATIVE_DEFAULTS`, `itemDigest(item)`, `loadRecord(path)` and `knobGate(record)`. The CLI default `--record` is `plugins/delivery-pipeline/references/review-routing-measurements.json`, resolved from the script's own directory so it works in the checkout, the installed Claude plugin and the Codex bundle. Record schema `shipyard.review-measurements.v1` with `items` and `thresholds`. Item ids: `window.claude-sonnet-5-5`, `window.claude-opus-5-5`, `window.gpt-6.1-sol`, `estimator-undercount`, `claude-compaction`, `claude-tool-result-bodies`, `claude-outside-worktree-read`, `claude-linked-worktree-git-diff`, `codex-batch-reader-2.6mb`, `partition-sizes-phase50`, `phase50-integrator-model-effort`, `codex-integrator-sandbox`, `producer-pin-invalidation`, `in-flight-procedure` (fourteen). Each item: `id`, `decision` ("R-10"), `obligation` (text from the ADR), `status`, `owner`, an optional `signoff`, and by status: `measured` needs `command`, `executed_at` (ISO), `source_revision` (40 hex) and a non-empty `observed` object; `owed` needs `command`, `owner` and `reason`; `limitation` needs `reason`; `documented` needs `document` naming an existing file (checked against the repository root in the CLI, not in run-time mode, see below); `tooling-pending` needs `tooling_ticket`, is refused by `validate --final` and cannot be signed. Thresholds: `review_inline_max_tokens` 150000, `review_pull_max_tokens` 150000, `review_unit_budget_tokens` 100000, `review_context_lines` 10, `review_reduction_fanout` 8, `review_max_units` 64, each `{ value, basis, informed_by, evidence }` with basis `conservative-unmeasured` or `measured`. `informed_by` lists the record items whose answer the knob depends on: for `review_inline_max_tokens` the three window items, `estimator-undercount` and `codex-batch-reader-2.6mb`; for `review_pull_max_tokens` those five plus `claude-compaction`, `claude-tool-result-bodies`, `claude-outside-worktree-read` and `claude-linked-worktree-git-diff`; for `review_unit_budget_tokens` the three window items, `estimator-undercount` and `partition-sizes-phase50`; for `review_context_lines`, `review_reduction_fanout` and `review_max_units`, `partition-sizes-phase50`.

Sign-off entry. An item may carry `signoff: { operator, signed_at, note, item_sha256 }`. `itemDigest(item)` is the sha256 of the canonical JSON (keys sorted at every depth, no whitespace) of the item without its `signoff` field, so the entry binds the operator's acceptance to the exact content signed: editing a measured item afterwards (an ingest `--record`, a corrected value, a changed status) makes the entry stale. `validateRecord` checks the shape of a present entry (`operator` non-empty text of at most 128 characters without control characters, `signed_at` ISO, `item_sha256` 64 hex) and refuses an entry on a `tooling-pending` item; it does not require entries. A sign-off is an attestation recorded in a tracked file and reviewed in a commit, not a cryptographic signature, and the plan does not claim more.

The threshold rule: basis `measured` requires every `informed_by` item to be `measured` with a current sign-off (`signoff.item_sha256 === itemDigest(item)`) and `evidence` to list them; any other state of any informing item (owed, tooling-pending, limitation, documented, unsigned, stale) forces basis `conservative-unmeasured`, an empty `evidence` list and `value` equal to the conservative default held in the exported constant `CONSERVATIVE_DEFAULTS` of the validator (T-53-11 pins that constant to `pipeline-config` `DEFAULTS`).

Run-time predicate. `validateRecord(record, { runtime: true })` performs no filesystem access (an installed plugin has no repository root, so a `documented` item's file is not looked up). `loadRecord(path)` reads and parses a record, returning `{ state: 'absent' | 'invalid' | 'loaded', record?, problems? }` and never throwing. `knobGate(record)` returns, for each of the six knobs, `{ unlocked, blocked_by }`: it first runs `validateRecord(record, { runtime: true })` and, if the record is not valid, locks every knob with `blocked_by: [{ item: 'record', reason: 'record-invalid' }]`; otherwise a knob is unlocked only when every item in its `informed_by` list is `measured` with a current sign-off, and each other informing item appears in `blocked_by` as `{ item, reason }` with reason `owed`, `limitation`, `documented`, `tooling-pending`, `unsigned` or `stale-signoff`. T-53-11 calls it on every threshold resolution.

Operator commands. `validate --signed` runs the `--final` checks and additionally requires that every item carries a sign-off entry whose `item_sha256` equals `itemDigest(item)`, naming each missing or stale item; an owed, limitation or documented item may be signed (the operator accepting that status) but only a measured item signed and current unlocks a knob. `signoff` writes, for each listed item (or every item that is not `tooling-pending` for `all`), an entry with the given operator, the current ISO time, the note and the current digest, and changes no other field; it refuses an unknown id, a `tooling-pending` item and an empty operator, and writes nothing if any listed item is refused. Sign-off is an operator act at the T-53-10 checkpoint: executors and tests never run the command against the shipped record (tests run it only on scratch copies). The record's `thresholds` describe the defaults the code ships (`pipeline-config` `DEFAULTS`, pinned equal by T-53-11), not an operator's configuration: an operator who wants calibrated values writes them into `.planning/config.json` from the `calibrate` proposal, and the router honours them only while `knobGate` unlocks the knob; changing the shipped defaults is a code change that needs the record's informing items measured and signed first.

Usage. `review-measure.cjs --help` (or `-h`) prints a `usage:` block to stdout and exits 0; no arguments, an unknown subcommand or an unknown option print it to stderr and exit 2 without touching any record. The block is generated from the one exported table that registers subcommands and their options, so T-53-08, T-53-09 and T-53-10 add theirs by registering them and each appears in the usage with no second edit; T-53-31's documentation test checks the prose against this output.

Observed keys. The calibration of T-53-11 reads two shapes from the record, so the validator pins them here and the tooling of T-53-09 and T-53-10 writes them: a `measured` `window.claude-sonnet-5-5`, `window.claude-opus-5-5` or `window.gpt-6.1-sol` item must carry `observed.usable_input_tokens`, a positive integer, the largest input in estimator tokens (`ceil(bytes/4)`) the child accepted without a refusal or a compaction; a `measured` `estimator-undercount` item must carry `observed.ratio`, a positive number, observed input tokens divided by estimated tokens. Other observed content stays free-form but non-empty; an `owed` item is not asked for them. This keeps T-53-11 independent of the tooling tickets: its in-memory records use these keys, and a measured window item that lacks them is refused by `validateRecord`, so a probe that wrote a different key could not unlock a knob.

Initial statuses: `producer-pin-invalidation` measured (run the T-53-04 test during this ticket and record its result), `in-flight-procedure` documented, `partition-sizes-phase50` tooling-pending T-53-08, the Claude items and `estimator-undercount` and the Claude window items tooling-pending T-53-09, the Codex items, `phase50-integrator-model-effort` and `gpt-6.1-sol` window tooling-pending T-53-10. No item carries a sign-off in the shipped record at the commit of this ticket. The markdown file explains the statuses, lists each item with its obligation and what evidence closes it, and has a "Runbook" heading that later tickets fill.

## Acceptance criteria

- The shipped record validates; `validate --final` fails while any item is tooling-pending and names each; the shipped record carries no sign-off and the suite does not require one.
- A measured item missing its command, a malformed date or revision, an empty observed object, an owed item without a command or owner, a documented item naming a missing file, an unknown status, a duplicate id and a missing R-10 id are each refused with a message naming the item.
- A threshold with basis measured citing an owed or limitation item is refused, and so is one whose cited items are all measured but one is unsigned or carries a stale sign-off, and one whose cited items are all measured and signed but whose `informed_by` list still contains an owed, tooling-pending or limitation item; at the commit of this ticket the shipped thresholds all carry basis conservative-unmeasured, an empty evidence list and values equal to `CONSERVATIVE_DEFAULTS`, and from then on the validator (run by a test on the shipped file) enforces the rule instead of a test that hard-codes today's statuses, so an operator who later measures and signs items and flips a threshold lawfully does not break the suite; a conservative-unmeasured threshold with a changed value is refused.
- Sign-off: `itemDigest` is stable under key order and changes when any field other than `signoff` changes; `validate --signed` refuses a record in which any item has no entry, an entry whose digest is stale (a measured item edited after it was signed), an empty operator or a malformed time, and accepts an in-memory record in which every item, including owed, limitation and documented ones, carries a current entry; `signoff` on a scratch copy signs the listed items with the current digest and changes nothing else, `--item all` signs every item that is not tooling-pending, and it refuses an unknown id, a tooling-pending item and an empty operator, writing nothing on a refusal.
- `knobGate` table, on in-memory records: all informing items measured and signed gives an unlocked knob; one unsigned item locks it naming the item with reason `unsigned`; a stale entry gives `stale-signoff`; an owed item gives `owed`; an invalid record locks every knob with `record-invalid`; a record with the three window items, the estimator item and the reader item measured and signed but `claude-tool-result-bodies` owed unlocks `review_inline_max_tokens` and blocks `review_pull_max_tokens`; on the shipped file the test computes the expected unlock set independently from the record (a knob is unlocked exactly when every informing item is measured with a current entry), so measuring and signing later cannot break the suite.
- `validateRecord(record, { runtime: true })` accepts a record whose documented item names a file that does not exist and performs no filesystem access (asserted by running it with `fs` reads made to throw); without the option the same record is refused. `loadRecord` returns `absent` for a missing path and `invalid` for malformed JSON, never throwing.
- `producer-pin-invalidation` carries the command that ran the T-53-04 test file `tests/unit/review-routing-pin-invalidation.test.cjs` whole (`node tests/unit/helpers/isolated-environment.cjs tests/unit/review-routing-pin-invalidation.test.cjs`), the source revision it ran at and the refusal counts taken from that run's two diagnostic lines, `review-routing producer-pin result:` (the Claude table) and `review-routing codex-pin result:` (the Codex installed-script table); no other item carries an observed number.
- Usage: `review-measure.cjs --help` exits 0 and its stdout names `validate`, `show`, `signoff` and each of `--record`, `--final`, `--signed`, `--operator`, `--item` and `--note`; no arguments, an unknown subcommand and an unknown option exit 2 with the block on stderr and leave a scratch record byte-identical; a subcommand added to the exported registration table (a test adds a dummy one) appears in the output without another edit.
- Observed keys: a measured window item without a positive integer `observed.usable_input_tokens` and a measured `estimator-undercount` item without a positive `observed.ratio` are each refused naming the item and the key; an owed item is not refused for lacking them.
- No test of this ticket requires the shipped record to be measured or signed, and none starts a live probe.
