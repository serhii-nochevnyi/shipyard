## Goal

`front.cjs` gains an ordering responsibility on top of classification (D4):
inside every actionable bucket, tickets are ordered by descendant count in the
DAG (unblocking power) first, so an unattended run takes the item that keeps the
most work available at 04:00 — with expected CI length as a late tiebreak.
Unattended, the ORDER decides how much of the graph is still open by morning.

## Scope

**`front.cjs`:**
- `descendants(id)`: number of transitive dependents of `id` among NOT-merged
  tickets, derived from `tickets[*].depends_on`. Build a children index once
  per `computeFront` call; count each descendant once (diamond-safe); exclude
  merged tickets (a merged descendant needs no unblocking). Cycle-tolerant
  (the graph is validated acyclic by Gate 2, but the front must not hang on a
  corrupt file).
- New sort inside every actionable bucket:
  `leftBehind ASC, descendants DESC, depth ASC, ciEstimate DESC, id ASC`.
  Descendants-descending preserves parent-before-child within a stack (a
  parent's descendant set strictly contains its unmerged child's), so the
  existing "drive the parents first" behavior is kept, and across stacks the
  widest unblocker wins. Left-behind-last is untouched and stays the FIRST key.
- `ciEstimates(graphDir, tickets)`, exported: reads `delivery-log.jsonl`
  `status_change` events; for each ticket that reached `merged`, duration =
  ts(first `to:'merged'`) − ts(first `to:'pr-open'`); group by the ticket's
  repo (`tickets[id].repo || null` for this repo); per-repo MEDIAN seconds.
  Estimate for a pending ticket = its repo's median; missing journal or no
  merged samples → 0 for everyone and the term falls through to `id`. This is
  a deliberate PROXY (PR lifetime, not pure CI wall time — CI wall time is not
  journalled); name it as such in the comment. Longer-first: starting the
  slowest pipeline earliest is what overlaps its wait with the rest of the
  front.
- `computeFront` takes the estimates as `opts.ci_estimates` ({ticket:
  seconds}); it must NOT read the filesystem itself (it is a pure function over
  its inputs — keep it that way).
- The CLI section calls `ciEstimates` and passes `ci_estimates`, exactly as it
  already mirrors `--parked`/drift/escalations.

**`state-sync.cjs`:** pass `ci_estimates: ciEstimates(GRAPH_DIR, tickets)` in
its `computeFront` options (one import extension + one field at line ~489). No
other state-sync behavior changes; in particular do NOT add any per-PR `gh`
field (the 41s-vs-7s lesson) — the estimate reads only the local journal.

## Acceptance criteria

- Within a bucket, a root ticket with 5 transitive unmerged dependents sorts
  before a root with 1, regardless of id order.
- A diamond (A ← B, A ← C, B ← D, C ← D) counts D once for A (descendants(A)
  = 3, not 4).
- Parent still sorts before its own stacked child; left-behind tickets still
  sort last and `left_behind_count` is unchanged.
- With equal descendants and depth, the ticket whose repo has the larger
  journal-derived median lands first; with no journal data the order falls back
  to id and nothing throws.
- `front.cjs` CLI and `state-sync.cjs` produce the SAME ordering for the same
  graph (both pass `ci_estimates`).
- `computeFront` still performs no filesystem access (grep the function body
  for `require('fs')` usage stays outside it).
- `delivery-front.json` and `formatFront` output remain shape-compatible (no
  consumer change needed in stop-gate.cjs or deliver.md).
