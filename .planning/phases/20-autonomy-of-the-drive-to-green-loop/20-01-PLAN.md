## Goal

One deterministic script, `failure-signature.cjs`, that (a) turns a CI failure log
into a normalized SIGNATURE (error class + test/job id + file, hashed), (b) reads
the ticket's signature history from the journal and returns the repair VERDICT,
and (c) owns the flake quarantine bookkeeping — so the repair policy can tell
progress from repetition from instability, mechanically (D1, D3). This is the
mechanism ticket; the loop wiring that calls it is T-20-06.

## Scope

New script `plugins/delivery-pipeline/scripts/failure-signature.cjs` with four
subcommands. Graph resolution for all of them: `--graph <dir>` accepted in ANY
position (same spelling and stripping as `drift-record.cjs`, including the
`GRAPH_FLAG_AT === -1` guard), `SHIPYARD_GRAPH_DIR` env, else
`<cwd>/.planning/graph`; when not explicit and `tickets.json` is absent, refuse
loudly with a message naming the cause and the fix (model on drift-record's).

**`compute [--log <file>] [--job <name>] [--json]`** — stdin when `--log` is
absent. Normalizes the log before extraction: strip ANSI escapes, ISO/locale
timestamps, durations (`12.3s`, `(345 ms)`), line:column suffixes, hex
addresses, and absolute path prefixes down to repo-relative. Extract:
- `error_class` — first match of common failure tokens (`\b[A-Z]\w*(Error|Exception|Failure)\b`,
  `AssertionError`, `--- FAIL:`, `not ok`, `FAILED`, non-zero exit-code lines);
  fallback `unknown`.
- `test_id` — the failing test/job identifier (jest/vitest `✕`/`FAIL <name>`,
  go `--- FAIL: <TestName>`, TAP `not ok N <name>`); fallback: the `--job` value.
- `file` — first repo-relative path token with a source/test extension in the
  failure block; fallback empty string.
- `signature` = first 16 hex chars of sha256 over
  `error_class + "\n" + test_id + "\n" + file`.
The command NEVER exits non-zero on an unparseable log — a degraded signature
(`unknown` + job name) is better than an aborted babysit round (the same ethos
as state-sync treating `gh pr checks` exit codes as data). `--json` prints
`{signature, error_class, test_id, file}`; bare mode prints the signature.

**`verdict <ticket> --signature <sig> --head <sha> [--k <n>] [--json]`** — reads
`delivery-log.jsonl` events for the ticket: `attempt` events carrying a
`signature` key, plus `flake`, `flake_rerun`, `flake_lift` events. Returns ONE
verdict from the pinned enum — `first | progress | repeat | flake_candidate |
flake | plan_defect` — by these rules, in this order:
1. A `flake` event exists for (ticket, signature) with no later `flake_lift`
   for the same pair → `flake` (quarantined: do not dispatch, do not charge).
2. The most recent prior `attempt` event with this signature carries the SAME
   `head`, and no `flake_rerun` event with `outcome=red` for (signature, head)
   was journalled after it → `flake_candidate` (the tree did not change between
   failures; the loop must re-run the job once before dispatching anything).
   A red `flake_rerun` record flips this to deterministic — fall through.
3. Distinct signatures observed (prior signatures plus the current one) >= k
   → `plan_defect` (K distinct with no progress; T-20-03 owns the marking).
4. No prior attempt event carries a signature → `first`.
5. Current signature equals the most recent prior one → `repeat` (change
   STRATEGY, hold the tier — the policy consequence lives in T-20-02).
6. Otherwise → `progress` (the signature changed; hold the tier, continue).
`--k` defaults to **3** (the same default T-20-02 declares as
`pipeline.plan_defect_signatures`; the loop passes the config value in
T-20-06). `--json` prints `{verdict, signature, head, distinct, k, seen}`.

**`rerun <ticket> --signature <sig> --head <sha> --outcome green|red [--job <name>]`**
— records the outcome of the one-shot re-run the loop performed on a
`flake_candidate`. `green` → journals a `flake` event
(`{ts, event:'flake', ticket, signature, head, job, by:'failure-signature'}`) —
this IS the quarantine, one act; `red` → journals a `flake_rerun` event
(`{ts, event:'flake_rerun', ticket, signature, head, outcome:'red',
by:'failure-signature'}`) so the next `verdict` reads the failure as
deterministic (`repeat`) instead of looping on `flake_candidate` forever.

**`lift <ticket> --signature <sig>`** — journals a `flake_lift` event; the next
`verdict` stops returning `flake` for that pair. This is the exit for a
quarantined signature that turns persistent (fails on re-run at a new head).

Journal appends happen under `withLock(lockDirFor(<project>), 'failure-signature', …)`
with the lock beside the graph (drift-record's rule: a lock taken at a worktree
cwd serializes nothing). The quarantine has NO store file of its own — the
journal is the record (D2's "no new subsystem" rule applied one decision over).

## Acceptance criteria

- The verdict enum is exactly `first | progress | repeat | flake_candidate |
  flake | plan_defect` — these literal strings, no others.
- Two logs of the same failure differing only in timestamps, ANSI codes,
  durations, and line numbers produce the SAME signature; a different failing
  test produces a different one.
- `compute` exits 0 on garbage input and yields a degraded (`unknown`-class)
  signature.
- Verdict sequences behave: fresh ticket → `first`; new signature after a push
  → `progress`; same signature after a push → `repeat`; k distinct signatures
  (default 3) → `plan_defect`; same signature at the same head → `flake_candidate`;
  after `rerun --outcome green` → `flake`; after `rerun --outcome red` →
  `repeat` (no infinite candidate loop); after `lift` → quarantine no longer
  reported.
- Quarantine is scoped to (ticket, signature) and survives a head change (a
  flaky test is flaky across pushes) until `lift`.
- Without `--graph`/`SHIPYARD_GRAPH_DIR` and with no `tickets.json` at the cwd
  graph dir, every subcommand that touches the journal refuses with a message
  naming `--graph <project>/.planning/graph`.
- `--graph` works in any argument position and is never swallowed into another
  value.
