## Goal

The main loop dispatches at most as many agents at once as the run can afford,
and the front says how many that is. A wave wider than the cap is cut, not
refused: the remainder is taken on the next round.

## Context (Reads)

- ADR-005 D11. It lives in phase 26 rather than 25 for a mechanical reason
  worth stating: `front.cjs` and `pipeline-config.cjs` are owned to the end of
  phase 26's chain, and a cross-phase contest over a file cannot cascade. The
  SUBJECT belongs with the model policy; the FILES do not, and Gate 2 is right
  that the files decide. The measurement that made this a ticket rather than a
  deferred note: on 2026-09-07 a run held nine `opus`/`xhigh` executors and a `fable`
  guard in flight and hit a per-session spend limit. Six agents died mid-ticket,
  five tickets lost their commits, and the recovery took a re-dispatch round
  with the predecessors' uncommitted tests handed forward. Priced on the same
  session's volumes, the whole ladder question is worth about $26 across
  thirteen tickets while the concurrency question is worth the entire run.
- **No choice of tier addresses this.** The policy is per dispatch and the limit
  is per session, so the missing axis is how many dispatches are open at once —
  the one thing `pipeline-config.cjs` does not model.
- GSD 1.13 added `dispatch.maxConcurrency` for its own wave parallelism. The
  conveyor never calls `execute-phase` (see `CLAUDE.md`'s executor-isolation
  boundary), so that key is not ours to read — but the SHAPE is the one to
  borrow, and naming ours the same way is how a reader connects them.
- `deliver.md` Step 3 fans out over every ready ticket in one Workflow call, and
  Step 4 posts a guard beside it. Nothing counts. The cap therefore has to be
  applied where the wave is BUILT, and the front is what the loop reads to build
  it — so the front is where the number belongs, not a rule in prose.
- `front.cjs` already orders the actionable buckets by unblocking power and
  stack depth (ADR-001 D4). A cap is a truncation of that order, which is why it
  must live beside it: the first N of a good order is still a good order.
- The guard counts against the cap. It is an agent, it holds tickets, and this
  session's failure included one. `front.sentinel.dispatched` already names the
  guard's share.

## Scope

- `pipeline.max_concurrent_agents` (default 4 — the largest wave this repository
  has completed without an interruption; say so in the comment, and that it is a
  measurement rather than a round number), declared in `capability.json` so it
  is GSD-settable, read through `pipeline-config.cjs` like every other knob.
- `computeFront` reports `capacity: { max, in_flight, free }` where `in_flight`
  counts live dispatch records of every role and `free` is what a wave may take
  now. The actionable ORDER is unchanged; the cap does not reorder anything.
- `formatFront` prints one line when the cap binds: `capacity: 4 agents, 4 in
  flight — 3 actionable item(s) wait for the next round`, so a reader is never
  puzzled by a non-empty front with nothing dispatched.
- **`fixpoint` must not read a capped front as finished.** A front with
  actionable items and no free capacity is `fixpoint: NO`, with a reason that
  says the run is waiting on capacity rather than on work. The stop gate reads
  the same file, so the gate keeps blocking, which is correct: the round is not
  over.
- `deliver.md` Step 3: build the wave from `front.capacity.free`, take the
  remainder next round, and never dispatch past the cap even when the front
  lists more. One sentence, in the step that fans out.

## Out of scope

Any per-role or per-model weighting of the cap (a `fable` guard and a `haiku`
judge are not one unit of cost, but weighting needs a cost model the conveyor
does not have). Rate-limit backoff and retry. The stop gate.

## Acceptance criteria

- `computeFront` on a board with 7 actionable and 0 dispatched, cap 4, reports
  `capacity: {max: 4, in_flight: 0, free: 4}` and leaves all 7 in `actionable`
  with the order unchanged.
- Same board with 4 live dispatch records → `free: 0`, `fixpoint: NO`, and the
  reason names capacity rather than work. Today there is no capacity field at
  all, so the test fails on current code.
- A cap of 0 or a malformed value warns and falls back to the default rather
  than stalling the run.
- `formatFront` prints the capacity line only when the cap binds.
- `deliver.md` contains the literal `front.capacity.free`.

## Test strategy

TDD in `front.test.cjs`: the capacity arithmetic first, then the fixpoint case,
which is the one that matters — a capped front that reported `YES` would end a
run mid-phase, the exact defect class phase 24 exists to remove.
