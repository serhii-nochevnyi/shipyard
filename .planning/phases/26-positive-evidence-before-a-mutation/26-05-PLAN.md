## Goal

`release()` removes a lock only if the owner file still names this holder;
takeover of a stale lock is atomic; and `state-sync` re-reads the previous
snapshot INSIDE its write lock and refuses to publish observations older than
the ones on disk — so a slower sync cannot roll the board back.

## Context (Reads)

- ADR-004 D5 (audit F12 reproduced: A acquires, TTL expires, B acquires, A's
  `release()` removes B's lock, C acquires while B holds; F13 by source).
- `lock.cjs` ~98–120: `release()` → `breakLock(lockPath)` unconditionally;
  takeover = `breakLock` then `continue` (two steps, not atomic — two waiters
  can both break and both create).
- `state-sync.cjs`: previous state, timestamps and every GitHub observation are
  gathered BEFORE `withLock` (~149); the locked section (~490–510) only appends
  transitions and writes. The main loop and the guard both run it; the one that
  started earlier and finished later wins with older facts.
- T-22-04 ("a lock is held from the instant it exists") is the previous fix in
  this file — read its test to keep its property.
- Cross-phase parent chain: T-26-03 → T-24-11 own `state-sync.cjs` before this.

## Scope

- `lock.cjs`: `owner.json` carries a random token; `release()` re-reads it and
  removes only on a token match (a mismatch is logged, not thrown); stale
  takeover renames the stale directory aside (`<lock>.stale-<ts>`) and then
  creates — `rename` is the atomic step; a loser of the race sees `EEXIST` and
  retries.
- `state-sync.cjs`: `observed_at` (start of the gh reads) is written into the
  state file; inside the lock, re-read the file on disk and, if its
  `observed_at` is newer than ours, EXIT 0 without writing, printing
  `state-sync: a newer snapshot (…) landed while this one was reading — kept
  the newer one`. The front/yaml/state triple is written in one locked section
  (already) and now with one `generation` counter.

## Out of scope

Readers taking the lock (front.cjs, stop-gate — the latter has a time budget).

## Acceptance criteria

- lock.test: A, expire, B, `A.release()` → B's lock still present, C's acquire
  blocks/times out while B holds. Today C acquires — fails on current code.
- Two concurrent takeovers of one stale lock → exactly one holder.
- Smoke: run state-sync twice with an injected `observed_at` older on the
  second run → the file keeps the first run's `generation`; the second exits 0
  with the message.
- All existing lock and T-22-04 cases pass.
