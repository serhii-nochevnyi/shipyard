## Goal

Whether a ticket needs a drift check is computed, not judged: `drift-needed.cjs`
answers yes or no by comparing the plan's last change against what has landed in
**the ticket's own base**, which in epic-stacked delivery is the epic, not the
integration branch.

## Context (Reads)

- Measured over one full session, 2026-09-07, delivering three phases:
  **17 drift scans, 17 verdicts of `fresh`, zero `drifted`.** The gate never once
  did the job it exists for, and it cost 1.24M subagent tokens, 21% of the
  session's entire agent spend, at about 73k per scan.
- The numbers say something sharper than "it ran too often". **13 of the 17
  produced no reuse candidate at all. All 16 candidates came from the 4 scans
  run against the EPIC** — the ones that deviated from Step 2's written
  condition, made after sibling tickets had squash-landed under the plan.
- `deliver.md` line ~742 states the condition: *"whose plan is older than the
  last merge into the configured base — `git.base_branch` when set, the repo
  default otherwise, the same ref the epic is cut from — or if more than 2 days
  have passed"*. On the measured day `origin/main` took **zero merges and zero
  commits touching code**, and every plan was written that day. By the letter,
  the correct number of scans was zero; the useful ones were the four the rule
  does not describe.
- The rule names the wrong ref for this integration mode. In `epic-stacked` the
  thing that moves under a plan is the ticket's own base — the epic for a root,
  the parent's branch for a cascade child — and it moves once per sibling. The
  integration branch may not move for weeks, which is exactly why the condition
  reads as never-fires.
- It is also PROSE, which is the class of rule this repository has repeatedly
  measured itself skipping (`CLAUDE.md`: prose rules get skipped, mechanical
  gates hold). Seventeen decisions were made by judgement and seventeen were
  wrong in one direction or the other.
- `state-sync.cjs` already computes each ticket's `base`; `graph-dir.cjs`
  resolves the graph from a worktree. Both are the inputs this needs.

## Scope

- New `drift-needed.cjs <ticket> [--graph <dir>] [--json]`: exit 0 with
  `{needed: true|false, reason, base, plan_mtime, base_moved_at}`. Needed when
  the ticket's resolved base has commits touching `files_modified`'s directories
  since the plan file's last commit, OR the plan is older than
  `pipeline.drift_max_age_days` (default 2). Not needed otherwise, and the
  reason says which test decided.
- The comparison is against `origin/<base>` (the base lives on origin — the
  lesson `graph-dir.cjs resolveBaseRef` already records), and a base that cannot
  be resolved answers `needed: true` with that reason: unknown is not clean.
- **`deliver.md` is deliberately NOT in scope, and that is what lets this ship
  now.** Every ticket that owns that file is in flight or blocked behind an
  epic, so wiring the prose in would put this behind fifteen waves — and the
  saving is wanted in the session that measured it, not next week. The SCRIPT is
  the mechanism; the loop calls it by hand until a ticket that owns `deliver.md`
  replaces the prose condition with the command. Say so in the script's header,
  so a reader who greps `deliver.md` and finds the old condition knows which one
  is authoritative.

## Out of scope

The reuse-candidate side of drift-check (T-26-14 addresses the fact that the
value the session actually got was reuse candidates, not verdicts). The judge's
own prompt.

## Acceptance criteria

- A plan committed after everything in its base → `needed: false`, reason names
  the base and that nothing landed since.
- One sibling commit in the base touching a declared directory after the plan's
  commit → `needed: true`.
- A plan 3 days old with a quiet base → `needed: true` by age; at 1 day, false.
- An unresolvable base → `needed: true`, reason names the failure.
- Replaying the measured session's shape (plans written today, `main` quiet,
  epic taking one commit per sibling) yields 4 needed and 13 not. That is the
  regression: it encodes the measurement, not an opinion.
- The script's header names `deliver.md` Step 2 as the prose it supersedes and
  the ticket that will wire it, so the two are not silently in disagreement.
