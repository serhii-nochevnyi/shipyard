## Goal

`state-sync.cjs` writes `delivery-front.json` with the dispatch overlay applied,
so a resync while agents hold tickets does not turn the board back into
`execute: …, finalize: …` until the next `dispatch-record.cjs mark` happens to
rewrite it.

## Context (Reads)

- ADR-002 D1/D2 and phase 23's REQ-13 ("a ticket handed to an agent is
  VISIBLE as dispatched").
- Measured on 2026-09-07, first wave of this phase: four tickets marked
  dispatched (three with the guard, one with an executor); `state-sync.cjs`
  then wrote a front with `actionable_count: 4`, `waiting.dispatched: []`, no
  `dispatches_applied_at`. Re-running `dispatch-record.cjs mark` on one ticket
  restored `actionable_count: 0` and all four under `waiting.dispatched`. The
  stop gate reads that file, so between the resync and the next mark it blocks
  over work that is in flight — the false block T-23-01 was written to remove.
  Counted over the delivery of this phase on 2026-09-07: the gate blocked THREE
  times on this cause in one session, each time after a background guard ran
  `state-sync` while six to ten tickets were with agents, and each time the
  overlay had to be reapplied by hand with `dispatch-record.cjs mark`. The
  guards sync on their own schedule, so the window is not avoidable by
  sequencing — only by this fix.
- **The sibling failure mode, observed 2026-09-07 while delivering this very
  phase**: `dispatch-record.cjs mark` DOES refresh the front, and its last line
  says which of the two happened (`the front reports it as waiting` versus `no
  board was refreshed just now … the next state-sync will apply it`). An
  operator redirecting that stdout to `/dev/null` in a `for` loop loses the one
  report that distinguishes them, and the stop gate then blocks over work that
  is in flight. Twice, in one session. The script is not at fault; the message
  exists precisely for this. Do not add a flag or a retry: this ticket's fix
  (state-sync applying the overlay itself) removes the window where the
  distinction matters at all, which is the better answer than a louder message.
- `front.cjs` CLI (line ~690) passes `dispatched: activeDispatches(root, state)`
  into `computeFront`. `dispatch-record.cjs refreshFront` does the same under
  the `state` lock and stamps `dispatches_applied_at`. `state-sync.cjs`
  (`computeFront(... ci_estimates: …)` near line ~480) passes no `dispatched`
  option at all — three writers of one file, one of them blind to the overlay.
- `activeDispatches` is exported from `dispatch-record.cjs`; `state-sync.cjs`
  already imports from sibling scripts (`front.cjs`, `pipeline-config.cjs`),
  so this is one require and one option.
- `tests/smoke/sentinel-smoke.sh` runs `state-sync.cjs` against a stubbed `gh`
  and asserts on the printed board — the natural place to prove the overlay
  survives a resync.

- **The same sync flattens the parks** (external audit 2026-09-07, F28):
  `state-sync.cjs` line ~488 calls `activeEscalations` — the flat string view
  — where `front.cjs` and `dispatch-record.cjs` call `activeParks`, the
  kind-aware record. A `plan_defect` park therefore reaches the board through
  state-sync with the ESCALATION lifetime sentence ("lifts when the PR moves"),
  which is false for a park bound to the plan hash. `escalation-record.cjs`
  lines ~97–115 explain exactly this trap and say the bare string must not be
  rendered; state-sync is the one caller that still does.

## Scope

- `state-sync.cjs`: pass `parked: activeParks(ROOT, state)` (the kind-aware
  record) instead of the flattened `activeEscalations`, so `escalationWhy`
  renders each park with the rule that actually expires it.
- `state-sync.cjs`: pass `dispatched: activeDispatches(ROOT, state)` to
  `computeFront`, stamp `dispatches_applied_at` the way `refreshFront` does,
  and print `dispatched: …` on the board line as `formatFront` already knows
  how to.
- `sentinel-smoke.sh`: one case — write a `dispatches.json` record for a
  ticket the fixture would otherwise list as actionable, run `state-sync`, and
  assert the board says `dispatched: <T>` and `front: 0 actionable`.

## Out of scope

`front.cjs`, `dispatch-record.cjs`, `stop-gate.cjs`. The fingerprint that lifts
a dispatch (T-24-08).

## Acceptance criteria

- With a live dispatch record for `T-01-01` in the smoke fixture, `state-sync`
  prints `waiting: dispatched: T-01-01` and `front: 0 actionable now`; the
  written `delivery-front.json` has `dispatches_applied_at` set and
  `waiting.dispatched` containing the ticket. Today the front lists it as
  actionable; the test fails on current code.
- Without a dispatch record the board is unchanged.
- An expired record (older than the TTL) does not suppress anything.
- A `mark-plan-defect` park in the smoke fixture is described on the board
  with the plan-hash lifetime ("lifts when the plan is re-planned"), not the
  PR-movement one. Today state-sync prints the wrong sentence; the test fails
  on current code.

## Test strategy

The smoke is the test: it already drives `state-sync` end to end with a stubbed
`gh`. Add the dispatch case next to the existing board assertions; drive the
expiry case by writing a record with an old `at`.
