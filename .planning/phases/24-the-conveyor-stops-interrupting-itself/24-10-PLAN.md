## Goal

`ci-wait.cjs` escalates a ticket only when ITS pipeline has not moved: a `gh`
failure is not an empty window, a settle clears only the settled ticket's
record, and the window is sized from the observed CI length when the front
carries one.

## Context (Reads)

- ADR-002 D9; `CLAUDE.md`'s `ci-wait.cjs` paragraph — the termination argument
  (three empty windows → escalation → the CI bucket empties) must keep holding
  after every change here.
- **A9, three defects in one loop:**
  1. Lines ~266–274: a window is EMPTY when `escalation-record.fingerprint`
     is unchanged. When `gh` is unreachable (rate limit, outage, expired
     token) every poll returns the same "nothing", every watched ticket's
     counter climbs together, and after 3 windows the waiter escalates the
     WHOLE board — each park then needs a human to lift. An outage is not a
     stall; a poll that failed must not increment anything, and the waiter
     should say `gh unreachable` and return 0 (the loop retries; the stop
     gate keeps the session).
  2. Line ~262: on the first settle, `delete store.tickets[w.id]` runs for EVERY
     watched ticket — the record of a ticket that has NOT moved for two
     windows is wiped because a neighbour finished. Clear only the settled
     ticket.
  3. `TIMEOUT_S` (line 97) default 15 min × `MAX_EMPTY` 3 = 45 min to
     escalation, regardless of the repo. The front carries `ci_estimates`
     (`front.cjs`, a per-repo median of PR lifetime — a proxy, documented as
     such). When present, the window defaults to a fraction of it (say the
     estimate / 3, clamped between the current 15 min and 60 min) so a repo
     whose CI takes 40 minutes is not escalated after 45.
- `ci-wait.cjs` exit codes are part of the loop contract (`0` returned/timeout,
  `3` refused, `waited:false` under `--json`); do not add a code — add fields
  (`outage: true`, `window_s`).
- T-24-03 is the parent because it changed the waiter's watch set
  (`waiting.parent`); this ticket must keep that set intact.
- Check classification is `check-state.cjs` (T-24-02) — do not reintroduce a
  list.

## Scope

- Distinguish poll outcomes: `settled` / `moved` / `unchanged` / `error`. Only
  `unchanged` counts as empty. `error` on every ticket for the whole window →
  return 0 with `outage: true` and no store change.
- Per-ticket record lifecycle: clear on settle for that ticket only; reset on
  any real change (unchanged rule).
- Window sizing from `front.ci_estimates[repo]` when present; explicit
  `--timeout` and `SHIPYARD_CI_WAIT_TIMEOUT_S` still win. Print the window and
  where it came from.

## Out of scope

The escalation itself (`escalation-record.cjs mark`, unchanged call). The
front's estimate (T-24-03/`front.cjs`). The stop gate.

## Acceptance criteria

- Stubbed `gh` failing for the whole window → exit 0, `outage: true`,
  `ci-waits.json` unchanged. Today the empties increment; the test fails on
  current code.
- Two watched tickets, A settles, B unchanged for two windows → B's record
  survives A's settle (`empties: 2`). Today it is deleted.
- Front with `ci_estimates: { 'o/r': 2400 }` (40 min) → chosen window ≥ 15 min
  and derived from the estimate; `--timeout 600` overrides it.
- Existing termination test (three empties → escalation → CI bucket empties)
  still passes.
