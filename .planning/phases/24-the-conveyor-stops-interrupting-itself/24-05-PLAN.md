## Goal

Four facts the merge path decided from cache or from absence now come from live
GitHub or from an explicit setting: a PR with NO reported checks is not green
but `merge_human`; the squash pins the head that was verified; the stack a
child may land into is the PHASE's stack; children are retargeted from live PR
data, not from the last sync.

## Context (Reads)

- ADR-002 D6. `CLAUDE.md` on `sentinel.cjs` ("`merge` re-verifies everything
  against LIVE GitHub") — this ticket closes the four places where that
  sentence was not yet true.
- **Б3** `front.cjs` line ~218: `none_reported` counts as green, so a PR whose
  repo has no CI (or whose CI never registered) reaches `merge` and lands with
  no test having run. `state-sync.cjs` prints a warning about exactly this
  (line 591) — a warning nobody reads at 3am. The honest bucket is
  `waiting.merge_human`, unless the project SAYS it has no CI:
  `delivery_pipeline.merge_without_ci: true` (declare it in `capability.json`
  so it is GSD-settable; read it through `pipeline-config.cjs` so `pipeline.*`
  and `delivery_pipeline.*` resolve the same way as every other knob).
- **Б5** `sentinel.cjs mergeOne` runs `gh pr merge --squash` with no
  `--match-head-commit`. Every gate above it was checked against a head that a
  concurrent push can replace between the check and the merge. `gh` has the
  flag for this race; the head is already in hand after T-24-04.
- **allowed set** `sentinel.cjs` line 486: `allowed = new Set([s.epic, t.epic,
  ...sameRepoTicketBranches])` — every ticket branch in the repository, from
  every phase. A child whose `pr_base` was hand-edited to another phase's
  branch would be merged there. The set must be this ticket's phase: the epic
  plus the branches of tickets sharing `t.phase` and `t.repo`.
- **retarget** after a merge, `mergeOne` retargets the children whose PR data it
  finds in cached `state`. A child whose PR opened after the last sync is not
  retargeted, goes DIRTY on the next sync, and waits for a person. Query the
  children's open PRs live (`gh pr list --head <branch> --repo …`, one call per
  child — this is the merge path, not the tick).
- **behindBy is broken cross-repo and fails permissively** (external audit
  2026-09-07, F06). `sentinel.cjs` line ~120 runs `gh api
  repos/{owner}/{repo}/compare/… --repo <o/n>`: `gh api` does not accept
  `--repo`, and the `{owner}/{repo}` placeholders resolve from the CURRENT
  repository, never from the ticket's. The call errors, `behindBy` returns
  `null`, and the gate treats `null` as "not behind" — the stale-base check is
  silently absent for every foreign-repo ticket. Use the repo-qualified
  endpoint (`repos/<owner>/<name>/compare/<head>...<base>`, the form
  `state-sync.cjs apiBase()` already builds), and make an UNKNOWN answer a
  refusal ("base freshness unproven — gh compare failed: …"), never a pass.
- Risk is HIGH because this changes what auto-merges and where; the checkpoint
  is deliberate. Pre-authorization at decomposition is the intended way to run
  it unattended.

## Scope

- `front.cjs`: `none_reported && !mergeWithoutCi` → `waiting.merge_human` with a
  `why` that says "no CI checks reported — confirm the repo has no CI
  (`merge_without_ci`) or wait for checks to register". With the setting true,
  current behaviour.
- `pipeline-config.cjs`: `merge_without_ci` (default `false`), declared in
  `capability.json` under the capability's config schema beside the existing
  knobs; test the precedence like the others.
- `sentinel.cjs mergeOne`: refuse `none_reported` unless `merge_without_ci`;
  `--match-head-commit <headRefOid>` from the live view; `allowed` restricted
  to the ticket's phase and repo; children discovered live for retargeting,
  falling back to cached state when `gh` fails (and saying so).
- `sentinel duty` mirrors the front: `none_reported` is not `merge`/`undraft`.
- `behindBy(base, head, repo)`: repo-qualified endpoint, no `--repo`; `null`
  (error/unparseable) → the merge REFUSES with the gh error in the reason.

## Out of scope

Reviewer semantics (T-24-06). The epic → integration PR (never auto-merged,
unchanged). CI classification (T-24-02).

## Acceptance criteria

- State with `checks.none_reported: true`, conform trailer, no threads:
  `computeFront` → `waiting.merge_human`, `sentinel merge` refuses with a reason
  naming `merge_without_ci`. Today both merge; the test fails on current code.
- Same with `merge_without_ci: true` → `merge` (unchanged path).
- The stubbed `gh pr merge` call in the sentinel test receives
  `--match-head-commit <sha>` equal to the live `headRefOid`.
- A ticket whose `pr_base` is a ticket branch of ANOTHER phase in the same repo
  is refused as outside the stack; a same-phase parent branch is accepted.
- A child whose PR exists only in the stubbed live `gh pr list` (absent from
  cached state) is retargeted after its parent merges.
- A foreign-repo ticket's merge drives `gh api repos/<owner>/<name>/compare/…`
  with NO `--repo` flag (assert on the stubbed argv); a stub that errors on the
  compare call makes the merge refuse naming "base freshness unproven". Today
  the same fixture merges; the test fails on current code.
- `make test-sentinel` (the end-to-end stubbed-gh smoke) passes with the stub
  extended to answer the new live queries.
