## Goal

A guard's dispatch expires when the guard's OUTPUT exists, a human's park
expires when a HUMAN's fields change, and neither is lifted by a CI check
finishing. The one shared hash that lifted both on every tick is retired from
the two stores that were wrong to use it — and kept, unchanged, for the one
consumer (`ci-wait.cjs`) whose subject really is the CI tallies.

## Context (Reads)

- ADR-002 D1.
- `escalation-record.cjs` `fingerprint(s)` (lines ~137–146) hashes `status,
  draft, review_decision, pr, checks.failing, checks.pending, checks.total,
  branch`. Three stores expire against it:
  - `dispatch-record.cjs` line 48 imports it: a sentinel dispatch (`fix`,
    `finalize`, `merge`) is "done" the moment ANY check finishes — long before
    the fixer has pushed. The front re-offers the PR, the stop gate blocks on
    it, and a second fixer can be dispatched at the same PR. (A1)
  - `escalation-record.cjs activeParks` lifts an `escalation` on the same
    hash: a parent merging retargets the child → CI re-runs → `pending` changes
    → the human's park lifts → review-fix/arch-review are re-dispatched at a PR
    a person was asked to judge, with the reason gone. (A8)
  - `ci-wait.cjs` counts EMPTY windows against it — there a tally change IS the
    event being waited for. Correct; must not change (T-24-10 refines the
    waiter separately, and depends on this hash staying stable).
- `dispatch-record.cjs` `activeDispatches(cwd, state)` (line ~190) and its TTL
  (90 min) — the TTL stays as the second trigger.
- Roles: `pipeline-config.cjs` `ROLES`; `front.cjs` names which roles are the
  guard's (`SENTINEL_ROLES`) and which the main loop's (`execute`, `publish`).
- What "the owner's output" is, per role:
  - executor (`execute`/`publish`): a branch appeared or a PR opened —
    `status`, `pr`, `branch`.
  - fixer (`ci-fix`, `review-fix`): a NEW HEAD (`head_sha` — after T-24-04 the
    state carries it; until then the fixer's push is visible as `status`/`pr`
    only, so include `head_sha` when present and fall back gracefully).
  - `arch-review`/`finalize`: the trailer (`gate`) or `draft` changed.
  - `merge`: `status` changed (to `merged`) or `pr_base` of children moved.
  A single per-role field list expresses all of this; the tallies appear in
  none of them.
- What a HUMAN moves on a parked PR: `review_decision`, `draft`, `head_sha`,
  `status` (closed/merged). Not `checks.*`, not `pr_base` (the conveyor moves
  that).
- `tests/unit/record-stores.test.cjs` covers the shared `--graph` parsing of
  the stores — keep it green; the flag contract is untouched.

## Scope

- `escalation-record.cjs`: keep `fingerprint` exactly as is (exported, for
  `ci-wait.cjs`); add `parkFingerprint(s)` over the human-moved fields and use
  it in `activeParks` for `kind: escalation`; the stored record carries which
  fingerprint kind it was bound to so an old record (bound to the full hash)
  is compared with the full hash until it lifts — no store migration.
- `dispatch-record.cjs`: `dispatchFingerprint(role, s)` — per-role field lists
  as above; `mark` stores the role's fingerprint; `activeDispatches` compares
  with the same role's function. Sentinel roles never include `checks.*`.
- `dispatchWhy`/`escalationWhy` name the fact that WILL lift the record ("lifts
  when the PR's head moves or after 90m", "lifts when a review decision, draft
  state or head changes") — the human should not have to guess.

## Out of scope

`ci-wait.cjs` (T-24-10). `front.cjs` (reads `activeDispatches`/`activeParks`
unchanged). Escalation `kind: plan_defect` (bound to the plan hash — correct).

## Acceptance criteria

- A `review-fix` dispatch marked on a PR with `checks.pending: 3`; state moves
  to `pending: 2` → dispatch STILL active. Today it lifts; the test fails on
  current code. Then `head_sha` changes → lifted.
- An `execute` dispatch on a `pending` ticket: state → `branched` → lifted
  (unchanged behaviour).
- An `escalation` park; state `checks.total` 17 → 34 (re-run after retarget) →
  park STILL active. `review_decision` `null` → `APPROVED` → lifted. Today the
  first case lifts; the test fails on current code.
- An escalation record written by the previous release (no fingerprint kind)
  is compared with the full hash and lifts exactly as before.
- `escalation-record.fingerprint` output for a fixed state is byte-identical to
  before (pin a hash in the test — `ci-wait.cjs`'s store depends on it).

## Test strategy
