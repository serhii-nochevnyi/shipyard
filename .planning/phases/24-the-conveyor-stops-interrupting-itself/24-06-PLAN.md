## Goal

Three duty answers that today send a fixer at something it cannot fix, or send
nobody at something the front says is actionable, become answers a fixer can
act on: `CHANGES_REQUESTED` with no unresolved thread is a person's; review
feedback is the state since the last push, one verdict per reviewer; a
DIRTY/BEHIND base is a `base-merge` duty with a workflow flag.

## Context (Reads)

- ADR-002 D4 (base-merge as a duty) and D7 (current review state).
- **A10** `sentinel.cjs` lines 339–341: `review_decision === 'CHANGES_REQUESTED'`
  → `review-fix`, regardless of thread count. A reviewer who requested changes
  in a summary comment (or a bot whose threads were all resolved but whose
  review verdict stands) leaves ZERO threads, so review-fix returns having
  done nothing, the signature repeats, and the ticket escalates after the
  budget. `review-fix.md` even says this state is "a fact for the orchestrator"
  — i.e. nobody's. The owner is a human: `waiting.human`, with a `why` that
  says "CHANGES_REQUESTED stands with no unresolved thread — a reviewer must
  re-review or dismiss". Both `sentinel duty` AND `front.cjs` (line 291 "review
  not settled") must route it the same way, like `checkpointParent`.
- **Б4** `reviewers.cjs`: `feedback` returns `.slice(-MAX_ITEMS)` of a bot's
  issue comments over the PR's whole life (line 322) — a fixer on round 4 reads
  rounds 1–3's already-addressed comments as live; `changes_requested` (line
  343) is `some(v => v.state === 'CHANGES_REQUESTED')` over EVERY historical
  review, so a reviewer who later approved still reads as blocking. Filter
  comments by `created_at` after the head commit's date (the last push — `gh pr
  view --json commits` or `headRefOid` + `gh api commits/<sha>`), and reduce
  reviews to the LAST state per author (GitHub's own `reviewDecision` does this
  for humans; the script must do it for the bot verdicts it aggregates).
- **Б7** `mergeOne` refuses `DIRTY`/`BLOCKED`/`BEHIND` with a message and no
  action; `duty` has no `base-merge` action; `workflows/fix-round.mjs` takes
  only `needsCiFix`/`needsReviewFix`/`attemptHistory`; `ci-fix.md` and
  `review-fix.md` reach `base-merge.cjs` only through "if the push is
  rejected". So the remedy documented in `CLAUDE.md` is reachable by prose
  alone. Add duty action `base-merge` (owner: the guard, role `ci-fix` tier —
  it is mechanical), a `needsBaseMerge` arg on `fix-round.mjs` whose prompt
  names `base-merge.cjs --worktree <path>` as the FIRST step, and make the two
  references state it as step 0 rather than as a fallback.
- `front.cjs` `fix` bucket must carry the reason (`base-merge`) so the duty
  line and the bucket agree (the ordering comment at line 428 explains why the
  two must not print different answers).

## Scope

- `sentinel.cjs duty`: `CHANGES_REQUESTED ∧ unresolved === 0` → `wait-human`
  (not in `ACTIONABLE`); `mergeStateStatus ∈ {DIRTY, BEHIND}` or `behindBy > 0`
  → action `base-merge`. `front.cjs`: matching `waiting.human` route and a
  `fix` entry with `why` = base-merge.
- `reviewers.cjs`: `feedback --since-head` default on (comments created after
  the head commit), `changes_requested` from last-state-per-author; `status`
  prints both the raw and the reduced view so a human can see the difference.
- `fix-round.mjs`: `needsBaseMerge: boolean`; when true the fixer prompt's first
  instruction is the base-merge invocation (exact string pinned in a comment
  and in `ci-fix.md`).
- `ci-fix.md`, `review-fix.md`: base-merge is step 0 when the dispatch says
  so; the CHANGES_REQUESTED-with-no-threads sentence is replaced by "not your
  case — the guard routes it to a human".

## Out of scope

`deliver.md`/`pr-sentinel.md` prose (T-24-07 documents the new action). The

## Acceptance criteria

- State: `review_decision: CHANGES_REQUESTED`, threads 0 → `duty` says
  `wait-human`, `computeFront` puts the ticket in `waiting.human`; with threads
  1 → `review-fix` / `fix` (unchanged). Today both say review-fix; the test
  fails on current code.
- `reviewers.cjs feedback` against a stubbed `gh` with two bot comments, one
  before and one after the head commit date → returns only the later one.
- `changes_requested` with reviews `[CHANGES_REQUESTED (bot, t1), APPROVED
  (bot, t2)]` → `false`.
- `duty` on a PR with `mergeStateStatus: BEHIND` → `base-merge`; the front's
  `fix` entry for it carries `why` containing `base-merge`.
- `fix-round.mjs` with `needsBaseMerge: true` hands its agent a prompt whose
  first numbered step contains `base-merge.cjs --worktree` (captured through a
  stubbed `agent`, see Test strategy); with it false/absent the prompt is
  byte-identical to today's.
