## Test strategy and release boundary

Ticket verification is scoped to the five commands below, including the doctor's source version-parity invariant and direct regular-file/nonempty notes-path checks. The coordinator supplies `GITHUB_BASE_REF=main` in the verification process environment so the marketplace test exercises the same freshness condition as integration to main; the PLAN command itself stays a supported simple `node` command. The package test builds and compares every generated file hash, including the derived version and digest. The release-gate unit test checks the existing receipt contract. No test fixture receipt counts as a live gate.

After the ticket merges, integration CI runs the full suite, including `make test-fast`, on the complete epic. After the epic reaches the final release tree, the release operator runs real `bash tests/live/live-round.sh --runtime claude` and `bash tests/live/live-round.sh --runtime codex` with installed hosts and a throwaway repository, then `node plugins/delivery-pipeline/scripts/live-receipt.cjs check --version 0.69.0 --tree-sha "$(git rev-parse 'HEAD^{tree}')"`. Both runtimes must have fresh passing receipts for the exact final tree and all required stages. Only then may `make release VERSION=0.69.0` create the local tag; publication separately pushes the tag and creates the GitHub Release with the notes file, followed by the remote release-notes smoke check. A ticket-branch receipt or fixture never substitutes for the final-tree runs.
