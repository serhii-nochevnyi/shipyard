## Reproduced case

T-43-10 PR #346 was `CLEAN`/mergeable and its `test-fast` run [36415123073](https://github.com/serhii-nochevnyi/shipyard/actions/runs/36415123073) succeeded at 11:25 UTC. The run log shows checkout of synthetic merge commit `15a927909f52f0dd642d56b04b5ece30e7d96f22`: head `f1eecaf606e26655268c2521f4fa8b78990ebbef` merged into then-epic `bf89a93fb9f4c89017f7e680511dad45bc9098de`. T-43-03 subsequently moved the epic to `305cae896aeaf761586454cb4f7a2ec2872dde8a` at 13:47 UTC. At inspection, PR #346 still reported `CLEAN` and its green check, but the checked-out combination named the old epic. Absence of textual conflicts does not prove tests against the new combination. The epic branch has no branch-protection rule; GitHub therefore does not require an up-to-date branch itself.

The installed `front.cjs` and `sentinel.cjs` compute `behind_by` even when GitHub reports `CLEAN`, and `sentinel merge` refuses a branch behind its base. Today the only supported remedy is `base-merge.cjs` into the ticket branch, a normal push, fresh CI, and a head-bound architecture gate. This preserves safety but changes the ticket head and can restart review/CI after every unrelated epic merge. T-43-05 and T-43-07 were mechanically base-merged after T-43-03; their prior green results could not be carried by the current contract. R3 already avoids judging lower-priority PRs before higher-priority merges, but it does not remove the mechanical push and CI wait.

On 2026-09-28, T-43-07 then passed exact-head `test-fast` CI on epic `f0e76f20d3ea69b4bdfc1cc89ed84f1a704c8883`, but its sealed native architecture review still found two source blockers in the missing-`ci-waits.json`/journalled-rerun path. This is a concrete counterexample to replacing independent architecture judgment with green CI or a clean merge-result attestation. R13 is limited to avoiding mechanical branch-update churn while preserving both gates.

GitHub documents that a `pull_request` workflow normally checks out the PR merge branch and tests the merged result. The local [test workflow](../../../.github/workflows/test.yml) uses `pull_request` and default `actions/checkout`, so its test identity must include the merge commit/tree and both parent SHAs, not just the PR head or green check name. GitHub also documents that **rerunning an old workflow uses the same original `GITHUB_SHA` and `GITHUB_REF`**; `gh run rerun` alone cannot certify a newly advanced epic. A merge queue is a possible hosted alternative for a protected, busy base, but GitHub says its required checks must run on `merge_group`; the current ephemeral epic branch and workflow have neither a merge-queue rule nor that trigger.

Sources: [GitHub Actions `pull_request` merge-branch semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request), [re-run SHA/ref semantics](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs), [protected-branch and merge-queue behavior](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## R13 research direction

Evaluate an exact merge-result attestation for a clean base move without changing the PR head. A trusted host or merge queue would compute the candidate from current base SHA plus unchanged head SHA, run the required CI on that precise commit/tree under the same workflow/tool configuration, then bind successful checks to repository, PR, head, base, merge tree/commit, workflow digest and run IDs. Immediately before merge, the gate must re-read the live base/head and prove the actual squash/merge result is the attested tree (or prove the precise equivalence required by the chosen merge method). If the base or head moves during testing or before merge, the attestation expires. GitHub `CLEAN` alone, an old check, a rerun of the old event, a local smoke test, or a reused arch-review verdict cannot stand in for this proof.

Investigate whether GitHub's merge queue can serve ephemeral epic bases with required checks and branch rules at acceptable setup cost, or whether an authenticated host check on a detached candidate is simpler. Preserve the existing base-merge path as fallback for conflicts, unsupported repositories, missing provenance, incompatible branch policy or changed governing inputs. Keep architecture judgment independent: phase-43 ADR-020 own-diff carry and phase-44 exact-input review reuse may reduce repeat model work only when their own identity contracts permit it; R13 cannot declare a changed-base review conform. Compare verified completion latency, CI runs, branch pushes, model review turns, escaped defects and refusal accuracy against the current base-merge flow. No claimed subscription saving follows from fewer GitHub CI runs alone.
