## Goal

REQ-158 separates completed code work from failed trusted finalization. The host persists an authenticated candidate before commit and can resume only that candidate after a signing, base-resolution or host error.

Moved verbatim from the checker-approved T-41-04 plan on 2026-09-25 (operator decision). The OS-sandboxed verification runner must be exercised by an environment that can run real `sandbox-exec`/`bwrap` denial tests (CI or an operator host), not inside a sandboxed executor.

## Scope

- After `launchAgent` returns, require the original `getVerifiedRecord` receipt, nonempty scoped delta and stable graph. Before finalizer call, the trusted host writes a 0600 atomic candidate under its outside-worktree state root. Bind canonical repository/worktree, ticket/branch/allowed paths, run/dispatch/launch IDs, authenticated receipt digest, graph and source plan digest, policy hash/model/effort, signer, expected HEAD/base, exact scoped tree digest, and every known verification command/artifact/status/digest. Required pre-commit host checks must pass; downstream CI/review gates remain explicitly pending until their trusted results arrive and cannot be reported green.
- **Trusted verification producer (implemented in this ticket):** add host-only `collectVerificationEvidence(prepared, verificationSpec)` to `codex-delivery-host.cjs` after verified executor completion and before candidate admission. Before model launch, pin the approved source PLAN and its verification specification: exact executable/argv/cwd, time/output bounds and required pre-commit gate IDs. Never accept commands or success values from executor output. Missing/unsupported specifications refuse with a named remedy. Implement `command-runner.cjs:createVerificationRunner` around `runBounded`; it returns actual process status, signal, error, timeout and bounded output, without a model/API call. It selects a host-approved OS sandbox backend (macOS `sandbox-exec`, Linux `bwrap`) and refuses when no supported backend or profile is available; never fall back to bare `runBounded`. Mount the exact repository/runtime dependencies read-only, an empty dedicated temporary directory as the only writable path, deny host state/HMAC/signing/key/socket paths and network, and pass only an explicit environment allowlist. Record backend realpath/digest and effective profile digest with every result. Test a hostile fixture command that tries to read a protected sentinel, write outside temp, or open a network socket; each must be denied by the actual OS backend in CI. The Codex permission profile alone is not evidence for this separately spawned process. Capture command/spec digest, run/dispatch, source plan/graph/policy, exact scoped tree before/after, status and bounded output digests. Nonzero, timeout, missing required check or changed scoped tree refuses finalization.
- **Authentication:** atomically persist versioned canonical verification records under protected host state and authenticate them with a separate host-owned HMAC key inaccessible to model and verification processes. Pin record digest in the candidate; resume verifies MAC, exact identity and every required result. Keys and runner callbacks are host configuration, never public executor request fields. Missing/corrupt records remain failed/pending; do not synthesize receipts. Original dispatch authentication still uses `getVerifiedRecord`. Downstream CI/review remains explicitly pending and gates merge, not initial commit. This scoped producer is delivered here, not assumed from phase 40.
- The finalizer exposes the exact tree it signs and compares it with the verified candidate; commit formatting stays in phase 40.
- Add the recovery-only CLI path `codex-delivery-host.cjs --resume-finalization <candidate-id> --scope-file <bounded-json>`. The scope file allows only repository/worktree/phase/ticket/run identity; it cannot carry prompts, role, dispatch ID, command specs, gate results, candidate paths or key material. The path creates a host-owned recovery run/owner lease and calls `host.resumeFinalization(candidateId, liveScope)`; it does not resolve a model, probe or launch Codex, call `launchAgent`, or start an executor. A missing candidate, missing original receipt, or runtime unavailability for ordinary dispatch cannot make this path launch an executor. It returns a typed finalization result or a named refusal. Test both CLI parsing and an end-to-end host fixture proving `launchAgent` call count remains zero.
- `resumeFinalization` authenticates the original durable dispatch receipt and verification-record HMAC, compares every live identity and verification item, then calls the existing finalizer without executor replay. A new recovery-specific idempotency claim fences concurrent attempts; the original failed controller run is immutable. On any changed identity, including base movement, refuse with named invalidated checks and leave candidate/gates visible. No partial revalidation is authorized.
- For crash after commit, recognize an already finalized candidate only if trusted finalization record, signed commit/signer, parent, tree, HEAD and scoped changed paths all match; return the same artifact. Otherwise refuse for reconciliation.

## Acceptance criteria

- REQ-158 candidate survives each finalization failure, is authenticated against original durable dispatch and remains visible with failed/pending gates; downstream gate completion is never inferred from signed commit.
- Real OS sandbox backends deny the hostile fixture's protected read, outside-temp write and network access in CI.
- The human checkpoint reviews the completed candidate and exact tree/gate binding before recovery is authorized. Changed identity has explicit refusal, and the T-39-16 scenario separates executor, finalizer and necessary revalidation usage.

## Test strategy

RED → GREEN → REFACTOR for candidate creation and recovery. Use isolated Git fixture repositories with signing configured by test harness. Live signing/host failure remains an operator/CI acceptance check.
