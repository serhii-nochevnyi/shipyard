## Goal
Reduce per-ticket bookkeeping overhead and make a whole launch wave's
attribution atomic. This is a dispatch-record slice of OPT-03; it does not
change model selection or launch behavior.

## Context (Reads)
ADR-011 D1, D8 and D11; ADR-011-ROLLOUT OPT-03; ADR-012 task-level model
ladder; `dispatch-record.cjs`; `pipeline-stats.cjs`; and the 2026-09-10 usage
audit showing repeated per-ticket orchestration calls and incomplete historical
dispatch metadata.

## Scope
Add `mark-many --stdin`, accepting a JSON array with the existing mark fields.
Validate every item and every ticket before mutation, write one dispatch event
per item under one lock, and refresh the derived front once. Preserve the
existing single-ticket command and its field semantics. Keep omitted and
unsupported observations explicit; never infer them from requested values.

## Out of scope
Model or effort policy changes, agent launches, workflow changes, automatic
runtime observation, subscription attribution, backlog lifecycle writes, and
global Claude/Codex settings.

## Acceptance criteria
- A valid multi-ticket payload creates one active record and one journal event
  per item, with the same resolver and observation fields as `mark`.
- Any duplicate, unknown ticket, unknown field, non-string value or invalid mark
  field rejects the entire payload before the store or journal changes.
- A concurrent state change is checked while the mutation lock is held; no
  record gets a fingerprint for a missing ticket.
- The front refresh is attempted once after a successful batch; the durable
  records remain valid when no front exists yet.
- The existing single-ticket path and all prior dispatch-record tests remain
  unchanged.
- The command is read-only with respect to policy and launch; it makes no
  quota/savings claim.

## Test strategy
Exercise a complete Workflow-shaped batch, verify exact store/journal counts,
and add a negative all-or-none case. Retain the existing full dispatch-record
and unit suites.
