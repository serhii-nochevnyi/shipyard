## Acceptance criteria

- With the environment reduced to PATH and HOME, `codex-delivery-host.cjs --args-file <pr-sentinel request>` run from `<custom Codex home>/shipyard/scripts` is admitted and reaches the native CLI call: `classifyLaunch` returns `reached`, meaning the fake `codex` logged exactly one `exec` invocation and the host ended with exit 0 or, because the fake emits no native evidence, with exit 1 and only `RUNTIME_EVIDENCE_*` codes on stderr (the expected terminal outcome, not a failure). The scenario never asserts that the host exited 0. The admission created its authority state under the fixture HOME, and the fake records `CODEX_HOME` equal to the realpath of the custom home (a path that is not `<HOME>/.codex`).
- Flipping one byte of the installed `codex-capabilities.json` makes the same launch `refused` (`classifyLaunch`: zero `exec` lines, non-zero exit) with exactly the code `CAPABILITY_EVIDENCE_STALE` on stderr as `hint[CAPABILITY_EVIDENCE_STALE]`, creates no `role-artifact-authority` directory and no provenance sidecar under the fixture HOME, and never invokes the fake `codex exec`.
- Exporting a `CODEX_HOME` that names a different directory makes the launch `refused` (zero `exec` lines, non-zero exit) with exactly the code `ENV_CONFLICT` as `hint[ENV_CONFLICT]` and a message naming both values.
- Source-checkout behaviour is unchanged: `tests/unit/runtime-context.test.cjs`, `tests/unit/codex-runtime-host.test.cjs` and `tests/unit/codex-delivery-host.test.cjs` pass without any edit.
- `--capability-only` on `codex-runtime-host.cjs` still exits 0.
- Harness isolation: every host run in the scenario goes through the write guard, whose violation log is empty at the end (no mutation outside the fixture work root, including under the real user's home that `os.userInfo().homedir` would reveal); after the admitted launch (case 1) the authority state the host created lies under the fixture HOME; a negative control, a child run under the same guard that writes a file beside the work root, is recorded, proving the guard can fail. The guard covers every host run, which is the code under test; the installer run that lays the bundle down is set up with HOME, CODEX_HOME and its own variables pointing into the work root and sits outside the guard (its isolation is the contract of the existing installer smoke). The scenario never lists, reads or compares the real `~/.local/state/shipyard` or `~/.codex`.
- SUMMARY records the observed child `CODEX_HOME`. It does not claim anything about a Codex home without a login: a fake `codex` cannot observe that, so it stays assumption A3 of 50-RESEARCH and is measured by the release live receipt (T-50-27 checklist, T-50-13). It also states the write guard's coverage limit from "Recorded limits" below.

## Recorded limits

- **Write guard coverage.** The guard is a `--require` module given to the host's own node process through node argv. It does not cover the processes that host spawns (the fake `codex`, `git`, `sh`): the host's environment carries only PATH and HOME, so there is no `NODE_OPTIONS` or other variable that could carry the guard into a child, and node argv does not pass to children. Those descendants are confined only by HOME being the fixture HOME and by being fake CLIs and git operating in fixture repositories. A descendant that wrote to an absolute path outside the work root would not be caught, and the negative control proves only that the guard fails on the host process. This is an accepted limit; the scenarios claim "no mutation outside the work root by the host's node process", not "by every descendant", and T-50-23, T-50-24 and T-50-25 repeat it.
- **Task 1 weight.** Task 1 carries the fixture library, the guard, the resolver and the two host wirings because the tracer must remain one end-to-end slice; it is not split further. Inside the task commit in three steps (the red scenario with `lib.cjs`, including its `classifyLaunch` helper; the `runtime-context.cjs` resolver; the `codex-runtime-host.cjs` and `codex-delivery-host.cjs` wiring) so a revert can drop one step.
- **Task 2 is characterisation, not red-first.** `launch-environment.test.cjs` is written after the tracer implementation and starts green, so the task is not marked `tdd="true"`; the red-first evidence for the same three behaviours, and for `classifyLaunch`, is the tracer scenario written red in Task 1.
- **Success is defined at the native CLI call.** The fake `codex` logs and exits 0 but emits no JSONL and no native session transcript, which the host demands after its child exits 0 (`codex-runtime-host.cjs` near `:260-263`, `:2921-2960`, `:1160-1189`). An admitted host therefore ends with exit 1 and `hint[RUNTIME_EVIDENCE_MISSING]` after exactly one exec, and this scenario treats that as the expected terminal outcome of an admitted launch. It does not give the fake native evidence, because that would model the very behaviour the live receipts (T-50-13, T-50-27) own. If the observed terminal code after the single exec is not in the `RUNTIME_EVIDENCE_*` family, that is a finding against this definition, never a reason to widen `classifyLaunch` silently.
