<objective>Replace the single refusal "unknown host provenance member before trusted mutation" with ADR-030's adoption: classify, adopt once under the existing lock, record the inventory in the protected state as historical-unverified, and keep every new or altered member refused.</objective>

## Goal

ADR-030 L-4 and L-5 and the first failure in INV-017: an upgraded project carrying 64 old sidecars refuses every launch (`ARCHIVE_AUTHORITY_INVALID`) and the only recovery was a manual deletion of history.

## Scope

Inside `role-artifact.cjs` only: (1) a pre-lock guard in `trustedBookkeepingMutation`: when no authority catalogue exists and the provenance directory has members, call the classifier and refuse a `blocked` result with its finding's code before `withArchiveAuthorityLock` can create anything; (2) under the lock, re-classify and, for `adoptable` and for no other state (an `unreadable` result, which the T-50-04 classifier returns when the protected authority namespace cannot be read, neither refuses nor adopts here: the guard lets `withArchiveAuthorityLock` run, which raises its own raw error exactly as before this phase), write `payload.legacy_bookkeeping = { schema, version, status: 'historical-unverified', adopted_at, members: [{ path, bytes, sha256 }] }` without touching `bookkeeping_state`; (3) allow authenticated paths together with recorded legacy paths in both inventory checks while keeping `bookkeeping_state` built only from authenticated and newly written paths; (4) re-read every present legacy member at each mutation and refuse a changed one with `LEGACY_HISTORY_CHANGED` before invoking the callback; (5) refuse an unknown member after adoption, or whenever an authenticated record already exists, with `LEGACY_HISTORY_UNKNOWN_MEMBER` while keeping the message prefix `unknown host provenance member`; (6) export nothing new except what T-50-04 already exports. Decisions taken here (ADR-030 leaves them to decomposition): a legacy member removed from disk after adoption is a preflight warning, not a refusal; adoption is recorded once and never repeated.

## Out of scope

The route in `dispatch-record.cjs` (T-50-09), lock liveness (T-50-08), preflight wiring, changing `historicalBookkeepingPins`, deleting, archiving, moving or rewriting any member, any new coordination beyond the existing catalogue lock (ADR-030 L-8).

## Acceptance criteria

- Adopting a project with 64 sidecars and no catalogue succeeds on the first `trustedBookkeepingMutation`; the sidecar bytes are identical before and after; `catalogue.json` holds one `legacy_bookkeeping` block with 64 members and status `historical-unverified`; `historicalBookkeepingPins` returns only authenticated pins; a second mutation changes no legacy record byte.
- A changed legacy member, a symlink or nested-directory member, an oversize inventory and an unknown member each refuse with the specified code before the callback runs; the first three leave `archiveAuthorityDirectory` absent when no catalogue existed.
- An authenticated record plus a forged unknown member still refuses with a message containing `unknown host provenance`.
- Two sequential adoptions of different worktrees do not interfere (the catalogue is per worktree).
- With the authority namespace unreadable (an `EPERM`-coded error injected on its `fs.lstatSync` with `mock.method`), `trustedBookkeepingMutation` on a legacy-bearing project adopts nothing and writes nothing: it fails with the same raw error as before this phase, creates no directory and leaves every sidecar byte-identical.
- Existing `role-artifact.test.cjs` assertions pass; each deliberate edit (for example a test that expected refusal of a legacy-only directory) is named in the SUMMARY.
