# Phase 50 — Make launch and upgrade reliable

Status: operator-approved scope from accepted ADR-030, 2026-10-15; PLANs 50-01 through 50-29 exist and carry the round-1 to round-5 plan-review revisions (see `50-REVIEWS.md`); the ticket graph is produced from them by the decomposition gates.

## Goal

After install or upgrade, the ordinary command works in an existing project on both runtimes with no manual `export`, no artifact cleanup and no knowledge of internal host commands. This is the readiness criterion of ADR-030.

## Source of truth

- Accepted ADR: `.planning/architecture/ADR-030-launch-and-upgrade-reliability.md` (decisions L-1…L-11), linked from `INV-017-launch-and-upgrade-reliability` (closed 2026-10-15).
- Evidence: `INV-017-launch-and-upgrade-reliability/EVIDENCE.md`, `research/*`, `spikes/SPIKES.md`.
- Baseline: Shipyard `v0.72.2` (`be7ab4f3`). Design is bound to it, not to `d8a70dec`.

## Locked scope (from ADR-030)

Library-first shape with no launcher, no persisted launch context, no new script file; self-locating environment with digest-verified capabilities and a refusal on env/bundle conflict; automatic one-time adoption of legacy sidecars as `historical-unverified` in the protected authority state; changed legacy member or later unknown file blocks with a named remedy; shared preflight in every host before `controller.begin` with `--preflight`; Claude and Codex share one route; existing catalogue lock only for concurrency; one `repositoryIdentity()` and one subject grammar contract; hermetic CI acceptance core plus live receipts at release.

## Planning mode

`--tdd`, granularity `fine`. UI design: none, so `--skip-ui`.

## Constraints to carry into every ticket

- Never weaken provenance, receipts, host-owned writer/lease, or the ADR-014 boundary; legacy files are never promoted to trusted evidence.
- `role-artifact.cjs` and `dispatch-record.cjs` changes need the runtime-digest refresh (`make refresh-runtime-digests`) and a regenerated `plugins/shipyard` package on main-bound PRs; never edit generated files by hand.
- Authority-touching tests override `os.homedir` (the `role-artifact.test.cjs:7-13` header, applied before any plugin module is required; setting `HOME` alone is not enough because the authority namespace calls `os.homedir()` at call time). This includes every test that runs `preflight` or `launch` in the test process (T-50-11, T-50-12, T-50-20), and the header's first test asserts the override. The acceptance harness isolates every state root and proves real user state is unchanged by asserting that no write lands outside harness-owned roots (a write guard supplied through node argv, plus the authority state of a launch sitting under the fixture HOME). It never lists, reads or compares the real state directory: a before-and-after listing races with concurrent real sessions and cannot be read under the Claude sandbox.
- Recorded limit of that guard: it is a `--require` module on the host's own node process only. The processes the host spawns (the fake CLIs, `git`) are outside it, because the host environment carries only PATH and HOME and so cannot carry the guard into a child; they are confined only by HOME being the fixture HOME. The scenarios claim "no mutation outside the work root by the host's node process", not by every descendant (T-50-01 records it; T-50-23, T-50-24 and T-50-25 repeat it).
- The unauthenticated linked-worktree sidecar write path found by spike S-1 must be covered, and only by host admission: adoption and its refusals are triggered through `recordInflight` and `clearInflight` (the three launch-admitting hosts). The orchestrator's direct `dispatch-record.cjs mark`, `mark-many`, `clear`, `clear-many` and `clear-round` paths and the round functions never adopt history and keep their behaviour, pinned by a test.
- Preflight classifies the provenance directory and authority key that admission will use: each host passes the graph directory it records into, and the bookkeeping root is derived from it as `dispatch-record` does, never from the request worktree.
- Every remedy in the hint map, old and new, is a documented marketplace command or a `node {bundle}/scripts/<script>` invocation of a script that ships in the bundle; none is checkout-relative (`make`, `plugins/` or `scripts/` paths, installer scripts) and none touches history.
- Concurrent first admission ends only in success or a named `ARCHIVE_AUTHORITY_BUSY` refusal: the authority key is created atomically (a complete temporary, linked to `hmac.key`, the temporary then unlinked), and every unlocked read of the key and of the catalogue retries a transient stat change a bounded number of times, because `authorityFile` compares `ctimeMs` and the unlink of the temporary changes the visible key's ctime after the key is already readable (T-50-08).
- An unreadable protected authority namespace (the Claude sandbox denies the model that directory, and `deliver-dispatch launch` runs preflight in the caller's process) never aborts a preflight or refuses a launch without a hint: the classifier returns state `unreadable` instead of rethrowing the raw error `role-artifact.cjs:1004-1005` produces, preflight records `legacy history: not evaluated, authority namespace unreadable (<code>)` as a note and keeps running every other check, and admission, which runs in the host where the state is readable, decides. `unreadable` is never `adoptable`: adoption writes only for `adoptable`, and the linked-worktree route takes the trusted path for it (T-50-04, T-50-07, T-50-09, T-50-11, T-50-20).
- The Claude installed layout, the fake `claude` that satisfies `probeClaudeRuntime` and the Claude project fixture have one owner: T-50-28 adds `stageClaudeLayout`, `installFakeClaude`, `installFakeGh`, `stageClaudeProject` and `writeClaudeRoleRequest` to `tests/smoke/installed-launch/lib.cjs`, pinned by `tests/unit/installed-launch-claude-layout.test.cjs` and `tests/unit/installed-launch-claude-project.test.cjs`, and the three scenarios that need them (T-50-23, T-50-24, T-50-25) depend on T-50-28 and neither duplicate the staging nor edit `lib.cjs`. None of the three depends on another of them: T-50-25 relies on the fixture T-50-28 supplies, not on anything T-50-23 records.
- The Claude role host cannot be driven to admission with a bare directory, and the fixture supplies exactly what it demands before `controller.begin` and `recordInflight` (`claude-role-host.cjs` `prepareInvocation` near `:902-917`, which also runs for `pr-sentinel` through `prepareSentinel` near `:695-811`; the CLI passes no options near `:1603-1604`, so nothing can be injected): a clean git work tree on `main` with a ticket row and its plan file (`rowFor` near `:205-213`, `sourceReferences` near `:388-402`, which needs an `## Acceptance criteria` list and at least one ADR file), a local `.planning/graph/` holding `tickets.json` and a `pr-open` row of `delivery-state.json`, an `origin` remote that `git fetch --no-tags origin +refs/heads/main:refs/remotes/origin/main` accepts (`branchOid` near `:223-242` and `sentinel-preflight.cjs` `fetchBase`) with `origin/HEAD` set so `baseDefaultBranch` resolves without `gh`, and a fake `gh` that answers `repo view`, `pr list`, `pr view`, `pr checks` and the three `gh api` shapes consistently with that delivery state, because the sentinel round preflight runs `state-sync.cjs` in the project (`sentinelPreflightRound` near `:674-693`, `preflightRound` in `sentinel-preflight.cjs`) against the fake `gh` and the project config (`delivery_pipeline.gsd_sync: false`). The graph directory is excluded locally (`.git/info/exclude`, never the real repository) and not committed, because that state-sync run rewrites graph files and `sentinel-preflight.cjs` `maybeCommitGraph` would commit them when `delivery-state.json` is tracked, moving `HEAD` under the host. A Claude host run adds exactly one variable to PATH and HOME: `TMPDIR`, inside the fixture work root, because the Claude runtime launcher creates its SessionStart evidence directory with `os.tmpdir()` (`claude-runtime-host.cjs` near `:735`), which without it is the system `/tmp`, outside the harness work root (the write guard records it) and refused under the Claude sandbox (`EPERM` at `mkdtemp`); `TMPDIR` is neither a `CLAUDE_*` nor a `SHIPYARD_*` input, so it does not weaken L-10's no-environment claim. Two Claude role hosts, or a Claude host and a host admitting the same ticket, on one project refuse the second with `round ticket T-... already has active dispatch ownership` from `reserveRound` (`dispatch-record.cjs` near `:1652`), so the concurrency scenario gives the Codex request a different ticket (the fixture's second, `pending` ticket in another phase) than the Claude round's member. Planning evidence, not a deliverable: a throwaway prototype of this fixture, built in a scratch directory outside the repository, drove the current checkout's `claude-role-host.cjs` from a staged copy to exactly one fake `claude` invocation on each of two consecutive launches of one project, with the project's `git status` clean afterwards, an emulated write guard logging nothing, the authority state under the fixture HOME and the provenance sidecar in the project's graph directory, and the run ending `claude-runtime-host: Claude stream contained no JSON records` (`RUNTIME_EVIDENCE_MISSING`); the same run without `TMPDIR` stopped with `EPERM` at `mkdtemp` in `/tmp`, and two concurrent Claude hosts on one ticket refused the second with the ownership message above. The production host was not modified; the executor of T-50-28 rebuilds the fixture in `lib.cjs` and pins it with the unit test.
- Every subject producer, including the architecture-review producers (`deliver-dispatch.cjs build`, `codex-arch-review-context.cjs`, `claude-role-host.cjs`), builds its repository through `repositoryIdentity()` or is round-tripped from its real entry point.
- The UI smoke (`gsd-ui-phase` then `gsd-ui-review`) is a declared gap only after a bounded, read-only check for a non-interactive, non-model driver has been made and recorded (assumption A7 is verified, not assumed). The check reads the GSD core install an operator would run (`${CLAUDE_CONFIG_DIR:-${CLAUDE_HOME:-$HOME/.claude}}/gsd-core`, `${CODEX_HOME:-$HOME/.codex}/gsd-core`, the roots T-50-06 records), resolved from the scenario process's own environment and never from the fixture HOME, whose `gsd-tools` is a stub. It has four statuses: `found`, `absent`, `unreadable` (an install exists but a read is refused) and `not-installed` (no GSD install exists in the environment, the expected CI status because `make test-fast-rest` installs none). `not-installed` is a passing, declared gap that keeps A7 open until a release receipt on a machine with GSD installed; the absence of GSD never turns the scenario red, and a unit test pins the record shape for every status (T-50-25).
- Whether a Codex home without a login is visible to the child (assumption A3) cannot be observed with the fake `codex` the hermetic scenarios use; only the release live receipt measures it.
- Hermetic host outcome (T-50-01, T-50-23, T-50-24, T-50-25). The fake `codex` and `claude` of the installed-package scenarios emit no native evidence, but after a native child exits 0 each host verifies exactly that evidence: Codex wants JSONL with a thread id and a completed turn with usage (`codex-runtime-host.cjs` near `:260-263`) and then a native session transcript (near `:2921-2960` and `:1160-1189`); Claude wants a stream with a session identity and SessionStart-hook launch evidence (`claude-runtime-host.cjs` near `:281-282`, `:411`, `:475`, `:553`, and `claude-role-host.cjs` near `:1489`). With the specified fakes an admitted host therefore ends with exit 1 and `hint[RUNTIME_EVIDENCE_MISSING]` after exactly one native invocation, so no hermetic scenario may assert that a host exits 0 or that a launch "succeeds". Host success in these scenarios is defined as admitted and reached the native CLI call, classified by one pure helper, `classifyLaunch(run, cliLines)` in `tests/smoke/installed-launch/lib.cjs` (owner T-50-01, pinned in `tests/unit/launch-environment.test.cjs`; T-50-23, T-50-24 and T-50-25 call it and do not edit `lib.cjs`), from the lines that host's own fake CLI appended during the run (the fakes log only native invocations, never their `--version`, `--help` and `auth status` probes) and from the `hint[LABEL]` codes on its stderr. `reached` means exactly one native invocation and either exit 0 with no code on stderr or a non-zero exit whose every stderr code is in the `RUNTIME_EVIDENCE_*` family; that terminal `RUNTIME_EVIDENCE_*` outcome after exactly one exec is expected and is never a failure. `refused` means zero native invocations, a non-zero exit and at least one stderr code, which the scenario then asserts by name (`ARCHIVE_AUTHORITY_BUSY`, `LEGACY_HISTORY_CHANGED`, `LEGACY_HISTORY_UNKNOWN_MEMBER`, `LEGACY_HISTORY_UNSAFE`, `CAPABILITY_EVIDENCE_STALE`, `ENV_CONFLICT`). Everything else is `unclassified` and fails the scenario: a second native invocation, a code outside the `RUNTIME_EVIDENCE_*` family after the native call, exit 0 with no native call, a signal, an `ARCHIVE_AUTHORITY_INVALID` torn read. A refusal by name is always before the native call, because both hosts record admission (`recordInflight`, `codex-delivery-host.cjs` near `:3523`, `claude-role-host.cjs` near `:1463`) before launching and swallow a `clearInflight` failure on the way out; "admitted" is therefore evidenced by the fake's log. Claims of "adopted once", "no second adoption", "the following launch succeeds" and "a third launch succeeds" are stated and asserted in these terms: the launch is `reached`, and the `legacy_bookkeeping` members read through `legacyBookkeepingMembers` (one block, 64 members) are unchanged, compared as serialised JSON, across the next admission. A host that stops before the native call for a reason the fixture does not model is `unclassified` in every scenario (T-50-23, T-50-24 and T-50-25 alike), fails the scenario and is returned as a finding against the fixture owner (T-50-01 for Codex, T-50-28 for Claude), never absorbed into the definition and never recorded as a documented gap: ADR-030 L-10 requires the no-environment launch and the concurrent launch on both runtimes, and only the UI smoke has a declared-gap allowance. The Claude fixture of T-50-28 is built so that the Claude role host does reach its native call (previous bullet). The native evidence itself is out of reach of the hermetic core and belongs to the live receipts (T-50-13, T-50-27).
