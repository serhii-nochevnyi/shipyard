# Alternatives — INV-011 model ladder refresh

**Decision boundary.** This report compares implementation paths; it does not select one. All candidate paths use the exact operator matrix in `docs/audits/2026-09-30-model-ladder-refresh.md:69-103` and `.planning/investigations/INV-011-model-ladder-refresh/DECISIONS.md:1-15`. Source inspection was pinned to `c105349656e445275db8b72cebd398c670f1b5ae` [V1]. The existing policy is `adr-014.v6`, with nine native roles and two runtime grids in `plugins/delivery-pipeline/scripts/model-policy-internal.cjs:26-59,68-203` [V2]. Model quality, subscription cost per accepted outcome, and live account access to each proposed pair are **unknown**. The next checks are a bounded host dispatch after activation and matched outcome observations; source inspection cannot answer them.

## Comparative options

| Path | Sketch and delivery cost | Main risks | What it forecloses or defers |
|---|---|---|---|
| **A. Retain v6; collect evidence** | No migration or install. Keep the present Sol 6, Luna/max, Opus/medium and Sonnet alias grid (`model-policy-internal.cjs:68-148`); use only current evidence collection. Lowest engineering cost. | Does not adopt the approved placement; alias can still observe an older Sonnet (`runtime-adapters.cjs:26-30`). Any apparent economy says little about the proposed ladder. | Defers the requested production policy migration and real application proof for the new pairs. It remains a valid historical control, not a substitute for delivery. |
| **B. One coherent new policy version** | Amend ADR-014 and ship the whole selected native grid in one new version: palette, rungs, signals, generated Codex agents, installer payload, config compatibility, fixtures and docs. Moderate concentrated cost; one review/install transition. | Many simultaneous tuple changes complicate attribution of quality or quota changes. Claude executor's capability-failure and proven-harder paths need a precisely authenticated signal or attempt contract before they can be routed (`model-policy-internal.cjs:324-449,183-198`). | Gives up clean intermediate production cohorts for identity-only and role-placement effects. Later experiments can still compare against preserved v6 records. |
| **C. Staged versioned activation** | First version pins `gpt-6.1-sol` and `claude-sonnet-5-5` while preserving role efforts and signals; later version(s) introduce Sol 6.1/low bases, Sonnet/xhigh judgment roles and Claude execution/repair rungs. Each stage regenerates, verifies and installs the full bundle. Higher repeated review and installation cost. | Old-stage receipts cannot be silently promoted into new-stage repair predecessors; in-flight work needs explicit policy reconciliation. Mixed installations or partially updated docs can refuse. | Defers complete adoption until the final stage, but permits clearer attribution to identity versus placement. A stage is a complete policy, never a config-only override. |
| **D. Redesign the host and outer coordinator alongside the ladder** | Rework session selection, handoffs, scheduling/context reuse and native dispatch together. Highest cost and cross-owner surface; overlaps ADR-023 phase-45 D1/D2/D6, C1/C2/C3 and phase-43 hot files (`.planning/architecture/ADR-023-residual-pipeline-efficiency.md:28-50`). | Creates more launch/receipt and ownership failure modes; makes model effects inseparable from context effects. Native policy does not presently govern the outer parent (`docs/audits/2026-09-30-model-ladder-refresh.md:115-131`). | Defers a small reviewable ladder migration and risks superseding active work. It may address parent inheritance, which B and C alone cannot change. |

**Interpretation.** A is the “do nothing” control. “Buy” is not a separate viable native alternative: these are selection and verification rules for already-used provider subscriptions, while external provider access remains an account/host fact to check. D is materially different because it changes the control plane rather than only the versioned native policy. The September audit's provider facts and pricing are advisory inputs (`docs/audits/2026-09-30-model-ladder-refresh.md:29-63`), not a measured Shipyard outcome or a reason to infer savings.

## Smallest complete delivery slices and dependencies

For B, and **for each complete activation in C**, the fastest self-contained native slice has the following dependency order. Independent Codex and Claude test/fixture preparation can proceed together after the accepted version specification; source generation, install and dispatch must follow their prerequisites. This is a proposed work breakdown, not a claim that any slice has shipped.

1. **Policy specification and identity.** Record an ADR-014 amendment with the exact role/rung table, signals, version and fingerprint. Change `runtime-adapters.cjs:9-30` for Sol 6.1 and pinned Sonnet 5.5, then `model-policy-internal.cjs:26-40,68-203,237-265,303-322` for the native grid and derived repair prerequisites. The current signal validator accepts only a fixed key set (`model-policy-internal.cjs:324-449`); define a typed, host-proven capability-failure/proven-harder signal before adding Claude executor Sonnet/high or Opus/high. Keep Fable's 250,000-token window rule as specified (`model-policy-internal.cjs:38-40,192-195`). Do not fold the independent outer-coordinator candidate into the native nine-role hash (`docs/audits/2026-09-30-model-ladder-refresh.md:115-131`).
2. **Apply through both runtime adapters.** `codex-model-remap.cjs:75-89,124-145` rejects a noncanonical model remap, so a project config override cannot implement this. `codex-dispatch-adapter.cjs:218-234,284-327,428-462` requires supported model/effort pairs and validates static file identity, digest and immutable handoff; dynamic executor/decomposition get explicit model and effort. `claude-dispatch-adapter.cjs:377-402,583-632` requires pair support, exact-session observation and receipt fields. The pinned Sonnet value takes exact-equality fallback in both `runtime-adapters.cjs:26-30` and `claude-runtime-host.cjs:295-299`; an older-Sonnet negative fixture should verify that path. A host matcher edit is conditional on that fixture failing. The Claude probe advertises local palette values but declares `live_execution: not_run` (`claude-runtime-host.cjs:220-239`), so preflight is not application proof.
3. **Generate, package and install coherently.** `scripts/gen-codex-shipyard.cjs:293-315,355-390` embeds version/hash and selections in static agent files and digested manifest. Update the source host package mirrors as part of the reviewed change, then use `scripts/install-shipyard-codex.sh:276-293` to validate staged capabilities before replacement. Config/projection checks in `plugins/delivery-pipeline/scripts/pipeline-config.cjs:1398-1465,1713-1717` must accept only the canonical new identity and continue refusing conflicting overrides. Preserve historical v6 receipts and installed evidence; do not relabel them to the new fingerprint. The new version must be active in the actual host before a new-grid run counts as adoption.
4. **Verify and document.** Update tuple and negative cases in `tests/unit/model-policy.test.cjs:42-60,102-151,289-318`, `codex-dispatch-adapter.test.cjs:113-168,199-228`, `claude-dispatch-adapter.test.cjs:23-65`, `model-capability.test.cjs:38-57`, `claude-runtime-host.test.cjs:160-185`, `gen-codex-shipyard.test.cjs:153-154`, and `tests/smoke/model-ladder-runtime-smoke.sh:53-56,223-227`. Verify absent/forged/stale receipts, wrong policy/hash, older observed Sonnet, unsupported pairs and stale static agents. Refresh `plugins/delivery-pipeline/commands/decompose.md:130-185,188-216`, `deliver.md:366-475`, ADR-014 and any installed guide that prints the grid. Then obtain host-owned requested/applied/observed model and effort plus installation provenance through a bounded real dispatch. Existing source tests only test the old policy.

## Exact repair and capability boundaries

Both fix roles must use these **new-policy** ordered chains from the approved target (`docs/audits/2026-09-30-model-ladder-refresh.md:80,99`): Codex `gpt-6.1-sol/low` → verified `gpt-6.1-sol/high` → verified `gpt-6.1-sol/xhigh`; Claude `claude-sonnet-5-5/high` → verified `claude-sonnet-5-5/xhigh` → verified `claude-opus-5-5/high`. The `repeat` predecessor is the base tuple and `repeat_exhausted` predecessor is the middle tuple. Policy derives these exact prerequisites from adjacent rungs (`model-policy-internal.cjs:237-265`), while the boundary rereads a durable `previous_dispatch_id`, checks ticket, role, runtime and requested/applied pair, and prevents reuse (`dispatch-boundary.cjs:1860-1929`). It also checks policy identity in application receipts (`dispatch-boundary.cjs:1331-1371`). Do not accept a caller-supplied receipt-shaped object as the predecessor.

For a **model-axis** promotion, the current boundary also evaluates a launch-bound capability snapshot and, when required, a completed attempt; unsupported/unknown pairs take the defined previous-rung path or refuse (`model-capability.cjs:38-80,117-134`; `dispatch-boundary.cjs:2025-2060`). An effort-only step still needs adapter pair support and observed application (`codex-dispatch-adapter.cjs:218-234`; `claude-dispatch-adapter.cjs:377-402,583-605`). Proposed Claude executor Sonnet/medium → Sonnet/high after capability-related failure and Sonnet/xhigh → Opus/high for proven harder reasoning need a new trustworthy attempt classification. **Unknown:** which host owns and persists that classification. Next check: inspect the accepted policy amendment and the delivery host's attempt artifact before implementing those signals. No invented flag or arbitrary per-dispatch override should stand in for it.
